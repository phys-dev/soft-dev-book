Разработка и применение программного обеспечения в физических исследованиях

Docker

Git запоминает историю кода. Но код сам по себе ничего не воспроизводит: расчёт зависит ещё и от версии Python, набора библиотек, системных пакетов и десятка настроек, которых в репозитории нет. На этом стыке и ломается воспроизводимость чужих результатов — его и закрывает следующий инструмент.

«У меня на машине работает»

Знакомая ситуация: ты написал скрипт обработки данных с эксперимента, он прекрасно работает на твоём ноутбуке. Отправляешь коллеге — у него падает с ImportError. Запускаешь на кластере — там Python 3.8 вместо твоего 3.12, системный numpy собран без нужных флагов, а права на установку пакетов есть только у администратора, который в отпуске. Через два года рецензент просит воспроизвести график из статьи, а ты уже и сам не помнишь, какие версии библиотек тогда стояли.

Для физики это не мелкая бытовая неприятность, а удар по главному принципу науки — воспроизводимости. Численный результат, который нельзя повторить, стоит немногим больше, чем результат, которого нет. Виртуальные окружения и requirements.txt решают проблему лишь частично. Они фиксируют версии Python-пакетов, но не версию самого Python, не системные библиотеки (BLAS, LAPACK, HDF5, компиляторы), не переменные окружения и не операционную систему.

Docker решает проблему радикально: ты упаковываешь приложение вместе со всем его окружением — интерпретатором, библиотеками, системными зависимостями, настройками — в единый образ. Этот образ запускается одинаково на твоём ноутбуке, на машине коллеги и на сервере лаборатории. «У меня работает» превращается в «работает у всех».

Контейнеры vs виртуальные машины

Первая мысль: «это же виртуальная машина». Нет, и разница принципиальна. Виртуальная машина эмулирует целый компьютер — внутри неё крутится полноценная гостевая операционная система со своим ядром, и гипервизор транслирует её обращения к железу. Изоляция надёжная, но дорогая: каждая ВМ занимает гигабайты и стартует десятки секунд.

Контейнер же — обычный процесс операционной системы, которому ядро Linux «подкрутило» два механизма. Namespaces (пространства имён) изолируют то, что процесс видит: у контейнера свои дерево процессов, сетевые интерфейсы, файловая система — он искренне считает, что один в системе. Cgroups (control groups) ограничивают то, что процесс потребляет: сколько памяти, процессорного времени и дискового ввода-вывода ему доступно. Ядро при этом общее для всех контейнеров и хоста, поэтому контейнер стартует за доли секунды, а образ весит от десятков до сотен мегабайт вместо гигабайт. Плата за лёгкость — чуть более слабая изоляция, чем у ВМ. Для запуска чужого недоверенного кода это важно, для упаковки собственных расчётов — нет.

На macOS и Windows нативных Linux-контейнеров не бывает, поэтому Docker Desktop незаметно для тебя держит лёгкую виртуальную машину с Linux, внутри которой и живут контейнеры.

Образы и контейнеры

Два центральных понятия, которые важно не путать:

  • Образ (image) — неизменяемый шаблон: файловая система с установленными программами плюс метаданные (какую команду запускать, какие порты открывать). Аналогия из программирования: образ — класс.
  • Контейнер (container) — запущенный экземпляр образа, живой процесс со своим состоянием. Контейнер — объект, экземпляр класса. Из одного образа можно запустить хоть сотню контейнеров.

Начнём с готовых образов. Их скачивают из реестра (по умолчанию — Docker Hub):

# скачать официальный образ Python 3.12 (slim — урезанный, без лишнего)
docker pull python:3.12-slim

# список локально скачанных образов
docker images

Запись python:3.12-slim читается как «репозиторий:тег». Тег — версия. Если тег не указать, подставится latest, но в науке так не делают: latest сегодня и через год — разные образы, а нам нужна воспроизводимость.

Теперь запустим контейнер:

# запустить контейнер и выполнить в нём одну команду
docker run python:3.12-slim python -c "print('hello from container')"

# интерактивный запуск: -i — пробросить stdin, -t — выделить терминал
# получаем REPL питона внутри контейнера
docker run -it python:3.12-slim python

# а так можно попасть в шелл контейнера и осмотреться
docker run -it python:3.12-slim bash

# --rm — удалить контейнер сразу после завершения (не копить мусор)
docker run --rm -it python:3.12-slim bash

Внутри контейнера ты в изолированном мире: ls / покажет чужую файловую систему, pip install поставит пакет внутри контейнера, и после его удаления всё исчезнет. Это фича, а не баг. Контейнеры эфемерны, всё ценное должно жить либо в образе, либо в примонтированных томах (о них ниже).

Управление контейнерами:

docker ps               # запущенные контейнеры
docker ps -a            # все, включая остановленные
docker stop <id|имя>    # мягко остановить контейнер
docker rm <id|имя>      # удалить остановленный контейнер
docker rmi <образ>      # удалить образ
docker logs <id|имя>    # посмотреть, что контейнер писал в stdout/stderr

Вместо полного идентификатора можно писать первые несколько символов или имя, которое Docker выдал контейнеру (или задать своё через --name).

Проброс портов и томов

Контейнер изолирован, в том числе по сети и по файлам. Чтобы он был полезен, изоляцию прокалывают в нужных местах двумя флагами.

Порты, -p хост:контейнер. Сервис слушает порт внутри контейнера, и снаружи его не видно, пока ты не пробросишь порт на хост.

Тома, -v путь_на_хосте:путь_в_контейнере. Каталог хоста монтируется внутрь контейнера: файлы видны с обеих сторон, а результаты переживают удаление контейнера.

Классический пример для физика — Jupyter в контейнере, без единого pip install на своей машине:

# jupyter/scipy-notebook — готовый образ с numpy, scipy, pandas, matplotlib
# -p 8888:8888          порт 8888 хоста -> порт 8888 контейнера
# -v ...:/home/jovyan/work   текущий каталог -> каталог work внутри контейнера
# тег фиксируем ради воспроизводимости
docker run --rm \
    -p 8888:8888 \
    -v "$(pwd)":/home/jovyan/work \
    jupyter/scipy-notebook:2024-05-27

Открываешь в браузере http://localhost:8888 (ссылку с токеном контейнер напечатает в лог) и работаешь в блокнотах, которые физически лежат в твоём текущем каталоге. Удалишь контейнер — блокноты останутся, окружение исчезнет без следа.

Dockerfile: свой образ для научного проекта

Чужие образы — хорошо, но твой расчётный код требует своего набора зависимостей. Рецепт сборки образа описывается в файле Dockerfile. Пусть у нас есть проект моделирования динамики пучка:

beam-simulation/
├── Dockerfile
├── requirements.txt      # numpy, scipy, matplotlib с версиями
├── simulate.py           # основной расчёт
└── beamlib/              # свои модули

Содержимое requirements.txt:

numpy==2.1.3
scipy==1.14.1
matplotlib==3.9.2

А вот Dockerfile:

# Базовый образ: официальный Python, slim-вариант без лишних пакетов.
# Всегда фиксируй версию — это фундамент воспроизводимости.
FROM python:3.12-slim

# Рабочий каталог внутри образа; все следующие команды выполняются в нём.
# Если каталога нет, он будет создан.
WORKDIR /app

# Сначала копируем ТОЛЬКО файл с зависимостями...
COPY requirements.txt .

# ...и устанавливаем их. --no-cache-dir не хранит кеш pip в образе,
# образ получается меньше.
RUN pip install --no-cache-dir -r requirements.txt

# Только теперь копируем весь остальной код проекта.
COPY . .

# Команда по умолчанию при запуске контейнера.
# Форма со скобками (exec form) запускает процесс напрямую, без оболочки.
CMD ["python", "simulate.py"]

Разберём инструкции:

  • FROM — от какого образа наследуемся. Всё, что есть в python:3.12-slim (Debian, Python, pip), достаётся нам бесплатно.
  • WORKDIR /app — задаёт текущий каталог для последующих COPY, RUN, CMD.
  • COPY <откуда> <куда> — копирует файлы из каталога проекта (контекста сборки) внутрь образа.
  • RUN — выполняет команду во время сборки и запекает результат в образ. Сюда же ставят системные пакеты: RUN apt-get update && apt-get install -y gfortran.
  • CMD — что запускать при старте контейнера. Выполняется не при сборке, а при docker run, и легко переопределяется: docker run мой-образ bash.

Слои и кеширование: почему requirements.txt копируют отдельно

Каждая инструкция Dockerfile создаёт слой — снимок изменений файловой системы. Образ — стопка слоёв, и Docker кеширует их: если инструкция и её входные файлы не изменились, слой берётся из кеша, а не пересобирается. Но как только один слой изменился, все последующие пересобираются заново.

Теперь смотри на порядок в нашем Dockerfile. Код (simulate.py) ты правишь по двадцать раз на дню, а requirements.txt — раз в месяц. Если бы мы писали COPY . . до установки зависимостей, любая правка кода инвалидировала бы слой копирования, и Docker заново гонял бы pip install со скачиванием numpy и scipy. Пять минут ожидания после каждой правки одной строчки. А в нашем порядке слой с зависимостями зависит только от requirements.txt. Правишь код — пересобирается лишь копеечный COPY . ., сборка занимает секунды. Правило простое: редко меняющееся — выше, часто меняющееся — ниже.

Ещё одна полезная деталь — файл .dockerignore (аналог .gitignore): перечисли в нём .git, __pycache__, данные и прочее, что не должно попадать в образ.

Сборка и запуск

# Собрать образ из Dockerfile в текущем каталоге (точка — контекст сборки).
# -t задаёт имя и тег.
docker build -t beam-simulation:0.1 .

# Тег можно навесить и потом (это просто ярлык на тот же образ)
docker tag beam-simulation:0.1 beam-simulation:latest

# Запуск: результаты пишем в примонтированный каталог,
# иначе они умрут вместе с контейнером
docker run --rm -v "$(pwd)/results":/app/results beam-simulation:0.1

# Переопределить CMD: запустить другой скрипт из того же образа
docker run --rm beam-simulation:0.1 python -m beamlib.diagnostics

Теперь весь расчёт — одна команда, одинаковая на любой машине с Docker.

Реестры: Docker Hub и ghcr.io

Образ собран, осталось отдать его коллеге. Можно выгрузить в файл (docker save и docker load), но стандартный путь лежит через реестр (registry) — git-хостинг для образов. По умолчанию используется публичный Docker Hub, оттуда мы качали python:3.12-slim. Второй популярный вариант, GitHub Container Registry (ghcr.io), удобен тем, что образы живут рядом с кодом проекта на GitHub и собираются автоматически через GitHub Actions.

Публикация выглядит так: имя образа должно включать твой аккаунт в реестре, дальше docker push:

# тегируем образ под свой аккаунт на Docker Hub
docker tag beam-simulation:0.1 fuodorov/beam-simulation:0.1

docker login                            # авторизация (однократно)
docker push fuodorov/beam-simulation:0.1

# коллега на любой машине делает:
docker pull fuodorov/beam-simulation:0.1

# для ghcr.io всё то же, только префикс реестра в имени:
docker tag beam-simulation:0.1 ghcr.io/fuodorov/beam-simulation:0.1
docker push ghcr.io/fuodorov/beam-simulation:0.1

Docker Compose: когда контейнеров больше одного

Реальная система редко состоит из одного контейнера. Типичный сценарий: приложение, которое пишет результаты измерений в базу данных PostgreSQL. Запускать оба контейнера руками, настраивать между ними сеть, помнить порядок запуска и десяток флагов — тоскливо. Docker Compose описывает всю связку декларативно, в одном файле compose.yaml:

services:
  app:
    build: .                    # собрать образ из Dockerfile в текущем каталоге
    volumes:
      - ./results:/app/results  # результаты — на хост
    environment:
      DB_HOST: db               # имя сервиса работает как сетевое имя хоста
      DB_USER: physicist
      DB_PASSWORD: secret
    depends_on:
      - db                      # сначала стартует база, потом приложение

  db:
    image: postgres:16          # готовый образ с Docker Hub
    environment:
      POSTGRES_USER: physicist
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: measurements
    volumes:
      - pgdata:/var/lib/postgresql/data   # именованный том: данные переживут контейнер

volumes:
  pgdata:

Compose автоматически создаёт общую сеть, в которой контейнеры видят друг друга по именам сервисов: приложение подключается к базе просто по адресу db:5432, никаких IP. Управление — две команды:

docker compose up -d      # собрать и запустить всё; -d — в фоне
docker compose logs -f    # смотреть логи всех сервисов
docker compose down       # остановить и удалить контейнеры (тома останутся)

Один файл в репозитории — и любой член группы поднимает всю инфраструктуру проекта одной командой.

Контейнеры в науке

Контейнер — готовый ответ на вопрос рецензента «а как воспроизвести твои результаты?». Всё чаще к статье прикладывают не только код, но и образ (или хотя бы Dockerfile в репозитории): docker run — и читатель получает те же графики из тех же данных, с точностью до версий всех библиотек. Есть нюанс с кластерами. На суперкомпьютерах Docker обычно запрещён, потому что его демон работает с правами root. Там используют Apptainer (бывший Singularity) — контейнерную систему, спроектированную для HPC: она работает без root-прав, дружит с MPI и GPU и умеет напрямую конвертировать Docker-образы. Так что образ, собранный для ноутбука, почти без изменений поедет и на кластер.
