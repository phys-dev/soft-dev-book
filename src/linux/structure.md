# Внутреннее устройство Linux

Система установлена и работает. Дальше стоит понять, что происходит внутри неё, — иначе первый же зависший расчёт или необъяснимо медленный ввод-вывод превратится в гадание.

## Почему важно изучать внутреннее устройство Linux

Расчёт, который ты запускаешь на кластере института, почти наверняка считается под Linux: на этой системе работают все пятьсот машин из списка Top500 и подавляющее большинство облачных серверов. Android тоже собран на её ядре, как и прошивки встроенных устройств. Иными словами, знание Linux — не выбор в пользу одной операционной системы из нескольких, а условие работы с научной вычислительной техникой вообще.

Но пользоваться системой и понимать, как она устроена, — разные вещи. Понимание внутренних механизмов нужно ровно в четырёх ситуациях, и все они рано или поздно наступают. Когда расчёт зависает или потребляет всю память, нужно уметь поставить диагноз, а не перезапускать наугад. Когда программа работает медленнее ожидаемого, нужно знать, куда смотреть. Когда пишешь код, полезно представлять, во что обходится системный вызов. И наконец, вся современная облачная инфраструктура построена на механизмах ядра Linux, так что понимать её без них не выйдет.

Последнее стоит сформулировать отдельно, потому что вокруг облаков много тумана: **облако — это просто чужие компьютеры в другом месте**. Те же процессы, та же память, та же сеть — только в удалённом дата-центре и с чужим счётом за электричество.

## 1. Зачем изучать Linux?

### Практическая ценность глубоких знаний

#### Быстрая диагностика проблем
```bash
# Вместо случайного тыкания
strace -p <pid>                    # что делает процесс?
perf record -g <command>          # где тратится время?
cat /proc/<pid>/status            # в каком состоянии?
```

**Пример из практики**: Сервис периодически «зависал». 
Анализ показал, что процесс переходил в состояние `D` (Uninterruptible sleep) при работе с NFS. 
Решение: настройка таймаутов и retry-логики.

#### Эффективное программирование
Знание стоимости операций:
- Системный вызов: ~1000 циклов CPU
- Context switch: ~1000-10000 циклов
- Page fault: ~10-100 микросекунд

**Оптимизация**: Сведение системных вызовов к минимуму, использование буферизации.

#### Облачные технологии
Контейнеры, оркестрация, serverless — все построено на механизмах Linux:
- **Docker** → cgroups + namespaces
- **Kubernetes** → управление процессами в масштабе
- **AWS Lambda** → изоляция и быстрый запуск

## 2. Процессы

### Детальное понимание процессов

#### Что такое процесс на самом деле?

Привычное определение «процесс — это запущенная программа» верно, но бесполезно: из него не следует ничего, что помогло бы разобраться с зависшим расчётом. Полезнее считать процесс **учётной единицей**, на которую ядро записывает всё, чем программа владеет и что о ней знает.

Владеет процесс четырьмя вещами: собственным виртуальным адресным пространством, набором открытых файловых дескрипторов, учётными данными и привилегиями (от чьего имени он работает) и маской сигналов вместе с их обработчиками. Именно этот набор ядро освобождает, когда процесс завершается, — и именно из-за него забытый открытый файл живёт ровно столько, сколько живёт процесс.

Знает о нём ядро тоже вполне определённые вещи: идентификаторы самого процесса и его родителя (PID и PPID), от какого пользователя и группы он запущен (UID и GID), с каким приоритетом его планировать, в каком состоянии он сейчас находится и сколько ресурсов уже израсходовал. Всё это лежит в файловой системе `/proc` и доступно для чтения — этим мы и воспользуемся ниже.

#### Структура процесса в ядре

```c
// Упрощенная task_struct (include/linux/sched.h)
struct task_struct {
    volatile long state;                    // состояние процесса
    void *stack;                           // указатель на стек
    struct mm_struct *mm;                  // память процесса
    struct files_struct *files;            // открытые файлы
    struct signal_struct *signal;          // сигналы
    // ... сотни полей
};
```

**Практическое использование**:
```bash
# Анализ конкретного процесса
ls -la /proc/1234/
cat /proc/1234/maps    # память процесса
cat /proc/1234/status  # состояние и лимиты
ls /proc/1234/fd/      # открытые файлы
```

### Создание процессов: fork() и exec()

#### Механизм Copy-on-Write (CoW)

Системный вызов `fork()` создаёт копию текущего процесса, и в наивной реализации он буквально копировал всю память родителя. Для расчёта, занявшего десять гигабайт, это означало десять гигабайт копирования — притом что сразу после `fork()` дочерний процесс обычно вызывает `exec()` и вся скопированная память немедленно выбрасывается.

Отсюда приём **copy-on-write**, копирования при записи. При `fork()` память не копируется вовсе: страницы просто помечаются как доступные только для чтения, и оба процесса читают одни и те же физические страницы. Настоящая копия делается лениво — в тот момент, когда один из процессов пытается в страницу записать, и только для этой страницы. В типичном случае «породить процесс и сразу запустить в нём другую программу» копировать не приходится почти ничего.

```c
pid_t pid = fork();
if (pid == 0) {
    // Дочерний процесс
    // Страницы памяти разделяются до первой записи
    execve("/bin/ls", args, env);
} else {
    // Родительский процесс
    waitpid(pid, &status, 0);
}
```

### Потоки (Threads) vs Процессы

#### Архитектурные различия

| Аспект | Процесс | Поток |
|--------|---------|-------|
| Память | Изолированная | Разделяемая |
| Файлы | Отдельные таблицы | Общая таблица |
| Стоимость создания | Высокая | Низкая |
| Изоляция | Полная | Минимальная |

#### Практические сценарии использования

Выбор между ними определяется тем, что для задачи важнее — изоляция или общая память.

Процессы берут, когда падение одной части работы не должно уронить остальные: у процессов раздельная память, поэтому обрушившийся обработчик уносит с собой только себя. По той же причине процессы нужны, если части программы должны работать от разных пользователей и с разными правами. И наконец, процессы — единственный вариант, если расчёт предстоит развести по нескольким машинам: потоки за пределы одной машины не выходят.

Потоки берут, когда частям работы нужно общее состояние: разделяемый кеш, пул соединений, общий массив с данными. Обмен между потоками не требует ни сериализации, ни копирования, задержка на порядки меньше, а общий кеш процессора работает на всех сразу. Плата за это — необходимость самому следить за одновременным доступом к общим данным, и в Python к ней добавляется глобальная блокировка интерпретатора, о которой речь пойдёт в главе про многопоточность.

### Межпроцессное взаимодействие (IPC)

#### Сигналы — асинхронные уведомления

```c
// Отправка сигнала
kill(pid, SIGTERM);

// Обработка сигнала
void handler(int sig) {
    // Асинхронно! Осторожно с shared state
}
signal(SIGTERM, handler);
```

**Важно**: Большинство функций не являются signal-safe! Используй только async-signal-safe функции в обработчиках.

#### Pipes — однонаправленная коммуникация

```bash
# Неименованные каналы
ls -la | grep ".txt" | wc -l

# Именованные каналы (FIFO)
mkfifo mypipe
echo "data" > mypipe &
cat mypipe
```

**Особенности**:
- Буферизация на уровне ядра
- Blocking I/O по умолчанию
- Размер буфера можно настраивать

#### Разделяемая память — максимальная производительность

```c
// Создание shared memory
int shm_id = shmget(key, size, IPC_CREAT | 0666);
void *ptr = shmat(shm_id, NULL, 0);

// Использование
memcpy(ptr, data, data_size);
```

Разделяемая память — самый быстрый способ обмена, потому что обмена как такового не происходит: оба процесса работают с одними и теми же физическими страницами, данные никуда не копируются, задержка сводится к обычному обращению в память. Для передачи больших массивов, например кадров с детектора, альтернативы практически нет.

Расплата в том, что ядро больше ничем не помогает. Канал сам упорядочивает данные, а разделяемая память не гарантирует ничего: если один процесс пишет, пока другой читает, получится мешанина. Синхронизацию — семафоры, блокировки, барьеры — приходится строить самому, и состояние гонки здесь самая обычная ошибка.

#### Семафоры — координация доступа

```c
// Бинарный семафор (мьютекс)
sem_wait(&mutex);
// Критическая секция
sem_post(&mutex);
```

**Типы семафоров**:
- **Binary** (0 или 1) — для взаимного исключения
- **Counting** — для ограничения ресурсов

### Состояния процессов: полный цикл жизни

#### Детали каждого состояния

Буква состояния в выводе `ps` говорит о процессе больше, чем кажется, поэтому разберём основные.

**R** (running / runnable) означает, что процесс либо выполняется прямо сейчас, либо стоит в очереди планировщика и готов выполняться. Ограничивает его только доступность процессорного времени. Если расчёт долго держится в `R` — он честно считает.

**S** (interruptible sleep) — процесс чего-то ждёт: завершения ввода-вывода, семафора, сигнала. Такое ожидание прерывается сигналом, то есть процесс в этом состоянии нормально завершается по `kill`. Для программ, которые больше ждут, чем считают, `S` — обычное рабочее состояние, и пугаться его не нужно.

**D** (uninterruptible sleep) — то же ожидание, но аппаратного ввода-вывода: диска или сети. Ключевое отличие в том, что оно **не прерывается сигналом, включая `kill -9`**. Именно с этим состоянием сталкиваются, когда процесс «повис намертво» и не убивается ничем: чаще всего под ним отвалившийся сетевой диск. Лечится это не сигналами, а разбирательством с самим устройством.

**T** (stopped) — процесс приостановлен сигналом `SIGSTOP` или `SIGTSTP` и продолжится по `SIGCONT`. Так работает нажатие Ctrl+Z в оболочке, и так же останавливают процесс отладчики.

**Z** (zombie) — процесс уже завершился, но родитель не забрал его код возврата. Ресурсы освобождены, осталась одна запись в таблице процессов, чтобы было откуда взять статус. Убить зомби нельзя, он и так мёртв; исчезнет он, когда родитель вызовет `wait`, а если родитель этого не делает по ошибке, то после его завершения — осиротевших зомби прибирает процесс `init`.

#### Практический мониторинг

```bash
# Понимание состояния процессов
ps aux | awk '{print $8}' | sort | uniq -c

# Поиск проблемных процессов
# Процессы в D состоянии
ps aux | awk '$8=="D" {print $0}'

# Zombie процессы
ps aux | awk '$8=="Z" {print $0}'
```

## 3. Планировщик (Scheduler)

### Эволюция планировщиков Linux

#### O(N) планировщик (до 2.4)
```c
// Псевдокод старого планировщика
for (each task in system) {
    calculate_goodness(task);
    if (goodness > max_goodness) {
        next_task = task;
        max_goodness = goodness;
    }
}
```
**Проблемы**: O(N) сложность, не масштабировался на многоядерные системы

#### O(1) планировщик (2.6.0–2.6.22)
- Две очереди: active и expired
- Bitmap для быстрого поиска
- Константное время планирования

**Достижения**: Хорошая масштабируемость, поддержка SMP

#### CFS (Completely Fair Scheduler) (2.6.23+)
```c
// Основан на красно-чёрных деревьях
struct rb_root_cached {
    struct rb_root rb_root;
    struct rb_node *rb_leftmost;
};
```

**Философия**: «Справедливое» распределение CPU времени

### Приоритеты и политики планирования

#### Real-Time политики

Для задач, где важна не общая пропускная способность, а гарантированное время реакции — управление установкой, сбор данных с жёстким тактом, — в ядре есть две политики реального времени.

**SCHED_FIFO** не выделяет процессу квант времени вовсе: получив процессор, процесс держит его, пока сам не отдаст или пока его не вытеснит процесс с более высоким приоритетом реального времени. Отсюда и опасность: зациклившаяся программа с этой политикой занимает ядро навсегда, и обычные процессы, включая твою оболочку, до него уже не доберутся.

**SCHED_RR** отличается тем, что квант всё-таки есть — по умолчанию 100 мс. Процессы одинакового приоритета сменяют друг друга по кругу, поэтому один зациклившийся не блокирует остальные. Эта политика заметно безопаснее, и начинать стоит с неё.

#### Normal политики

**SCHED_NORMAL/OTHER**:
- Динамические приоритеты (nice значения)
- Интерактивные процессы получают «бонус»
- Фоновые процессы слегка «штрафуются»

#### Nice значения и приоритеты

```bash
# Установка nice значения
nice -n 10 ./long_running_task    # низкий приоритет
nice -n -20 ./critical_task       # высокий приоритет

# Изменение running процесса
renice -n 5 -p 1234
```

**Диапазон**: -20 (высший) до +19 (низший)

### CFS: внутреннее устройство

#### Ключевые концепции

В основе планировщика лежат три величины, и понимание их снимает большую часть вопросов о том, почему процессы получают время именно так.

**Виртуальное время выполнения** (vruntime) — счётчик, который у каждого процесса растёт, пока тот занимает процессор, но растёт со скоростью, зависящей от приоритета: у процесса с высоким приоритетом медленнее, с низким быстрее. Планировщик всегда выбирает процесс с наименьшим vruntime, и в этом вся идея — «справедливым» считается тот, кто получил меньше всех. Значение `nice`, которым ты понижаешь или повышаешь приоритет, влияет именно на скорость накопления этого счётчика.

**Целевая задержка** (target latency) — срок, за который каждый готовый к выполнению процесс должен успеть получить процессор хотя бы раз. На настольных системах это 6 мс, на серверных — 24 мс: за отзывчивость интерфейса платят более частыми переключениями.

**Minimal Granularity**:
- Минимальное время выполнения перед вытеснением
- 0.75ms для предотвращения частого переключения

#### Реализация на красно-чёрных деревьях

```c
// Вставка процесса в дерево
struct sched_entity {
    struct rb_node run_node;
    u64 vruntime;
    // ...
};

// Быстрый поиск процесса с минимальным vruntime
struct task_struct *pick_next_task(struct rq *rq) {
    struct rb_node *left = rb_first_cached(&rq->tasks_timeline);
    return rb_entry(left, struct task_struct, se.run_node);
}
```

**Преимущества**: O(log N) для вставки/удаления

### Управление планировщиком на практике

#### CPU Affinity

```bash
# Привязка процесса к конкретным ядрам
taskset -c 0,1 ./application

# Просмотр текущей маски
taskset -p 1234

# Запуск с распределением по ядрам
numactl --cpunodebind=0,1 --membind=0,1 ./app
```

**Сценарии использования**:
- Изоляция критичных процессов
- Улучшение locality кеша
- NUMA-оптимизация

#### Настройка планировщика

```bash
# Просмотр параметров
cat /proc/sys/kernel/sched_min_granularity_ns
cat /proc/sys/kernel/sched_latency_ns

# Изменение параметров
echo 10000000 > /proc/sys/kernel/sched_latency_ns
```

#### Мониторинг планировщика

```bash
# Статистика переключений
cat /proc/1234/sched

# Очереди выполнения
cat /proc/sched_debug

# Профилирование
perf sched record ./application
perf sched latency
```

## 4. Прерывания

### Архитектура прерываний в x86/x64

#### Аппаратные прерывания (IRQs)

Прерывание — это способ устройства сказать процессору «я готово, займись мной». Источников в обычной машине немного: системные таймеры, сетевые карты, дисковые контроллеры и устройства на шине USB. В лаборатории к ним добавляется всё, что стоит в крейте: АЦП, счётчики, генераторы задержек.

**Механизм**:
```c
// Регистрация обработчика
request_irq(IRQ_NUMBER, handler, flags, name, dev);

// Обработчик прерывания
static irqreturn_t my_handler(int irq, void *dev_id) {
    // Быстрая обработка
    return IRQ_HANDLED;
}
```

#### Исключения процессора

**Типы**:
- **Faults** — исправимые (page fault)
- **Traps** — преднамеренные (breakpoints)
- **Aborts** — фатальные ошибки

### Обработка прерываний: Upper и Bottom Halves

#### Upper Half (Верхняя половина)

**Требования**:
- Максимально быстрое выполнение
- Минимальная работа
- Без блокирующих операций

```c
// Типичный upper half
irqreturn_t eth_interrupt(int irq, void *dev_id) {
    struct net_device *dev = dev_id;
    disable_irq_nosync(dev->irq);
    schedule_work(&dev->tx_work);
    return IRQ_HANDLED;
}
```

#### Bottom Half (Нижняя половина)

Обработчик прерывания обязан отработать мгновенно, поэтому всю содержательную работу он откладывает на потом — в так называемую нижнюю половину. Способов отложить три, и различаются они тем, насколько поздно и в каком контексте выполнится отложенное.

**SoftIRQ** — самый быстрый механизм, но он зашит в ядро статически: набор мягких прерываний фиксирован (сеть, блочные устройства), и добавить свой нельзя. **Tasklet** создаётся динамически и потому годится для драйверов, но один и тот же tasklet никогда не выполняется на двух ядрах одновременно — это упрощает жизнь, зато ограничивает масштабирование. **Очередь работ** (work queue) отличается принципиально: она выполняется в контексте обычного процесса ядра, а значит, ей разрешено засыпать и делать блокирующие вызовы. За эту свободу платят задержкой, поэтому очереди берут для действительно долгой работы.

```c
// Work queue пример
DECLARE_WORK(my_work, my_work_function);

void my_work_function(struct work_struct *work) {
    // Медленная обработка
    process_packets();
    enable_irq(dev->irq);
}
```

### Практическая работа с прерываниями

#### Мониторинг прерываний

```bash
# Статистика прерываний
cat /proc/interrupts

# Распределение прерываний по CPU
cat /proc/irq/*/smp_affinity

# Изменение привязки прерываний
echo 2 > /proc/irq/24/smp_affinity
```

#### Оптимизация обработки

Когда прерываний становится слишком много — а на быстрой сетевой карте или скоростном АЦП их десятки тысяч в секунду, — обработку настраивают. Приёмов четыре.

Прерывания **распределяют между ядрами процессора**: по умолчанию все они могут сыпаться на нулевое ядро, которое захлёбывается, пока остальные простаивают. Вместо устаревшего механизма прерываний по выделенной линии используют **MSI**, где устройство сообщает о событии записью в память, — это снимает ограничение на число линий и упрощает распределение. Для сетевых карт **подбирают длину очередей**: слишком короткая теряет пакеты на всплесках, слишком длинная раздувает задержку. И наконец, включают **объединение прерываний** (coalescing), когда устройству разрешают накопить несколько событий и сообщить о них разом: число прерываний падает в разы ценой небольшой задержки.

## 5. Системные вызовы

### Механизм системных вызовов

#### Переключение между пространствами

**Пользовательское пространство** → **Пространство ядра**:
```assembly
; x86-64 системный вызов
mov rax, 1      ; номер syscall (write)
mov rdi, 1      ; fd (stdout)
mov rsi, buffer ; буфер
mov rdx, count  ; размер
syscall         ; переход в ядро
```

За одной инструкцией `syscall` скрывается шесть шагов, и каждый из них стоит времени. Процессор сохраняет контекст пользовательского кода — регистры, указатель инструкций, — и переходит в режим ядра. Ядро проверяет переданные параметры, потому что доверять пользовательской программе нельзя: адрес буфера может указывать куда угодно. Затем выполняется собственно операция, результат записывается туда, где его ждёт программа, и контекст восстанавливается обратно.

Отсюда и берётся стоимость системного вызова: сама операция может быть тривиальной, но обрамление из сохранения, проверки и восстановления никуда не девается.

#### Таблица системных вызовов

```c
// Определение syscall (kernel/sys.c)
SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf,
                size_t, count)
{
    struct fd f = fdget_pos(fd);
    // ... обработка
    return ret;
}
```

**Важно**: Все параметры проверяются на валидность!

### Безопасность системных вызовов

#### Проверки доступа

```c
// Проверка указателей из userspace
if (copy_from_user(kernel_buf, user_buf, size))
    return -EFAULT;

// Проверка прав доступа
if (!file_permission(file, MAY_READ))
    return -EPERM;
```

#### Capabilities-based security

```c
// Вместо проверки UID == 0
if (!capable(CAP_SYS_ADMIN))
    return -EPERM;
```

### Производительность системных вызовов

#### Измерение стоимости

```c
#include <sys/time.h>

struct timeval start, end;
gettimeofday(&start, NULL);
// системный вызов
gettimeofday(&end, NULL);

long microseconds = (end.tv_sec - start.tv_sec) * 1000000 
                  + (end.tv_usec - start.tv_usec);
```

Порядки величин стоит запомнить, потому что они определяют, о чём вообще имеет смысл беспокоиться. Простой системный вызов вроде `getpid` обходится в 0.1–1 микросекунду. Вызовы с вводом-выводом — от микросекунды до миллисекунды, разброс зависит от того, попал ли запрос в кеш или пошёл на диск. Переключение контекста между процессами стоит 1–10 микросекунд.

Сравни это с обычным обращением в оперативную память, которое занимает около сотни наносекунд, и станет понятно, почему в тесном цикле системные вызовы недопустимы: один `write` на каждое число превратит расчёт в ожидание.

#### Оптимизация

Раз системный вызов стоит дорого, оптимизация сводится к тому, чтобы делать их реже. Работает это четырьмя способами.

Вызовы **объединяют**: вместо десяти `write` подряд делают один `writev`, который принимает сразу список буферов. Файл **отображают в память** через `mmap` и дальше работают с ним как с обычным массивом, без `read` и `write` вовсе — приём особенно уместен для больших файлов данных. Лишние вызовы просто **убирают**: типичный случай — проверять существование файла перед открытием, хотя открытие и так вернёт ошибку. А для нескольких самых частых вызовов вроде `gettimeofday` в Linux есть **vDSO** — кусок кода ядра, отображённый прямо в память процесса, так что переключаться в режим ядра не приходится совсем.

### Управление памятью на практике

#### Анализ памяти процесса

```bash
# Детальная информация о памяти
pmap -XX 1234

# Статистика памяти
cat /proc/1234/smaps

# Page faults
ps -o min_flt,maj_flt,cmd -p 1234
```

#### Типы page faults

Промахи по страницам бывают двух видов, и различаются они на три порядка по цене.

**Малый промах** (minor fault) случается, когда нужная страница уже есть в физической памяти, но пока не прописана в таблицах страниц процесса — например, она разделяется с другим процессом или только что выделена. Ядру достаточно обновить таблицы, и это быстро.

**Большой промах** (major fault) означает, что страницы в памяти нет и её нужно читать с диска. Здесь речь идёт о миллисекундах вместо микросекунд. Если `ps` или `top` показывают, что расчёт набирает большие промахи тысячами, значит, ему не хватает памяти и система ушла в подкачку — оптимизировать код в этот момент бессмысленно, надо разбираться с памятью.

### Проблемы с памятью и решения

#### Out of Memory (OOM)

**Механизм OOM killer**:
1. Ядро обнаруживает нехватку памяти
2. Вычисляет "badness score" для каждого процесса
3. Выбирает и завершает процесс с максимальным score

**Управление OOM**:
```bash
# Настройка политики OOM
echo -1000 > /proc/1234/oom_score_adj    # защитить процесс
echo 1000 > /proc/1234/oom_score_adj     # первым кандидат

# Ручной вызов OOM killer
echo f > /proc/sysrq-trigger
```

#### SWAP управление

```bash
# Мониторинг swap
swapon --show
free -h

# Настройка swappiness
echo 10 > /proc/sys/vm/swappiness    # меньше swap (сервер)
echo 60 > /proc/sys/vm/swappiness    # больше swap (десктоп)
```

#### NUMA оптимизация

```bash
# Информация о NUMA
numactl --hardware

# Запуск с учетом NUMA
numactl --membind=0 --cpunodebind=0 ./application

# Статистика NUMA
cat /proc/1234/numa_maps
```

## 7. Изоляция

### Эволюция изоляции в Linux

#### От chroot до контейнеров

Контейнеры кажутся изобретением последних лет, но идея старше почти всех, кто ими сегодня пользуется. Она развивалась постепенно, и каждый шаг добавлял к изоляции что-то одно:

- **1979** — `chroot` в UNIX: процессу подменяют корень файловой системы;
- **2000** — FreeBSD Jails: к файловой системе добавляется изоляция процессов и сети;
- **2001** — Linux-VServer, **2004** — Solaris Zones: те же идеи в других системах;
- **2008** — LXC: в ядре Linux появляются пространства имён и cgroups, то есть всё необходимое;
- **2013** — Docker: удобная упаковка поверх готовых механизмов ядра;
- **2014** — Kubernetes: управление контейнерами в масштабе кластера.

Обрати внимание, что технической революции в 2013 году не произошло: механизмы ядра были готовы за пять лет до Docker. Революция была в удобстве — появился простой способ описать образ файлом и передать его другому человеку. Это общий сюжет: технология выстреливает не тогда, когда становится возможной, а когда становится удобной.

### Cgroups: управление ресурсами

#### Иерархия cgroups v2

```
/sys/fs/cgroup/
├── system.slice/          # системные службы
│   ├── ssh.service
│   └── docker.service
├── user.slice/            # пользовательские процессы
│   ├── user-1000.slice
│   └── user-1001.slice
├── kubepods.slice/        # Kubernetes pods
│   ├── pod1/
│   └── pod2/
└── cgroup.controllers     # доступные контроллеры
```

#### Контроллеры ресурсов

**CPU**:
```bash
# Ограничение CPU
echo "200000 1000000" > /sys/fs/cgroup/mygroup/cpu.max
# 200ms из каждых 1000ms

# CPU shares
echo 512 > /sys/fs/cgroup/mygroup/cpu.weight
```

**Память**:
```bash
# Лимит памяти
echo 1G > /sys/fs/cgroup/mygroup/memory.max

# SWAP лимит
echo 2G > /sys/fs/cgroup/mygroup/memory.swap.max

# OOM политика
echo "oom_group" > /sys/fs/cgroup/mygroup/memory.oom.group
```

**I/O**:
```bash
# Ограничение дискового I/O
echo "8:0 rbps=1048576 wbps=1048576" > /sys/fs/cgroup/mygroup/io.max
```

### Namespaces: изоляция представлений

#### Типы namespaces

| Namespace | Изолирует | Команда |
|-----------|-----------|---------|
| PID | Process IDs | unshare --pid |
| Network | Network stack | unshare --net |
| Mount | Filesystem mounts | unshare --mount |
| UTS | Hostname, domain | unshare --uts |
| IPC | System V IPC | unshare --ipc |
| User | User/group IDs | unshare --user |
| Cgroup | Cgroup hierarchy | unshare --cgroup |
| Time | System time | unshare --time |

#### Практическое использование namespaces

**Создание изолированного окружения**:
```bash
# Создание namespace и запуск процесса
sudo unshare --fork --pid --mount-proc bash

# В новом namespace:
ps aux    # видит только свои процессы
mount     # видит только свои mount points
```

**Docker-подобный контейнер вручную**:
```bash
# Создание root filesystem
mkdir /mycontainer
debootstrap stable /mycontainer

# Запуск в изоляции
unshare --fork --pid --mount-proc --net --uts chroot /mycontainer /bin/bash

# В контейнере:
hostname mycontainer
ip link set lo up
```
