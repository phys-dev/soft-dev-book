# От скрипта к приложению

## Введение

Почти любой код в лаборатории рождается одинаково. Вечером перед семинаром ты пишешь `analysis.py` на пятьдесят строк: загрузить осциллограммы, вычесть базовую линию, найти пик, нарисовать график. Скрипт работает, график попадает в отчёт, все довольны.

Дальше события развиваются по знакомому сценарию:

- через полгода в скрипте 800 строк: добавились калибровка, три формата входных файлов и ветка `if experiment == "march":`;
- рядом лежат `analysis_new.py`, `analysis_final.py` и `analysis_final_v2_REAL.py`, и никто не помнит, чем они отличаются;
- пути к данным (`/home/vasya/data/2026-03-12/`) и параметры установки зашиты в код: перед каждым запуском ты правишь исходник;
- на другой машине скрипт не запускается: «а какая у тебя версия numpy?»;
- приходит новый студент, и ты полчаса объясняешь, какие строки закомментировать, чтобы «просто посчитать спектр».

Одноразовый скрипт — нормальный жанр, стыдиться его не нужно. Проблемы начинаются, когда одноразовый код незаметно становится многоразовым: им пользуется вся группа, на его результатах строятся статьи, а устроен он по-прежнему как черновик.

Разница между скриптом и приложением — не в количестве строк, а в свойствах:

- приложение ставится на чистую машину одной-двумя командами;
- его запускают, не открывая исходники в редакторе;
- оно внятно сообщает об ошибках и ведёт журнал работы;
- его можно менять, не боясь незаметно сломать физику, — есть тесты;
- в нём разберётся другой человек. Или ты сам через полгода — это тот же случай.

В главе про [жизненный цикл ПО](./life.md) мы смотрели на разработку с высоты птичьего полёта. Здесь спустимся на землю и пройдём путь целиком на сквозном примере: превратим скрипт обработки осциллограмм в пакет `beamtool`, которым сможет пользоваться вся группа.

## Структура проекта

Начнём с механики. Любой файл `.py` — это *модуль*, его можно импортировать. Каталог с файлом `__init__.py` — это *пакет*: набор модулей с общим именем. Как только код перестаёт помещаться в один файл, разложи его по модулям по смыслу: чтение данных отдельно, формулы отдельно, графики отдельно. Правило простое: один модуль — одна зона ответственности.

Типовая структура проекта выглядит так:

```text
beamtool/                  # корень git-репозитория
├── pyproject.toml         # метаданные проекта и зависимости
├── README.md              # что это, как поставить, как запустить
├── .gitignore
├── configs/
│   └── default.toml       # параметры обработки по умолчанию
├── src/
│   └── beamtool/          # сам пакет
│       ├── __init__.py
│       ├── io.py          # чтение и запись данных
│       ├── physics.py     # формулы и численные методы
│       ├── plotting.py    # вся работа с matplotlib
│       └── cli.py         # интерфейс командной строки
└── tests/
    ├── test_io.py
    └── test_physics.py
```

Это так называемый *src-layout*: пакет спрятан в каталоге `src/`. Есть и плоский вариант (flat layout), где `beamtool/` лежит прямо в корне репозитория, — для маленьких проектов он тоже годится. Преимущество src-layout в том, что пакет нельзя случайно импортировать прямо из рабочего каталога, минуя установку: тесты проверяют ровно то, что получит пользователь.

Отдельный вопрос — где живут данные. Сырые данные экспериментов в репозиторий не кладут: git плохо переносит гигабайты бинарников, а история изменений для них бессмысленна. Данные лежат на сервере или дисках группы, в репозитории — путь к ним в конфиге и маленькие файлы-образцы для тестов (`tests/data/`). Каталоги `data/`, `.venv/`, `__pycache__/` и файлы `*.log` добавь в `.gitignore` сразу, не дожидаясь первого случайного коммита на два гигабайта.

## Виртуальные окружения и зависимости

Системный Python — общая кухня: в ней готовят все программы машины, и обновление библиотеки для одного проекта ломает другой. Поэтому у каждого проекта должно быть своё *виртуальное окружение* — изолированный набор пакетов:

```bash
cd beamtool
python -m venv .venv
source .venv/bin/activate    # в Windows: .venv\Scripts\activate
pip install numpy matplotlib
```

Окружение — расходный материал: сломалось или запуталось — удаляешь каталог `.venv` и создаёшь заново за минуту. Но это работает, только если список зависимостей хранится в репозитории, а не в твоей голове. Записать его можно двумя способами.

Классический — файл `requirements.txt`, простой список для `pip install -r requirements.txt`:

```text
numpy==2.1.3
matplotlib==3.9.2
```

Современный — секция `dependencies` в `pyproject.toml`, едином файле с метаданными проекта (мы разберём его в разделе про упаковку). Для нового проекта выбирай `pyproject.toml`; `requirements.txt` останется тебе как точный слепок окружения.

Обрати внимание на закрепление версий. Здесь есть два режима. В библиотеке, которую ставят другие, версии ограничивают мягко (`numpy>=2.0`), чтобы не конфликтовать с чужими зависимостями. В приложении для обработки данных важнее воспроизводимость: команда `pip freeze > requirements.txt` фиксирует всё окружение до последней цифры, и через год ты сможешь пересоздать его и повторить расчёт для статьи. Обновление той же scipy иногда меняет численные результаты в последних знаках — для науки это не мелочь, а повод зафиксировать версии.

Вместо связки venv + pip можно взять современный менеджер проектов: [poetry](https://python-poetry.org/) или [uv](https://docs.astral.sh/uv/). Они делают то же самое — окружение, зависимости, lock-файл с точными версиями, — но одной командой и с автоматическим разрешением конфликтов; uv к тому же написан на Rust и работает на порядок быстрее pip. Начни с venv и pip, чтобы понимать механику, а на менеджеры перейдёшь, когда почувствуешь, какую рутину они убирают.

## Точки входа

Модуль должен переживать импорт без побочных эффектов: при `import beamtool.cli` ничего не должно считаться, рисоваться и писаться на диск. Поэтому исполняемый код закрывается стандартной конструкцией:

```python
if __name__ == "__main__":
    main()
```

Переменная `__name__` равна `"__main__"` только тогда, когда файл запущен как программа, а не импортирован. Это уже было в наших требованиях к коду; теперь сделаем следующий шаг — нормальный интерфейс командной строки, чтобы параметры передавались аргументами, а не правкой исходника. В стандартной библиотеке для этого есть модуль `argparse`:

```python
"""Интерфейс командной строки beamtool."""

import argparse
from pathlib import Path

import numpy as np


def parse_args() -> argparse.Namespace:
    """Разбирает аргументы командной строки."""
    parser = argparse.ArgumentParser(
        prog="beamtool",
        description="Обработка осциллограмм: базовая линия, пик, заряд.",
    )
    parser.add_argument(
        "--input", type=Path, required=True,
        help="входной CSV-файл с колонками time, voltage",
    )
    parser.add_argument(
        "--output", type=Path, required=True,
        help="файл для записи результатов",
    )
    parser.add_argument(
        "--plot", action="store_true",
        help="показать график после обработки",
    )
    return parser.parse_args()


def main() -> None:
    """Точка входа приложения."""
    args = parse_args()
    time, voltage = np.loadtxt(args.input, delimiter=",", unpack=True)

    # Базовая линия — среднее по первым точкам до прихода сигнала.
    baseline = voltage[:100].mean()
    signal = voltage - baseline
    peak_index = int(np.argmax(signal))
    area = float(np.trapezoid(signal, time))

    np.savetxt(
        args.output,
        [[time[peak_index], signal[peak_index], area]],
        delimiter=",",
        header="peak_time,peak_voltage,area",
    )

    if args.plot:
        # Ленивый импорт: без --plot matplotlib даже не загружается,
        # и скрипт работает на сервере без дисплея.
        from beamtool.plotting import show_signal
        show_signal(time, signal, peak_index)


if __name__ == "__main__":
    main()
```

Запуск теперь выглядит так: `python -m beamtool.cli --input shot_042.csv --output results.csv --plot`. Бесплатным приложением идёт `--help`: argparse сам генерирует справку, проверяет обязательные аргументы и приводит типы. Пользователю больше не нужно открывать код — а значит, он не сможет его случайно сломать.

Для разросшихся интерфейсов с подкомандами (как `git commit`, `git push`) есть сторонние библиотеки [click](https://click.palletsprojects.com/) и [typer](https://typer.tiangolo.com/) — они делают то же самое декораторами и аннотациями типов. Но argparse из стандартной библиотеки хватает надолго, и он всегда под рукой.

## Конфигурация

Магические числа и пути в коде — главный источник хаоса в лабораторных скриптах. Порог дискриминатора, частота дискретизации АЦП, путь к данным — всё это меняется от запуска к запуску, и если оно зашито в исходник, каждый запуск требует правки кода. История в git превращается в мусор из «поменял порог обратно», а воспроизводимость умирает: никто не помнит, с какими параметрами был получен график в статье.

Правило разделения: код отвечает на вопрос «как считать», конфигурация — «что и с какими параметрами». Параметры выносятся в конфиг-файл; удобный формат — TOML, который читается стандартной библиотекой (Python 3.11+):

```toml
# configs/default.toml

[detector]
sampling_rate_hz = 2.5e9   # частота дискретизации АЦП
impedance_ohm = 50.0

[analysis]
baseline_points = 100      # точек на оценку базовой линии
peak_threshold_v = 0.05    # порог отбора событий
```

```python
import tomllib

with open("configs/default.toml", "rb") as f:
    config = tomllib.load(f)

threshold = config["analysis"]["peak_threshold_v"]
```

YAML — то же самое по духу (нужен пакет `pyyaml`); выбери один формат и держись его. Конфиг лежит в репозитории, и его версия в git — это история твоих параметров обработки: видно, кто, когда и какой порог поменял.

Для того, что зависит от конкретной машины или должно оставаться секретным, используют переменные окружения:

```python
import os

data_dir = os.environ.get("BEAMTOOL_DATA_DIR", "/data/beam")
```

Пароли и токены (например, доступ к базе данных группы — о ней в следующей главе) не попадают ни в код, ни в git никогда: только переменные окружения или локальный файл `.env`, добавленный в `.gitignore`. Итоговый приоритет источников обычно такой: значения по умолчанию → конфиг-файл → переменные окружения → аргументы командной строки; каждый следующий уровень перекрывает предыдущий.

## Логирование вместо print

`print` хорош для отладки на две минуты. Дальше начинаются проблемы: отладочный вывод нельзя отключить, не вырезая его из кода; у сообщений нет времени и важности; всё уходит в консоль и исчезает вместе с ней. А когда ночная обработка падает на 3742-м файле из 5000, тебе нужен журнал: что происходило, с какими файлами и когда.

Всё это умеет стандартный модуль `logging`. У сообщений есть уровни — `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` — и глобальный порог, который решает, что показывать. Настройка с выводом одновременно в консоль и в файл:

```python
import logging

logger = logging.getLogger(__name__)


def setup_logging(logfile: str = "beamtool.log") -> None:
    """Включает вывод логов в консоль и в файл одновременно."""
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s %(levelname)-8s %(name)s: %(message)s",
        handlers=[
            logging.StreamHandler(),
            logging.FileHandler(logfile, encoding="utf-8"),
        ],
    )
```

Использование в коде:

```python
logger.info("Загружен файл %s: %d точек", path, n_points)
logger.warning("Пик ниже порога %.3f В, файл пропущен", threshold)
logger.error("Не удалось разобрать файл %s", path, exc_info=True)
```

Три детали. `getLogger(__name__)` в каждом модуле даёт по именованному логгеру — в журнале видно, какой модуль пишет. Флаг `--verbose` в CLI может опускать порог до `DEBUG`, не трогая код: отладочные сообщения пишутся всегда, а показываются по требованию. А `exc_info=True` добавляет к сообщению полный traceback — утром ты увидишь не только «файл пропущен», но и почему.

## Обработка ошибок

Главный принцип научного кода — *fail fast*: обнаружил некорректные данные — падай сразу и громко. Альтернатива страшнее падения: тихий NaN проползает через все стадии обработки и превращается в правдоподобный, но неверный график. Упавшую программу чинят; красивую кривую с ошибкой отправляют в статью.

Python сообщает об ошибках исключениями, и ты можешь определять свои — это обычные классы, наследники `Exception`:

```python
import numpy as np


class BeamtoolError(Exception):
    """Базовый класс ошибок beamtool."""


class InvalidSignalError(BeamtoolError):
    """Сигнал не пригоден для обработки."""


def find_peak(signal: np.ndarray) -> int:
    """Возвращает индекс максимума сигнала."""
    if signal.size == 0:
        raise InvalidSignalError("пустой сигнал")
    if not np.all(np.isfinite(signal)):
        raise InvalidSignalError("в сигнале есть NaN или inf")
    return int(np.argmax(signal))
```

Зачем свои классы? Они отделяют *ожидаемые* ошибки от багов. На верхнем уровне, в `main()`, ты ловишь `except BeamtoolError` — кривой файл в пачке из тысячи это штатная ситуация: записать в журнал и перейти к следующему. А `KeyError` или `TypeError` — это баг в твоём коде; он должен пролететь наружу с полным traceback, чтобы его починили, а не спрятали.

Худшее, что можно сделать с исключением, — проглотить его:

```python
# Так делать нельзя: ошибка исчезает бесследно,
# а в результатах молча появляется дыра.
try:
    result = process(path)
except Exception:
    pass
```

Правило: лови исключение только там, где знаешь, что с ним делать. Во всех остальных местах — не лови вовсе.

## Тесты

Научному коду тесты нужны даже больше, чем сайтам и мессенджерам. Главный риск здесь — не «программа упала», а «программа выдала правдоподобное, но неверное число». Особенно коварны рефакторинги формул: ты «слегка упростил» выражение, потерял двойку в знаменателе — и все результаты уехали, а код по-прежнему работает без единой ошибки. Тесты фиксируют поведение: любое изменение, сдвинувшее численный результат, всплывает немедленно. Это и есть защита от регрессий.

Стандарт де-факто — [pytest](https://docs.pytest.org/): тесты лежат в `tests/test_*.py`, называются `test_*` и состоят из обычных `assert`. Возьмём функцию из `beamtool`:

```python
# src/beamtool/physics.py

ELECTRON_REST_ENERGY_MEV = 0.511


def lorentz_gamma(kinetic_energy_mev: float) -> float:
    """Возвращает лоренц-фактор по кинетической энергии электрона."""
    if kinetic_energy_mev < 0:
        raise ValueError("кинетическая энергия отрицательна")
    return 1.0 + kinetic_energy_mev / ELECTRON_REST_ENERGY_MEV
```

И тесты к ней:

```python
# tests/test_physics.py

import pytest

from beamtool.physics import lorentz_gamma


def test_gamma_at_rest():
    # Покоящийся электрон: гамма-фактор равен единице.
    assert lorentz_gamma(0.0) == pytest.approx(1.0)


def test_gamma_one_mev():
    assert lorentz_gamma(1.0) == pytest.approx(2.9569, abs=1e-4)


def test_negative_energy_rejected():
    with pytest.raises(ValueError):
        lorentz_gamma(-1.0)
```

Команда `pytest` в корне проекта сама найдёт и прогонит все тесты. Обрати внимание на `pytest.approx`: сравнивать float через `==` нельзя из-за ошибок округления, а `approx` сравнивает с допуском — абсолютным (`abs=`) или относительным (`rel=`).

Что тестировать в первую очередь: функции-формулы на входах с известным ответом (аналитические пределы, симметрии, законы сохранения), парсеры форматов данных на файлах-образцах из `tests/data/`, граничные случаи (пустой сигнал, один отсчёт, отрицательная энергия). Отличный приём для численных методов — прогнать решатель на упрощённой задаче, у которой есть аналитическое решение, и сравнить. Написал тест один раз — и каждый следующий рефакторинг проверяется бесплатно.

## Типизация

Аннотации типов ты уже видел во всех примерах выше:

```python
def rebin(spectrum: np.ndarray, factor: int = 2) -> np.ndarray:
    """Огрубляет спектр, суммируя соседние каналы."""
    n_bins = spectrum.size // factor * factor
    return spectrum[:n_bins].reshape(-1, factor).sum(axis=1)
```

Во время выполнения Python их не проверяет — это машиночитаемая документация. Но её понимают инструменты: редактор подсказывает атрибуты и ловит опечатки, а статический анализатор [mypy](https://mypy.readthedocs.io/) командой `mypy src/` находит несостыковки до запуска: сюда передали `str` вместо `Path`, там функция может вернуть `None`, а вызывающий код об этом не знает. Для расчёта, который идёт три часа, поймать такую ошибку за секунду до запуска — большая экономия жизни. Аннотируй хотя бы публичные функции пакета и добавь mypy в CI рядом с линтерами.

## Документация

Минимальный набор документации у тебя уже почти есть. Docstring у каждой публичной функции — что делает, что принимает, что возвращает и в каких единицах (перепутанные мэВ и МэВ не поймает ни один тайпчекер). README в корне репозитория отвечает на три вопроса: что это за проект, как его поставить, как запустить — с одним работающим примером команды; это первое, что увидит коллега, и часто единственное, что он прочитает. Когда проект вырастает, из docstring'ов и markdown-файлов собирают сайт документации — [mkdocs](https://www.mkdocs.org/) или [sphinx](https://www.sphinx-doc.org/); документация при этом живёт в том же репозитории и обновляется вместе с кодом, а не в отдельном вордовском файле на сетевом диске.

## Упаковка и распространение

Осталось собрать всё воедино. Центральный файл современного Python-проекта — `pyproject.toml`:

```toml
[project]
name = "beamtool"
version = "0.1.0"
description = "Обработка осциллограмм с датчиков пучка"
requires-python = ">=3.11"
dependencies = [
    "numpy>=2.0",
    "matplotlib>=3.9",
]

[project.scripts]
beamtool = "beamtool.cli:main"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

Теперь проект можно установить в окружение в режиме разработки:

```bash
pip install -e .
```

Флаг `-e` (editable) ставит пакет «ссылкой» на рабочий каталог: правки в коде видны сразу, без переустановки. После установки заработают импорты `from beamtool.physics import ...` из любого места — в том числе из тестов. А секция `[project.scripts]` создаёт в окружении настоящую консольную команду: функция `main()` из `cli.py` теперь вызывается просто как `beamtool --input shot_042.csv --output results.csv`.

Распространение — по нарастающей. Коллегам из группы достаточно git-репозитория: `pip install git+https://github.com/mygroup/beamtool` ставит пакет прямо оттуда со всеми зависимостями. Команда `python -m build` собирает из проекта wheel-файл в `dist/` — его можно приложить к релизу на GitHub или передать на машину без интернета. Публикация на [PyPI](https://pypi.org/) через `twine upload` (или `uv publish`) — финальная ступень, когда инструментом хотят пользоваться незнакомые тебе люди; для внутренних инструментов группы она не обязательна.

## Когда приложение вырастает в систему

Всё, что описано выше, — про один инструмент, который делает одну вещь. Рано или поздно появляется задача, которую одним инструментом не закрыть: провести эксперимент целиком. Выставить токи магнитов, дождаться стабилизации, снять показания с десятка датчиков, посчитать результат, решить, куда двигаться дальше, повторить — и всё это сотни раз подряд, ночью, без человека у пульта.

Такую программу уже нельзя писать «плоско». Разберём, как устроена библиотека SCAUT, которая занимается оркестрацией экспериментов на линейном ускорителе инжектора ЦКП «СКИФ» — то есть согласованным управлением всеми компонентами установки, от магнитов до детекторов.

Ключевая идея — **разделение на слои**, где каждый слой знает только о соседнем:

```
Интерфейс эксперимента   что именно сканируем и в каких пределах
        │
Управление сканированием планировщик точек, обработчики событий, обработка аварий
        │
Абстракция оборудования  «мотор» и «датчик» — независимо от того, что за железо
        │
Коммуникация             EPICS, Tango, OPC UA — или расчётная модель вместо железа
        │
Данные                   сериализация, метаданные эксперимента, хранилище
        │
Анализ                   визуализация, статистика, постобработка
```

Разберём, что даёт каждая граница.

**Абстракция оборудования** — самая ценная из них. Верхние слои оперируют понятиями «мотор» (нечто, чему можно задать значение) и «датчик» (нечто, у чего можно спросить значение). Что стоит за мотором — источник питания квадруполя, шаговый двигатель экрана или регулятор фазы СВЧ — процедуре сканирования безразлично. Добавление нового прибора не требует правок в логике эксперимента: пишется новый адаптер, и всё.

**Слой коммуникации** отделяет протокол от смысла. Ускорительные комплексы управляются разными системами — EPICS, Tango, OPC UA, — и код эксперимента не должен об этом знать. Но интереснее другое: на место реального железа можно подставить **расчётную модель**. Тот же самый сценарий эксперимента, без единой правки, прогоняется сначала на модели пучка, а потом на установке. Ошибка в логике сканирования обнаруживается на модели, где она стоит ноль, а не в смену, где она стоит пучкового времени всей группы.

**Слой данных** отвечает за то, чтобы результат пережил эксперимент. Кроме собственно измерений сохраняются метаданные: когда, кем, при каких настройках, какой версией кода. Без этого через полгода из архива нельзя будет извлечь ничего, кроме массива чисел неизвестного происхождения.

Процедура сканирования при этом всегда проходит одни и те же шесть этапов:

1. **Инициализация** — проверить, что нужное оборудование на связи, выставить начальные параметры.
2. **Планирование** — построить последовательность точек в пространстве параметров.
3. **Выполнение** — на каждом шаге выставить параметры и снять данные.
4. **Обработка событий** — вызвать пользовательские функции анализа.
5. **Сериализация** — сохранить результаты и метаданные.
6. **Завершение** — освободить ресурсы, сформировать отчёт.

Первый и последний пункты выглядят формальностью ровно до первого ночного прогона, который упал на середине. Если инициализация не проверила связь с прибором, эксперимент честно отработает четыре часа и запишет нули. Если завершение не освободило ресурсы, следующий запуск не сможет подключиться к оборудованию, потому что предыдущий процесс всё ещё держит соединение.

Мораль этого раздела не в конкретной архитектуре, а в принципе, который за ней стоит: **границы проводят там, где ожидаются изменения**. Железо меняется — значит, нужен слой абстракции оборудования. Протоколы управления разные — значит, нужен слой коммуникации. Способ анализа данных меняется чаще всего — значит, анализ отделён от сбора и может переписываться, не трогая ничего остального. Слой, за которым ничего никогда не меняется, — лишний, и его не стоит вводить «на будущее».

## Чек-лист: скрипт стал приложением

Проверь свой проект по списку:

- [ ] Код разложен по модулям со смыслом: ввод-вывод, физика, графика, CLI.
- [ ] Проект ставится на чистую машину командами `git clone` и `pip install -e .`.
- [ ] Зависимости с версиями записаны в `pyproject.toml`, точный слепок окружения можно получить и восстановить.
- [ ] Запуск не требует открывать исходники: все параметры передаются через аргументы CLI и конфиг-файл.
- [ ] Пути, калибровки и пороги живут в конфиге, а не в коде; секретов в репозитории нет.
- [ ] Вместо `print` — `logging`: после ночного прогона остаётся журнал с временем и уровнями.
- [ ] Некорректные данные вызывают внятную ошибку сразу, а не тихий NaN в результатах.
- [ ] Ключевые формулы покрыты тестами; `pytest` проходит перед каждым коммитом.
- [ ] Публичные функции аннотированы типами и снабжены docstring; `mypy` молчит.
- [ ] README отвечает на вопросы «что это», «как поставить», «как запустить».
- [ ] Файл `analysis_final_v2_REAL.py` удалён: версии живут в git, а не в именах файлов.

Не пытайся сделать всё это в первый же вечер. Структура, окружение и git нужны сразу — они почти ничего не стоят. Конфиг, логирование и CLI появляются, когда скрипт запускают чаще раза в неделю. Тесты — как только результатам начинают доверять другие люди. Превращение скрипта в приложение — не событие, а привычка: каждый раз, когда ты вытаскиваешь константу в конфиг или превращаешь баг в тест, код группы становится немного надёжнее. А когда твоему инструменту понадобятся веб-интерфейс для всей группы и хранилище результатов — об этом следующие главы.
