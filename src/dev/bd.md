# Базы данных

Данные из сети мы забирать научились. Теперь вопрос, где их держать. Файлов хватает до тех пор, пока данные не понадобились нескольким людям одновременно.

## Когда файлов перестаёт хватать

Эволюция хранения данных в лаборатории почти всегда идёт по одному сценарию. Сначала появляется `result.csv`. Потом `result_final.csv`, `result_final_v2.csv` и папка `2026-08-20/` с двадцатью файлами, названия которых кодируют энергию пучка, номер захода и фамилию оператора. Через год у тебя десятки гигабайт CSV-файлов, и вопрос «покажи все измерения канала BPM01 при энергии выше 10 МэВ» превращается в вечер со скриптом, который рекурсивно обходит папки и парсит имена файлов.

Файлы и папки ломаются на трёх вещах:

- **Конкурентный доступ.** Скрипт сбора данных пишет в файл, а ты в этот момент открываешь его для анализа и читаешь половину строки. Два процесса пишут одновременно, и файл оказывается повреждённым. У файловой системы нет понятия «одновременно и безопасно».
- **Целостность.** CSV не проверяет ничего. В столбец с температурой попадает строка `"error"`, в одном файле столбцы идут в одном порядке, в другом файле в другом, а измерение ссылается на заход, удалённый кем-то вместе с папкой.
- **Поиск.** Чтобы найти нужные записи, приходится читать *все* файлы целиком в память. На миллионах записей это минуты; при правильной организации данных тот же запрос выполняется за миллисекунды.

Все три задачи решает **СУБД**, система управления базами данных. Она берёт на себя хранение, разводит одновременный доступ, следит за целостностью и даёт язык запросов, чтобы ты описывал, *что* найти, а не *как* перебирать файлы.

## Реляционная модель

Реляционную модель предложил Эдгар Кодд в 1970 году, и она до сих пор основная. Идея простая. Данные укладываются в **таблицы**, называемые в теории отношениями (relations). Строка таблицы содержит запись об одном объекте, а столбец задаёт атрибут с фиксированным типом.

Спроектируем схему для типичного эксперимента. У тебя есть измерительные кампании, внутри каждой лежат заходы (runs) с разными параметрами установки, а внутри каждого захода точки измерений с датчиков.

```
experiments ──< runs ──< measurements
   (1)          (N)          (N)
```

- `experiments` описывает кампанию, её название, установку и дату начала;
- `runs` описывает заход, его кампанию, номер, энергию пучка и оператора;
- `measurements` описывает отдельную точку, её заход, канал, время и значение.

Знак `──<` читается как связь «один ко многим», поскольку у одной кампании много заходов, а у одного захода много точек.

### Ключи и связи

**Первичным ключом** (primary key) называют столбец или набор столбцов, однозначно идентифицирующий строку. Обычно это суррогатный целочисленный `id`, который база выдаёт сама.

**Внешним ключом** (foreign key) называют столбец, ссылающийся на первичный ключ другой таблицы. `runs.experiment_id` хранит `id` кампании, и так строки связываются между собой. СУБД следит за валидностью ссылки. Нельзя вставить заход с `experiment_id = 42`, если кампании с таким `id` нет, и нельзя удалить кампанию, на которую ссылаются заходы.

Связь «многие ко многим» (например, публикации и авторы) выражается через промежуточную таблицу с двумя внешними ключами, и отдельного механизма для неё не нужно.

### Нормализация

Соблазнительно свалить всё в одну широкую таблицу, повторяя в каждой строке измерения название кампании, энергию и фамилию оператора. Работает это до первой правки. Оператор оказался «Ивановым», а не «Ивановым А.», и обновлять надо миллион строк; а если скрипт упадёт на середине, данные останутся противоречивыми. Такие ситуации называются аномалиями обновления.

**Нормализацией** называют устранение дублирования, при котором каждый факт хранится один раз, а всё остальное на него ссылается. Формально она описывается нормальными формами, для практики достаточно первых трёх, сводящихся к мнемонике: неключевые атрибуты зависят «от ключа, от всего ключа и ни от чего, кроме ключа». Энергия остаётся свойством захода, а не точки измерения, значит, ей место в `runs`. Название установки принадлежит кампании, значит, лежит в `experiments`.

Обратный процесс, денормализация, тоже бывает осмысленным. Для тяжёлой аналитики иногда специально собирают широкую таблицу, чтобы не соединять таблицы на каждый запрос. Но начинают всегда с нормализованной схемы.

## Основы SQL на примере SQLite

**SQL** (Structured Query Language) представляет собой декларативный язык работы с реляционными базами. Ты описываешь результат, а СУБД сама решает, как его получить.

Учиться будем на **SQLite**. Это встраиваемая СУБД, работающая без всякого сервера, вся база у неё лежит в одном файле на диске, а драйвер входит в стандартную библиотеку Python (модуль `sqlite3`). При этом SQLite остаётся полноценной реляционной СУБД с транзакциями, спокойно работающей с базами в десятки гигабайт. Для лабораторных данных этого более чем достаточно.

Открыть консоль SQLite можно командой `sqlite3 lab.db` (файл создастся сам), а посмотреть на базу глазами позволяет программа [DB Browser for SQLite](https://sqlitebrowser.org/).

### CREATE TABLE: создаём таблицы

Схема из трёх таблиц, нарисованная выше, на SQL выглядит почти так же, как читалась словами. Приписки после типов задают ограничения, соблюдаемые базой самостоятельно, что бы ни делал твой код.

```sql
CREATE TABLE experiments (
    id         INTEGER PRIMARY KEY,   -- первичный ключ, база выдаёт сама
    name       TEXT NOT NULL UNIQUE,  -- название кампании, без повторов
    setup      TEXT,                  -- описание установки
    started_at TEXT NOT NULL          -- дата в ISO-формате: '2026-08-20'
);

CREATE TABLE runs (
    id            INTEGER PRIMARY KEY,
    experiment_id INTEGER NOT NULL REFERENCES experiments(id),  -- внешний ключ
    run_number    INTEGER NOT NULL,
    energy_mev    REAL NOT NULL,      -- энергия пучка в заходе, МэВ
    operator      TEXT,
    started_at    TEXT NOT NULL,
    UNIQUE (experiment_id, run_number)  -- номер захода уникален внутри кампании
);

CREATE TABLE measurements (
    id      INTEGER PRIMARY KEY,
    run_id  INTEGER NOT NULL REFERENCES runs(id),
    channel TEXT NOT NULL,            -- имя канала: 'BPM01', 'T_magnet', ...
    t       REAL NOT NULL,            -- время от начала захода, с
    value   REAL NOT NULL             -- измеренное значение
);
```

Ограничения `NOT NULL`, `UNIQUE` и внешние ключи и дают ту целостность, которой не было у CSV. Попытка записать мусор закончится ошибкой, а не испорченными данными.

У SQLite здесь есть подвох, на который натыкаются все. Внешние ключи она проверяет только тогда, когда проверка включена явно, и включать её надо в каждом новом соединении:

```sql
PRAGMA foreign_keys = ON;
```

Без этой строки вставка ссылки на несуществующую кампанию пройдёт молча, и база тихо наберёт битых связей. PostgreSQL и MySQL проверяют внешние ключи всегда, без всяких оговорок.

### INSERT: вставляем данные

Вставка добавляет строки. Заполняемые базой столбцы перечислять не нужно, `id` она выдаст очередной. А вот `experiment_id` для захода придётся указать, иначе непонятно, к какой кампании он относится.

```sql
INSERT INTO experiments (name, setup, started_at)
VALUES ('Калибровка датчиков положения', 'стенд ЛИУ', '2026-08-20');

INSERT INTO runs (experiment_id, run_number, energy_mev, operator, started_at)
VALUES (1, 1, 12.5, 'Иванов', '2026-08-20T10:15:00');

-- несколько строк одним запросом
INSERT INTO measurements (run_id, channel, t, value) VALUES
    (1, 'BPM01',    0.0, 0.412),
    (1, 'BPM01',    0.1, 0.418),
    (1, 'T_magnet', 0.0, 42.3);
```

Последняя форма, со списком кортежей после `VALUES`, вставляет пачку строк одним запросом. Для тысячи точек с АЦП это на порядки быстрее тысячи отдельных `INSERT`; причина станет понятна в разделе про транзакции.

### SELECT: выбираем

Ради этого всё и затевалось. Тот самый вопрос, который раньше требовал вечера со скриптом-обходчиком папок, теперь пишется в три строки:

```sql
-- все точки канала BPM01 из первого захода, по возрастанию времени
SELECT t, value
FROM measurements
WHERE run_id = 1 AND channel = 'BPM01'
ORDER BY t;

-- десять последних заходов с энергией выше 10 МэВ
SELECT run_number, energy_mev, started_at
FROM runs
WHERE energy_mev > 10
ORDER BY started_at DESC
LIMIT 10;
```

`WHERE` фильтрует строки, `ORDER BY` сортирует (`DESC` задаёт убывание), `LIMIT` обрезает результат. Звёздочка `SELECT *` вернёт все столбцы, что удобно в консоли, но в скриптах лучше перечислять нужные явно.

### JOIN: соединяем таблицы

Нормализация разложила данные по трём таблицам, а `JOIN` собирает их обратно. Соединение сопоставляет строки по условию, обычно «внешний ключ равен первичному»:

```sql
-- каждая точка вместе с номером захода и названием кампании
SELECT e.name, r.run_number, m.t, m.value
FROM measurements AS m
JOIN runs        AS r ON r.id = m.run_id
JOIN experiments AS e ON e.id = r.experiment_id
WHERE m.channel = 'BPM01'
ORDER BY e.name, r.run_number, m.t;
```

`AS m` задаёт псевдоним таблицы, чтобы не писать длинные имена. Кроме обычного (внутреннего) `JOIN` есть `LEFT JOIN`, сохраняющий строки левой таблицы, даже если пары в правой не нашлось. Так можно, например, найти заходы вообще без измерений.

### GROUP BY: агрегируем

Агрегатные функции (`COUNT`, `AVG`, `SUM`, `MIN`, `MAX`) сворачивают группу строк в одно число, а `GROUP BY` задаёт, по чему группировать:

```sql
-- сводка по каждому заходу: число точек и статистика сигнала
SELECT r.run_number,
       r.energy_mev,
       COUNT(*)     AS n_points,
       AVG(m.value) AS mean_value,
       MIN(m.value) AS min_value,
       MAX(m.value) AS max_value
FROM measurements AS m
JOIN runs AS r ON r.id = m.run_id
WHERE m.channel = 'BPM01'
GROUP BY r.id
HAVING COUNT(*) >= 100   -- отбрасываем слишком короткие заходы
ORDER BY r.energy_mev;
```

Не спутай `HAVING` с `WHERE`. Первый фильтрует *после* группировки, по агрегатам; второй отбирает строки *до* неё.

### Индексы: ускоряем поиск

Без индекса запрос с `WHERE` заставляет базу просмотреть таблицу целиком. **Индексом** называют дополнительную структуру (обычно B-дерево), позволяющую находить строки по значению столбца за логарифмическое время, наподобие предметного указателя в книге.

```sql
CREATE INDEX idx_measurements_run_channel
ON measurements (run_id, channel);
```

Теперь выборка точек конкретного канала конкретного захода не зависит от общего размера таблицы. Первичный ключ и `UNIQUE` индексируются автоматически, а вот внешние ключи и столбцы, по которым ты часто фильтруешь, приходится индексировать самому. Платой за индекс становятся место на диске и чуть более медленная вставка, поэтому создавать индексы «на всякий случай» на все столбцы не нужно. Проверить, пользуется ли запрос индексом, можно, приписав перед ним `EXPLAIN QUERY PLAN`.

## Тот же SQL из Python

Модуль `sqlite3` входит в стандартную библиотеку, и устанавливать ничего не надо.

```python
import sqlite3

# открываем (или создаём) файл базы; ":memory:" — временная база в памяти
con = sqlite3.connect("lab.db")

# в SQLite проверка внешних ключей по умолчанию выключена — включаем
con.execute("PRAGMA foreign_keys = ON")

cur = con.cursor()  # курсор выполняет запросы и отдаёт результаты

# создаём таблицу, если её ещё нет (текст запроса — тот же SQL)
cur.execute("""
    CREATE TABLE IF NOT EXISTS measurements (
        id      INTEGER PRIMARY KEY,
        run_id  INTEGER NOT NULL,
        channel TEXT NOT NULL,
        t       REAL NOT NULL,
        value   REAL NOT NULL
    )
""")

# одиночная вставка: значения передаём кортежем, в запросе — знаки вопроса
cur.execute(
    "INSERT INTO measurements (run_id, channel, t, value) VALUES (?, ?, ?, ?)",
    (1, "BPM01", 0.0, 0.412),
)

# массовая вставка: executemany принимает любой итерируемый объект;
# read_adc() здесь — твоя функция опроса АЦП
points = [(1, "BPM01", 0.1 * i, read_adc()) for i in range(1000)]
cur.executemany(
    "INSERT INTO measurements (run_id, channel, t, value) VALUES (?, ?, ?, ?)",
    points,
)
con.commit()  # фиксируем изменения на диске

# выборка: по курсору можно итерироваться, каждая строка — кортеж
for t, value in cur.execute(
    "SELECT t, value FROM measurements WHERE channel = ? ORDER BY t",
    ("BPM01",),
):
    print(t, value)

con.close()
```

Для небольших выборок удобны `cur.fetchone()` и `cur.fetchall()`, но итерация по курсору экономнее, потому что строки читаются по мере надобности, а не все сразу в память.

### Параметризованные запросы и SQL-инъекции

В примерах выше значения подставлялись через знаки вопроса, а не f-строками. Это не вкусовщина, а безопасность. Представь, что имя канала приходит извне, из формы на веб-странице, из аргумента командной строки или из чужого файла.

```python
channel = input("Канал: ")

# ТАК ДЕЛАТЬ НЕЛЬЗЯ: запрос склеивается из чужого текста
cur.execute(f"SELECT t, value FROM measurements WHERE channel = '{channel}'")
```

Если пользователь введёт `' OR '1'='1`, итоговый запрос превратится в `... WHERE channel = '' OR '1'='1'`, где условие всегда истинно, фильтр исчез, а наружу утекла вся таблица. А ввод вида `'; DROP TABLE measurements; --` в СУБД, чей драйвер исполняет несколько команд подряд, просто уничтожит таблицу. Всё это называется **SQL-инъекцией**, одной из самых старых и до сих пор самых распространённых уязвимостей (классику жанра описывает [xkcd про школьника Bobby Tables](https://xkcd.com/327/)).

Параметризованный запрос неуязвим по построению: текст запроса и данные передаются драйверу *раздельно*, и введённая строка останется просто строкой, что бы в ней ни было:

```python
# правильно: запрос отдельно, данные отдельно
cur.execute("SELECT t, value FROM measurements WHERE channel = ?", (channel,))
```

Правило простое: **значения передаются только через параметры, всегда**, даже если «данные точно свои». Единственное ограничение состоит в том, что параметром может быть лишь значение, но не имя таблицы или столбца. Если имена приходится подставлять динамически, проверяй их по белому списку.

## Транзакции и ACID

**Транзакцией** называют группу запросов, выполняемую как единое целое, поэтому применяются либо все, либо ни один. Классические гарантии транзакций описываются аббревиатурой **ACID**:

- **Atomicity** (атомарность) означает неделимость транзакции, и сбой на середине откатывает всё сделанное;
- **Consistency** (согласованность) переводит базу из одного корректного состояния в другое, не нарушая ограничений (ключи, `NOT NULL`, `UNIQUE`);
- **Isolation** (изолированность) прячет промежуточные состояния параллельных транзакций друг от друга;
- **Durability** (долговечность) сохраняет подтверждённые (`COMMIT`) данные даже при отключении питания.

Заход и его точки должны попасть в базу вместе, ведь заход без точек и точки-сироты одинаково бессмысленны.

```python
def save_run(con, run_row, points):
    """Сохраняет заход и все его измерения одной транзакцией."""
    cur = con.cursor()
    try:
        # первый INSERT неявно открывает транзакцию
        cur.execute(
            "INSERT INTO runs (experiment_id, run_number, energy_mev, started_at) "
            "VALUES (?, ?, ?, ?)",
            run_row,
        )
        run_id = cur.lastrowid  # id только что вставленной строки
        cur.executemany(
            "INSERT INTO measurements (run_id, channel, t, value) "
            "VALUES (?, ?, ?, ?)",
            [(run_id, ch, t, v) for ch, t, v in points],
        )
        con.commit()    # всё получилось — фиксируем
    except sqlite3.Error:
        con.rollback()  # любая ошибка — откатываем целиком
        raise
```

Ту же пару commit/rollback даёт конструкция `with con:`, подтверждающая транзакцию при успешном выходе из блока и откатывающая её при исключении. Заодно транзакции ускоряют массовую вставку. Миллион `INSERT` с commit после каждого означает миллион синхронизаций с диском, а те же вставки в одной транзакции быстрее на порядки.

## SQLite, PostgreSQL или MySQL

Рано или поздно возникает вопрос, не пора ли перерасти один файл. Три реляционные СУБД встречаются в лаборатории чаще всего, и различаются они не столько языком запросов, поскольку SQL везде почти один и тот же, сколько тем, кто и как до базы дотягивается.

| | SQLite | PostgreSQL | MySQL / MariaDB |
|---|---|---|---|
| Архитектура | встраиваемая библиотека, вся база в одном файле | клиент-серверная | клиент-серверная |
| Установка | не нужна, есть в Python | отдельный сервис | отдельный сервис |
| Одновременная запись | один пишущий процесс | много клиентов | много клиентов |
| Типизация | динамическая, мягкая | строгая, богатая (массивы, JSONB, диапазоны) | строгая, скромнее |
| Права доступа | нет (права на файл) | пользователи, роли, гранулярные права | пользователи и права |
| Сильная сторона | нулевая настройка, переносимость | функциональность и расширения (PostGIS, TimescaleDB) | распространённость в веб-хостинге |
| Типичный случай | локальные данные, прототипы, файлы до единиц ГБ | серверное приложение, общая база группы | веб-проекты, легаси-системы |

Практическое правило простое. Если данные лежат на твоём диске и работаешь с ними ты и твои скрипты, бери **SQLite** и не выдумывай лишнего. Если база нужна нескольким людям или сервисам по сети, если пишут в неё одновременно и требуются права доступа, бери **PostgreSQL**, сегодня это выбор по умолчанию для серверной СУБД. **MySQL** чаще достаётся как данность вместе с существующим проектом или хостингом, чем выбирается осознанно для новой системы.

## ORM: SQLAlchemy

Писать SQL строками внутри Python-кода не всегда удобно. Строки не проверяются до запуска, результаты приходят безликими кортежами, а логика «объект и его связи» размазывается по запросам. **ORM** (Object-Relational Mapping) отображает таблицы на классы, строки на объекты, а внешние ключи на атрибуты-связи. Стандартом де-факто в Python служит [SQLAlchemy](https://docs.sqlalchemy.org/).

```python
from sqlalchemy import ForeignKey, create_engine, select
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column, relationship, Session,
)

class Base(DeclarativeBase):
    pass

class Run(Base):
    __tablename__ = "runs"

    id: Mapped[int] = mapped_column(primary_key=True)
    energy_mev: Mapped[float]
    # связь "один ко многим": у захода — список измерений
    measurements: Mapped[list["Measurement"]] = relationship(back_populates="run")

class Measurement(Base):
    __tablename__ = "measurements"

    id: Mapped[int] = mapped_column(primary_key=True)
    run_id: Mapped[int] = mapped_column(ForeignKey("runs.id"))
    channel: Mapped[str]
    value: Mapped[float]
    run: Mapped[Run] = relationship(back_populates="measurements")

engine = create_engine("sqlite:///lab.db")  # та же база, поменяется только URL
Base.metadata.create_all(engine)            # создаёт таблицы по описанию классов

with Session(engine) as session:
    # объекты вместо INSERT: связи расставляются сами
    run = Run(energy_mev=12.5)
    run.measurements.append(Measurement(channel="BPM01", value=0.412))
    session.add(run)
    session.commit()

    # запрос вместо SELECT ... JOIN: строится из Python-выражений
    stmt = select(Measurement).join(Run).where(Run.energy_mev > 10)
    for m in session.execute(stmt).scalars():
        print(m.channel, m.value, m.run.energy_mev)
```

Заметь, что смена SQLite на PostgreSQL сводится к правке строки в `create_engine`, а остальной код не изменится.

ORM оправдан в приложении с десятком связанных таблиц и развивающейся схемой (миграции удобно вести инструментом [Alembic](https://alembic.sqlalchemy.org/)), при командной разработке и множестве типовых операций «создать-прочитать-обновить-удалить». Чистый SQL лучше для аналитических запросов с многоэтажными агрегатами и оконными функциями (SQL здесь короче и прозрачнее ORM-конструкций), для массовых загрузок и разовых скриптов. И в любом случае ORM не освобождает от знания SQL. Под капотом он генерирует всё тот же SQL, и когда запрос внезапно тормозит, разбираться придётся с ним (включи `create_engine(..., echo=True)` и посмотри, что реально уходит в базу).

## Нереляционные базы данных

Реляционная модель универсальна, но не единственна. Под конкретные профили нагрузки есть специализированные базы, которые скопом называют «NoSQL». Знать их надо хотя бы обзорно, чтобы узнавать задачу в лицо.

Проще всех устроено хранилище пар «ключ → значение», [Redis](https://redis.io/). Оно живёт в оперативной памяти, и операции занимают микросекунды. Типичными ролями становятся кеш (результат тяжёлого запроса или расчёта кладётся под ключ с временем жизни), очереди задач между процессами (на Redis работают брокеры для Celery), счётчики и pub/sub-уведомления. Запись на диск есть, но опциональна. Redis отвечает за скорость, а не за главное хранилище истины.

Там, где у записей нет общей структуры, берут документные базы вроде [MongoDB](https://www.mongodb.com/). Единицей хранения служит документ, JSON-подобная вложенная структура; документы собираются в коллекции, и жёсткой схемы нет, поэтому соседние документы могут иметь разные поля. Удобно для разнородных метаданных, у которых структура меняется от записи к записи. Подвох в том, что «отсутствие схемы» означает лишь одно. Схема живёт не в базе, а в голове и в коде, и проверять её теперь тоже тебе.

Телеметрию установки, то есть давление в вакуумной камере, токи магнитов и температуры, приходящие с сотен датчиков каждую секунду годами, держат в базах временных рядов. Это то, что в ускорительной технике называется slow control, и [InfluxDB](https://www.influxdata.com/) заточена под такой поток «метка времени → значение» с тегами. Такие базы умеют автоматически прореживать и удалять старые данные (retention policies), быстро агрегировать по окнам времени («среднее за каждую минуту последних суток») и штатно стыкуются с [Grafana](https://grafana.com/) для живых дашбордов мониторинга. Близким родственником в мире PostgreSQL выступает расширение TimescaleDB.

Наконец, для аналитики на миллиардах записей придуманы колоночные базы, самая известная из которых называется [ClickHouse](https://clickhouse.com/). Она хранит данные не по строкам, а по столбцам. Значения одного столбца лежат рядом, отлично сжимаются, и запрос «среднее value по миллиарду строк» читает с диска только нужные столбцы, укладываясь в секунды на обычном сервере вместо часов и сохраняя привычный SQL-диалект. Платой становится слабость в точечных обновлениях и удалениях; колоночные базы рассчитаны на «дописывай и анализируй», а не на правки отдельных строк.

### Как выбирают: пример реальной системы

Обзор типов баз отвечает на вопрос «что бывает», но не на вопрос «что брать мне». Разберём это на живом примере, системе хранения данных ускорительного комплекса, где используются сразу три базы. Такой подход называется **полиглотным хранением** (polyglot persistence), при котором под каждый профиль данных берётся приспособленное к нему хранилище.

В PostgreSQL уходит всё, что должно быть строгим: пользователи и их роли, конфигурация ускорителя и его элементов, метаданные экспериментов (что за эксперимент, когда, кто ответственный), расписание работы установки и журнал событий. Общее у этих данных одно. Структура известна заранее, меняется редко, а целостность критична. Если запись эксперимента ссылается на несуществующего оператора, это ошибка, которую должна ловить база, а не код. Здесь и нужны схема, внешние ключи и ACID-транзакции.

В MongoDB складывают то, что разнородно: результаты измерений, данные пучка (траектории, размеры, интенсивность), временные ряды параметров, результаты моделирования и оптимизации. У этих данных нет и не может быть единой схемы, потому что каждый новый тип эксперимента приносит свой набор полей. Требовать миграции базы под каждую новую методику — верный способ добиться того, чтобы данные складывали мимо базы, в файлы на рабочем столе. Гибкая схема здесь не уступка, она и есть требование задачи.

Redis держит то, что живёт недолго: кеш частых запросов, текущие состояния устройств, сессии пользователей веб-интерфейса, очереди сообщений между компонентами. Ключевое слово здесь «текущее». Значение тока магнита *прямо сейчас* спрашивают сотни раз в секунду, и ходить за ним в дисковую базу бессмысленно. Потеря этих данных при перезапуске неприятна, но не катастрофична, так как истина хранится в других двух базах.

Схему выбора можно свести к одному признаку на каждую базу.

| Признак данных | Подходящая база |
|---|---|
| Структура известна заранее, а нарушение связей недопустимо | PostgreSQL |
| Структура меняется от записи к записи | MongoDB |
| Данные нужны очень быстро, а их потеря не смертельна | Redis |

У полиглотного хранения есть и цена, о которой лучше знать заранее. Как только данные разъезжаются по трём базам, **исчезает транзакция, охватывающая их все**, и одним атомарным действием уже не записать эксперимент в PostgreSQL вместе с его результатами в MongoDB. Согласованность приходится обеспечивать вручную, распределёнными транзакциями или компенсирующими действиями, откатывающими то, что успело записаться. Сложность заметная. Окупается она, только когда профили данных действительно разные.

Отсюда практический вывод для студенческого проекта: **начинай с одной базы**. Одна PostgreSQL закрывает потребности лабораторного сервиса на годы вперёд, а для документов в ней есть тип `JSONB` с индексацией по полям внутри документа. Вторую базу заводят не потому, что «так делают в больших системах», а когда первая измеримо перестала справляться с конкретным профилем нагрузки.

## Pandas и базы данных

Мост между базой и анализом данных встроен в pandas. Функция `read_sql` выполняет запрос и возвращает `DataFrame`, а `to_sql` записывает `DataFrame` в таблицу.

```python
import pandas as pd
import sqlite3

con = sqlite3.connect("lab.db")

# фильтрация и агрегация выполняются в базе,
# в память попадает только готовая сводка
df = pd.read_sql(
    """
    SELECT r.energy_mev, AVG(m.value) AS mean_signal
    FROM measurements AS m
    JOIN runs AS r ON r.id = m.run_id
    WHERE m.channel = 'BPM01'
    GROUP BY r.id
    """,
    con,
)

# дальше — обычный pandas: график зависимости сигнала от энергии
df.plot.scatter(x="energy_mev", y="mean_signal")

# и обратно: результат анализа — в новую таблицу
df.to_sql("run_summary", con, if_exists="replace", index=False)
```

Тяжёлую фильтрацию и агрегацию отдавай базе (SQL с `WHERE` и `GROUP BY`), а в pandas загружай уже компактный результат, тогда и память, и время расходуются на порядки экономнее, чем при подходе «прочитать всё и фильтровать в DataFrame». Связка «SQL-запрос → DataFrame → график» и даёт простейшее приложение для визуализации данных; про сами графики смотри главы про [обработку](python/numpy-and-pandas.md) и [визуализацию](python/visualization/practice.md) данных.

## С чего начать в своей лаборатории

Не нужно ждать большого проекта, чтобы применить всё это. Рецепт перехода от тысячи CSV к одной базе:

1. Заведи один файл `lab.db` и опиши схему. Минимально нужны таблицы вида `experiments`, `runs`, `measurements` с первичными и внешними ключами и `NOT NULL` на важных полях. Схема служит документацией, которая ещё и проверяет сама себя.
2. Импортируй накопленные CSV одним скриптом:

    ```python
    from pathlib import Path
    import pandas as pd
    import sqlite3

    con = sqlite3.connect("lab.db")

    for csv_path in Path("data").glob("**/*.csv"):
        df = pd.read_csv(csv_path)
        df["source_file"] = str(csv_path)  # не теряем происхождение данных
        df.to_sql("measurements_raw", con, if_exists="append", index=False)
    ```

    Дальше «сырую» таблицу можно разложить по нормализованной схеме уже SQL-запросами.
3. Новые данные пиши сразу в базу, применяя в скрипте сбора `executemany` пачками точек и `commit` раз в несколько секунд, а не файл на каждый заход.
4. Включи `PRAGMA journal_mode=WAL`, и в этом режиме SQLite позволит читать базу (строить графики) параллельно с идущей записью.
5. Смотреть данные глазами удобно в DB Browser for SQLite, а резервной копией служит обычная копия одного файла (`Connection.backup()` из Python делает её корректно даже во время работы).

Когда данными начнёт пользоваться вся группа с нескольких машин, перенесёшь схему в PostgreSQL; SQL и почти весь код при этом останутся прежними.
