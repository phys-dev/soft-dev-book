# Базы данных

Данные из сети мы забирать научились. Теперь вопрос, где их держать: файлов хватает ровно до тех пор, пока данные не понадобились нескольким людям одновременно.

## Когда файлов перестаёт хватать

Эволюция хранения данных в лаборатории почти всегда проходит одни и те же стадии. Сначала появляется `result.csv`. Потом `result_final.csv`, `result_final_v2.csv` и папка `2026-08-20/` с двадцатью файлами, названия которых кодируют энергию пучка, номер захода и фамилию оператора. Через год у тебя десятки гигабайт CSV-файлов, и вопрос «покажи все измерения канала BPM01 при энергии выше 10 МэВ» превращается в вечер со скриптом, который рекурсивно обходит папки и парсит имена файлов.

Файлы и папки ломаются на трёх вещах:

- **Конкурентный доступ.** Скрипт сбора данных пишет в файл, а ты в этот момент открываешь его для анализа — и читаешь половину строки. Два процесса пишут одновременно — файл повреждён. У файловой системы нет понятия «одновременно и безопасно».
- **Целостность.** CSV не проверяет ничего: в столбец с температурой попадает строка `"error"`, в одном файле столбцы идут в одном порядке, в другом — в другом, а измерение ссылается на заход, который кто-то удалил вместе с папкой.
- **Поиск.** Чтобы найти нужные записи, приходится читать *все* файлы целиком в память. На миллионах записей это минуты; при правильной организации данных тот же запрос выполняется за миллисекунды.

Ровно эти три задачи решает **СУБД** — система управления базами данных. Это программа, которая берёт на себя хранение, разграничивает одновременный доступ, следит за целостностью и предоставляет язык запросов, чтобы ты описывал *что* найти, а не *как* перебирать файлы.

## Реляционная модель

Реляционную модель предложил Эдгар Кодд в 1970 году, и она до сих пор основная. Идея простая: данные — **таблицы** (в теории они называются отношениями, relations). Строка таблицы — запись об одном объекте, столбец — атрибут с фиксированным типом.

Спроектируем схему для типичного эксперимента. У тебя есть измерительные кампании, внутри каждой — заходы (runs) с разными параметрами установки, внутри каждого захода — точки измерений с датчиков:

```
experiments ──< runs ──< measurements
   (1)          (N)          (N)
```

- `experiments` — кампания: название, установка, дата начала;
- `runs` — заход: к какой кампании относится, номер, энергия пучка, оператор;
- `measurements` — отдельная точка: к какому заходу относится, канал, время, значение.

Знак `──<` читается как связь «один ко многим»: у одной кампании много заходов, у одного захода много точек.

### Ключи и связи

**Первичный ключ** (primary key) — столбец (или набор столбцов), который однозначно идентифицирует строку. Обычно это суррогатный целочисленный `id`, который база выдаёт сама.

**Внешний ключ** (foreign key) — столбец, который ссылается на первичный ключ другой таблицы. `runs.experiment_id` хранит `id` кампании — так строки связываются между собой. СУБД следит, чтобы ссылка была валидной: нельзя вставить заход с `experiment_id = 42`, если кампании с таким `id` нет, и нельзя удалить кампанию, на которую ссылаются заходы.

Связь «многие ко многим» (например, публикации и авторы) выражается через промежуточную таблицу с двумя внешними ключами — отдельного механизма для неё не нужно.

### Нормализация

Соблазнительно свалить всё в одну широкую таблицу: в каждой строке измерения повторять название кампании, энергию и фамилию оператора. Это работает ровно до первой правки: оператор оказался «Ивановым», а не «Ивановым А.», и обновлять надо миллион строк, причём если скрипт упадёт на середине, данные останутся противоречивыми. Такие ситуации называются аномалиями обновления.

**Нормализация** — процесс устранения дублирования: каждый факт хранится ровно один раз, а всё остальное на него ссылается. Формально описывается нормальными формами, для практики достаточно первых трёх, которые сводятся к мнемонике: неключевые атрибуты зависят «от ключа, от всего ключа и ни от чего, кроме ключа». Энергия — свойство захода, а не точки измерения, значит, ей место в `runs`. Название установки — свойство кампании, значит, в `experiments`.

Обратный процесс — денормализация — тоже бывает осмысленным: для тяжёлой аналитики иногда специально собирают широкую таблицу, чтобы не соединять таблицы на каждый запрос. Но начинать всегда стоит с нормализованной схемы.

## Основы SQL на примере SQLite

**SQL** (Structured Query Language) — декларативный язык работы с реляционными базами: ты описываешь результат, а СУБД сама решает, как его получить.

Учиться будем на **SQLite**. Это встраиваемая СУБД: никакого сервера, вся база — один файл на диске, а драйвер встроен в стандартную библиотеку Python (модуль `sqlite3`). При этом SQLite — полноценная реляционная СУБД с транзакциями, которая спокойно работает с базами в десятки гигабайт. Для лабораторных данных этого более чем достаточно.

Открыть консоль SQLite можно командой `sqlite3 lab.db` (файл создастся сам), а посмотреть на базу глазами — программой [DB Browser for SQLite](https://sqlitebrowser.org/).

### CREATE TABLE: создаём таблицы

```sql
CREATE TABLE experiments (
    id         INTEGER PRIMARY KEY,   -- первичный ключ, база выдаёт сама
    name       TEXT NOT NULL UNIQUE,  -- название кампании, без повторов
    setup      TEXT,                  -- описание установки
    started_at TEXT NOT NULL          -- дата в ISO-формате: '2026-08-20'
);

CREATE TABLE runs (
    id            INTEGER PRIMARY KEY,
    experiment_id INTEGER NOT NULL REFERENCES experiments(id),  -- внешний ключ
    run_number    INTEGER NOT NULL,
    energy_mev    REAL NOT NULL,      -- энергия пучка в заходе, МэВ
    operator      TEXT,
    started_at    TEXT NOT NULL,
    UNIQUE (experiment_id, run_number)  -- номер захода уникален внутри кампании
);

CREATE TABLE measurements (
    id      INTEGER PRIMARY KEY,
    run_id  INTEGER NOT NULL REFERENCES runs(id),
    channel TEXT NOT NULL,            -- имя канала: 'BPM01', 'T_magnet', ...
    t       REAL NOT NULL,            -- время от начала захода, с
    value   REAL NOT NULL             -- измеренное значение
);
```

Ограничения `NOT NULL`, `UNIQUE` и внешние ключи — это и есть целостность, которую CSV не давал: попытка записать мусор закончится ошибкой, а не испорченными данными.

### INSERT: вставляем данные

```sql
INSERT INTO experiments (name, setup, started_at)
VALUES ('Калибровка датчиков положения', 'стенд ЛИУ', '2026-08-20');

INSERT INTO runs (experiment_id, run_number, energy_mev, operator, started_at)
VALUES (1, 1, 12.5, 'Иванов', '2026-08-20T10:15:00');

-- несколько строк одним запросом
INSERT INTO measurements (run_id, channel, t, value) VALUES
    (1, 'BPM01',    0.0, 0.412),
    (1, 'BPM01',    0.1, 0.418),
    (1, 'T_magnet', 0.0, 42.3);
```

### SELECT: выбираем

```sql
-- все точки канала BPM01 из первого захода, по возрастанию времени
SELECT t, value
FROM measurements
WHERE run_id = 1 AND channel = 'BPM01'
ORDER BY t;

-- десять последних заходов с энергией выше 10 МэВ
SELECT run_number, energy_mev, started_at
FROM runs
WHERE energy_mev > 10
ORDER BY started_at DESC
LIMIT 10;
```

`WHERE` фильтрует строки, `ORDER BY` сортирует (`DESC` — по убыванию), `LIMIT` обрезает результат. Звёздочка `SELECT *` вернёт все столбцы — удобно в консоли, но в скриптах лучше перечислять нужные явно.

### JOIN: соединяем таблицы

Нормализация разложила данные по трём таблицам — `JOIN` собирает их обратно. Соединение сопоставляет строки по условию, обычно «внешний ключ равен первичному»:

```sql
-- каждая точка вместе с номером захода и названием кампании
SELECT e.name, r.run_number, m.t, m.value
FROM measurements AS m
JOIN runs        AS r ON r.id = m.run_id
JOIN experiments AS e ON e.id = r.experiment_id
WHERE m.channel = 'BPM01'
ORDER BY e.name, r.run_number, m.t;
```

`AS m` — псевдоним таблицы, чтобы не писать длинные имена. Кроме обычного (внутреннего) `JOIN` есть `LEFT JOIN`: он сохраняет строки левой таблицы, даже если пары в правой не нашлось. Так можно, например, найти заходы вообще без измерений.

### GROUP BY: агрегируем

Агрегатные функции (`COUNT`, `AVG`, `SUM`, `MIN`, `MAX`) сворачивают группу строк в одно число, а `GROUP BY` задаёт, по чему группировать:

```sql
-- сводка по каждому заходу: число точек и статистика сигнала
SELECT r.run_number,
       r.energy_mev,
       COUNT(*)     AS n_points,
       AVG(m.value) AS mean_value,
       MIN(m.value) AS min_value,
       MAX(m.value) AS max_value
FROM measurements AS m
JOIN runs AS r ON r.id = m.run_id
WHERE m.channel = 'BPM01'
GROUP BY r.id
HAVING COUNT(*) >= 100   -- отбрасываем слишком короткие заходы
ORDER BY r.energy_mev;
```

Обрати внимание на `HAVING`: это фильтр *после* группировки (по агрегатам), тогда как `WHERE` фильтрует строки *до* неё.

### Индексы: ускоряем поиск

Без индекса запрос с `WHERE` заставляет базу просмотреть таблицу целиком. **Индекс** — дополнительная структура (обычно B-дерево), которая позволяет находить строки по значению столбца за логарифмическое время — как предметный указатель в книге:

```sql
CREATE INDEX idx_measurements_run_channel
ON measurements (run_id, channel);
```

Теперь выборка точек конкретного канала конкретного захода не зависит от общего размера таблицы. Первичный ключ и `UNIQUE` индексируются автоматически, а вот внешние ключи и столбцы, по которым ты часто фильтруешь, — нет: их индексируй сам. Плата за индекс — место на диске и чуть более медленная вставка, поэтому создавать индексы «на всякий случай» на все столбцы не нужно. Проверить, пользуется ли запрос индексом, можно, приписав перед ним `EXPLAIN QUERY PLAN`.

## Тот же SQL из Python

Модуль `sqlite3` входит в стандартную библиотеку — ничего устанавливать не надо:

```python
import sqlite3

# открываем (или создаём) файл базы; ":memory:" — временная база в памяти
con = sqlite3.connect("lab.db")

# в SQLite проверка внешних ключей по умолчанию выключена — включаем
con.execute("PRAGMA foreign_keys = ON")

cur = con.cursor()  # курсор выполняет запросы и отдаёт результаты

# создаём таблицу, если её ещё нет (текст запроса — тот же SQL)
cur.execute("""
    CREATE TABLE IF NOT EXISTS measurements (
        id      INTEGER PRIMARY KEY,
        run_id  INTEGER NOT NULL,
        channel TEXT NOT NULL,
        t       REAL NOT NULL,
        value   REAL NOT NULL
    )
""")

# одиночная вставка: значения передаём кортежем, в запросе — знаки вопроса
cur.execute(
    "INSERT INTO measurements (run_id, channel, t, value) VALUES (?, ?, ?, ?)",
    (1, "BPM01", 0.0, 0.412),
)

# массовая вставка: executemany принимает любой итерируемый объект;
# read_adc() здесь — твоя функция опроса АЦП
points = [(1, "BPM01", 0.1 * i, read_adc()) for i in range(1000)]
cur.executemany(
    "INSERT INTO measurements (run_id, channel, t, value) VALUES (?, ?, ?, ?)",
    points,
)
con.commit()  # фиксируем изменения на диске

# выборка: по курсору можно итерироваться, каждая строка — кортеж
for t, value in cur.execute(
    "SELECT t, value FROM measurements WHERE channel = ? ORDER BY t",
    ("BPM01",),
):
    print(t, value)

con.close()
```

Для небольших выборок удобны `cur.fetchone()` и `cur.fetchall()`, но итерация по курсору экономнее: строки читаются по мере надобности, а не все сразу в память.

### Параметризованные запросы и SQL-инъекции

В примерах выше значения подставлялись через знаки вопроса, а не f-строками. Это не вкусовщина, а безопасность. Представь, что имя канала приходит извне — из формы на веб-странице, аргумента командной строки, чужого файла:

```python
channel = input("Канал: ")

# ТАК ДЕЛАТЬ НЕЛЬЗЯ: запрос склеивается из чужого текста
cur.execute(f"SELECT t, value FROM measurements WHERE channel = '{channel}'")
```

Если пользователь введёт `' OR '1'='1`, итоговый запрос превратится в `... WHERE channel = '' OR '1'='1'` — условие всегда истинно, фильтр исчез, наружу утекла вся таблица. А ввод вида `'; DROP TABLE measurements; --` в СУБД, чей драйвер исполняет несколько команд подряд, просто уничтожит таблицу. Это называется **SQL-инъекцией** — одна из самых старых и до сих пор самых распространённых уязвимостей (классика жанра — [xkcd про школьника Bobby Tables](https://xkcd.com/327/)).

Параметризованный запрос неуязвим по построению: текст запроса и данные передаются драйверу *раздельно*, и введённая строка останется просто строкой, что бы в ней ни было:

```python
# правильно: запрос отдельно, данные отдельно
cur.execute("SELECT t, value FROM measurements WHERE channel = ?", (channel,))
```

Правило простое: **значения — только через параметры, всегда**, даже если «данные точно свои». Единственное ограничение: параметром может быть лишь значение, но не имя таблицы или столбца — если имена приходится подставлять динамически, проверяй их по белому списку.

## Транзакции и ACID

**Транзакция** — группа запросов, которая выполняется как единое целое: либо применяются все, либо ни один. Классические гарантии транзакций описываются аббревиатурой **ACID**:

- **Atomicity** (атомарность) — транзакция неделима: сбой на середине откатывает всё сделанное;
- **Consistency** (согласованность) — база переходит из одного корректного состояния в другое, ограничения (ключи, `NOT NULL`, `UNIQUE`) не нарушаются;
- **Isolation** (изолированность) — параллельные транзакции не видят промежуточных состояний друг друга;
- **Durability** (долговечность) — после подтверждения (`COMMIT`) данные переживут даже отключение питания.

Пример: заход и его точки должны попасть в базу вместе — заход без точек или точки-сироты одинаково бессмысленны:

```python
def save_run(con, run_row, points):
    """Сохраняет заход и все его измерения одной транзакцией."""
    cur = con.cursor()
    try:
        # первый INSERT неявно открывает транзакцию
        cur.execute(
            "INSERT INTO runs (experiment_id, run_number, energy_mev, started_at) "
            "VALUES (?, ?, ?, ?)",
            run_row,
        )
        run_id = cur.lastrowid  # id только что вставленной строки
        cur.executemany(
            "INSERT INTO measurements (run_id, channel, t, value) "
            "VALUES (?, ?, ?, ?)",
            [(run_id, ch, t, v) for ch, t, v in points],
        )
        con.commit()    # всё получилось — фиксируем
    except sqlite3.Error:
        con.rollback()  # любая ошибка — откатываем целиком
        raise
```

Ту же пару commit/rollback даёт конструкция `with con:` — она подтверждает транзакцию при успешном выходе из блока и откатывает при исключении. Заодно транзакции ускоряют массовую вставку: миллион `INSERT` с commit после каждого — миллион синхронизаций с диском, а те же вставки в одной транзакции быстрее на порядки.

## SQLite, PostgreSQL или MySQL

| | SQLite | PostgreSQL | MySQL / MariaDB |
|---|---|---|---|
| Архитектура | встраиваемая библиотека, база — один файл | клиент-серверная | клиент-серверная |
| Установка | не нужна, есть в Python | отдельный сервис | отдельный сервис |
| Одновременная запись | один пишущий процесс | много клиентов | много клиентов |
| Типизация | динамическая, мягкая | строгая, богатая (массивы, JSONB, диапазоны) | строгая, скромнее |
| Права доступа | нет (права на файл) | пользователи, роли, гранулярные права | пользователи и права |
| Сильная сторона | нулевая настройка, переносимость | функциональность и расширения (PostGIS, TimescaleDB) | распространённость в веб-хостинге |
| Типичный случай | локальные данные, прототипы, файлы до единиц ГБ | серверное приложение, общая база группы | веб-проекты, легаси-системы |

Практическое правило. Данные лежат на твоём диске и работаешь с ними ты и твои скрипты — **SQLite**, не выдумывай лишнего. База нужна нескольким людям или сервисам по сети, много одновременной записи, нужны права доступа — **PostgreSQL**: сегодня это выбор по умолчанию для серверной СУБД. **MySQL** чаще встречается как данность в существующих проектах и хостингах, чем как осознанный выбор для новой системы.

## ORM: SQLAlchemy

Писать SQL строками внутри Python-кода не всегда удобно: строки не проверяются до запуска, результаты — безликие кортежи, а логика «объект и его связи» размазывается по запросам. **ORM** (Object-Relational Mapping) — библиотека, которая отображает таблицы на классы, строки — на объекты, а внешние ключи — на атрибуты-связи. Стандарт де-факто в Python — [SQLAlchemy](https://docs.sqlalchemy.org/):

```python
from sqlalchemy import ForeignKey, create_engine, select
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, mapped_column, relationship, Session,
)

class Base(DeclarativeBase):
    pass

class Run(Base):
    __tablename__ = "runs"

    id: Mapped[int] = mapped_column(primary_key=True)
    energy_mev: Mapped[float]
    # связь "один ко многим": у захода — список измерений
    measurements: Mapped[list["Measurement"]] = relationship(back_populates="run")

class Measurement(Base):
    __tablename__ = "measurements"

    id: Mapped[int] = mapped_column(primary_key=True)
    run_id: Mapped[int] = mapped_column(ForeignKey("runs.id"))
    channel: Mapped[str]
    value: Mapped[float]
    run: Mapped[Run] = relationship(back_populates="measurements")

engine = create_engine("sqlite:///lab.db")  # та же база, поменяется только URL
Base.metadata.create_all(engine)            # создаёт таблицы по описанию классов

with Session(engine) as session:
    # объекты вместо INSERT: связи расставляются сами
    run = Run(energy_mev=12.5)
    run.measurements.append(Measurement(channel="BPM01", value=0.412))
    session.add(run)
    session.commit()

    # запрос вместо SELECT ... JOIN: строится из Python-выражений
    stmt = select(Measurement).join(Run).where(Run.energy_mev > 10)
    for m in session.execute(stmt).scalars():
        print(m.channel, m.value, m.run.energy_mev)
```

Заметь: сменить SQLite на PostgreSQL — поменять строку в `create_engine`, остальной код не изменится.

Когда ORM оправдан: приложение с десятком связанных таблиц и развивающейся схемой (миграции удобно вести инструментом [Alembic](https://alembic.sqlalchemy.org/)), командная разработка, много типовых операций «создать-прочитать-обновить-удалить». Когда чистый SQL лучше: аналитические запросы с многоэтажными агрегатами и оконными функциями (SQL здесь короче и прозрачнее ORM-конструкций), массовые загрузки, разовые скрипты. И в любом случае ORM не освобождает от знания SQL: под капотом он генерирует именно SQL, и когда запрос внезапно тормозит, разбираться придётся с ним (включи `create_engine(..., echo=True)` и посмотри, что реально уходит в базу).

## Нереляционные базы данных

Реляционная модель универсальна, но не единственна. Под конкретные профили нагрузки существуют специализированные — «NoSQL» — базы. Знать их стоит хотя бы обзорно, чтобы узнавать задачу «в лицо».

**Ключ-значение: [Redis](https://redis.io/).** Хранилище пар «ключ → значение», живущее в оперативной памяти: операции занимают микросекунды. Типичные роли — кеш (результат тяжёлого запроса или расчёта кладётся под ключ с временем жизни), очереди задач между процессами (на Redis работают брокеры для Celery), счётчики и pub/sub-уведомления. Персистентность на диск есть, но опциональна: Redis — про скорость, а не про главное хранилище истины.

**Документные: [MongoDB](https://www.mongodb.com/).** Единица хранения — документ, JSON-подобная вложенная структура; документы собираются в коллекции, и жёсткой схемы нет: соседние документы могут иметь разные поля. Удобно для разнородных метаданных, у которых структура меняется от записи к записи. Подвох в том, что «отсутствие схемы» означает лишь, что схема живёт не в базе, а в голове и в коде, — и проверять её теперь тоже тебе.

**Временные ряды: [InfluxDB](https://www.influxdata.com/).** Заточена под поток «метка времени → значение» с тегами: телеметрия установки — давление в вакуумной камере, токи магнитов, температуры, — приходящая с сотен датчиков каждую секунду годами. Это ровно то, что в ускорительной технике называется slow control. Такие базы умеют автоматически прореживать и удалять старые данные (retention policies), быстро агрегировать по окнам времени («среднее за каждую минуту последних суток») и штатно стыкуются с [Grafana](https://grafana.com/) для живых дашбордов мониторинга. Близкий родственник в мире PostgreSQL — расширение TimescaleDB.

**Колоночные: [ClickHouse](https://clickhouse.com/).** Хранит данные не по строкам, а по столбцам: значения одного столбца лежат рядом, отлично сжимаются, и запрос «среднее value по миллиарду строк» читает с диска только нужные столбцы. Результат — аналитика на миллиардах записей за секунды на обычном сервере, с привычным SQL-диалектом. Плата — слабость в точечных обновлениях и удалениях: колоночные базы рассчитаны на «дописывай и анализируй», а не на правки отдельных строк.

### Как выбирают: пример реальной системы

Обзор типов баз отвечает на вопрос «что бывает», но не на вопрос «что брать мне». Разберём это на живом примере — системе хранения данных ускорительного комплекса, где используются сразу три базы. Такой подход называется **полиглотным хранением** (polyglot persistence): под каждый профиль данных берётся то хранилище, которое к нему приспособлено.

В PostgreSQL уходит всё, что должно быть строгим: пользователи и их роли, конфигурация ускорителя и его элементов, метаданные экспериментов (что за эксперимент, когда, кто ответственный), расписание работы установки и журнал событий. Общее у этих данных одно: структура известна заранее, меняется редко, а целостность критична. Если запись эксперимента ссылается на несуществующего оператора, это ошибка, которую должна ловить база, а не код. Здесь и нужны схема, внешние ключи и ACID-транзакции.

В MongoDB складывают то, что разнородно: результаты измерений, данные пучка (траектории, размеры, интенсивность), временные ряды параметров, результаты моделирования и оптимизации. У этих данных нет и не может быть единой схемы, потому что каждый новый тип эксперимента приносит свой набор полей. Требовать миграции базы под каждую новую методику — верный способ добиться того, чтобы данные складывали мимо базы, в файлы на рабочем столе. Гибкая схема здесь не компромисс, а требование задачи.

Redis держит то, что живёт недолго: кеш частых запросов, текущие состояния устройств, сессии пользователей веб-интерфейса, очереди сообщений между компонентами. Ключевое слово здесь «текущее». Значение тока магнита *прямо сейчас* спрашивают сотни раз в секунду, и ходить за ним в дисковую базу бессмысленно. Потеря этих данных при перезапуске неприятна, но не катастрофична, ведь истина хранится в других двух базах.

Схема выбора, если свести её к одному вопросу на каждую базу:

| Вопрос | Ответ «да» → база |
|---|---|
| Структура известна заранее, а нарушение связей — ошибка? | PostgreSQL |
| Структура меняется от записи к записи? | MongoDB |
| Данные нужны очень быстро, а их потеря не смертельна? | Redis |

У полиглотного хранения есть и цена, о которой стоит знать заранее. Как только данные разъезжаются по трём базам, **исчезает транзакция, охватывающая их все**: невозможно одним атомарным действием записать эксперимент в PostgreSQL и его результаты в MongoDB. Согласованность приходится обеспечивать вручную — распределёнными транзакциями или компенсирующими действиями, откатывающими то, что уже успело записаться. Это заметная сложность, и она окупается только тогда, когда профили данных действительно разные.

Отсюда практический вывод для студенческого проекта: **начинай с одной базы**. Одна PostgreSQL закрывает потребности лабораторного сервиса на годы вперёд, а если хочется хранить документы — в ней есть тип `JSONB` с индексацией по полям внутри документа. Вторую базу заводят не потому, что «так делают в больших системах», а когда первая измеримо перестала справляться с конкретным профилем нагрузки.

## Pandas и базы данных

Мост между базой и анализом данных встроен в pandas: `read_sql` выполняет запрос и возвращает `DataFrame`, `to_sql` записывает `DataFrame` в таблицу:

```python
import pandas as pd
import sqlite3

con = sqlite3.connect("lab.db")

# фильтрация и агрегация выполняются в базе,
# в память попадает только готовая сводка
df = pd.read_sql(
    """
    SELECT r.energy_mev, AVG(m.value) AS mean_signal
    FROM measurements AS m
    JOIN runs AS r ON r.id = m.run_id
    WHERE m.channel = 'BPM01'
    GROUP BY r.id
    """,
    con,
)

# дальше — обычный pandas: график зависимости сигнала от энергии
df.plot.scatter(x="energy_mev", y="mean_signal")

# и обратно: результат анализа — в новую таблицу
df.to_sql("run_summary", con, if_exists="replace", index=False)
```

Ключевая мысль: тяжёлую фильтрацию и агрегацию отдавай базе (SQL с `WHERE` и `GROUP BY`), а в pandas загружай уже компактный результат — так и память, и время расходуются на порядки экономнее, чем «прочитать всё и фильтровать в DataFrame». Связка «SQL-запрос → DataFrame → график» — это и есть простейшее приложение для визуализации данных; про сами графики смотри главы про [обработку](python/numpy-and-pandas.md) и [визуализацию](python/visualization/practice.md) данных.

## С чего начать в своей лаборатории

Не нужно ждать большого проекта, чтобы применить всё это. Рецепт перехода от тысячи CSV к одной базе:

1. Заведи один файл `lab.db` и опиши схему: минимум — таблицы вида `experiments`, `runs`, `measurements` с первичными и внешними ключами и `NOT NULL` на важных полях. Схема — документация, которая ещё и проверяет сама себя.
2. Импортируй накопленные CSV одним скриптом:

    ```python
    from pathlib import Path
    import pandas as pd
    import sqlite3

    con = sqlite3.connect("lab.db")

    for csv_path in Path("data").glob("**/*.csv"):
        df = pd.read_csv(csv_path)
        df["source_file"] = str(csv_path)  # не теряем происхождение данных
        df.to_sql("measurements_raw", con, if_exists="append", index=False)
    ```

    Дальше «сырую» таблицу можно разложить по нормализованной схеме уже SQL-запросами.
3. Новые данные пиши сразу в базу: в скрипте сбора это `executemany` пачками точек и `commit` раз в несколько секунд, а не файл на каждый заход.
4. Включи `PRAGMA journal_mode=WAL` — в этом режиме SQLite позволяет читать базу (строить графики) параллельно с идущей записью.
5. Смотреть данные глазами удобно в DB Browser for SQLite, а резервная копия — это просто копия одного файла (`Connection.backup()` из Python делает её корректно даже во время работы).

Когда данными начнёт пользоваться вся группа с нескольких машин — перенесёшь схему в PostgreSQL; SQL и почти весь код при этом останутся прежними.
