# Git

Git — распределённая система контроля версий (version control system, VCS). Она запоминает историю изменений твоих файлов, умеет откатываться к любой прошлой версии и объединять работу нескольких человек над одним проектом. Для современной научной работы Git так же обязателен, как Python или LaTeX, — и в этой главе мы разберём его от базового цикла до команд спасения.

## Зачем физику контроль версий

История, знакомая каждому, кто писал курсовую с расчётами:

```text
processing.py
processing_new.py
processing_final.py
processing_final_v2.py
thesis_final_v2_FINAL(2).py
thesis_final_v2_FINAL(2)_fixed_mass.py
```

Через месяц нужно перегенерировать третий рисунок для статьи — и выясняется, что никто, включая тебя, не помнит, какой из этих файлов его строил. А «финальная» версия почему-то даёт другой хвост распределения, потому что по дороге ты поменял константу и забыл об этом.

Контроль версий закрывает сразу три проблемы:

*   **История вместо зоопарка файлов.** В проекте лежит один `processing.py`, а все его прошлые версии хранит Git. К любой можно вернуться, любые две — сравнить построчно.
*   **Воспроизводимость расчётов.** Каждое состояние проекта имеет уникальный идентификатор — хеш коммита. Достаточно записать его рядом с результатом, и через год ты дословно восстановишь код, которым посчитан график. «Рисунок 3 построен на коммите `a3f2c17`» — это и есть воспроизводимость.
*   **Совместная работа.** Когда над обработкой данных работают три человека из научной группы, Git аккуратно объединяет их изменения и показывает, кто, что и зачем поменял. Пересылать архивы `code_v7_new.zip` по почте больше не нужно.

Бонус: репозиторий на сервере — это ещё и резервная копия. Запушил вечером — и умерший диск ноутбука перестал быть научной катастрофой.

## Как устроен Git

Git гораздо проще понять, если знать три вещи о его устройстве. Дальше почти всё поведение команд выводится из этой картинки.

### Снимки, а не различия

Git хранит не «патчи к предыдущей версии», а **снимки** (snapshots): каждый коммит — это фотография всего проекта в момент фиксации плюс метаданные — автор, дата, сообщение и ссылка на родительский коммит. Неизменившиеся файлы при этом не копируются: Git ссылается на уже сохранённые объекты, поэтому репозиторий не разбухает.

Каждый объект адресуется хешем SHA-1 — те самые строки вида `a3f2c17b...` в `git log`. В командах достаточно первых 6–8 символов хеша.

### Три состояния

Файлы проекта живут в трёх зонах:

```text
рабочая директория  ──►  индекс (staging area)  ──►  репозиторий (.git)
  правишь файлы          git add: отбираешь           git commit:
                         изменения для коммита        фиксируешь снимок
```

*   **Рабочая директория (working directory)** — обычные файлы, которые ты редактируешь.
*   **Индекс (staging area)** — «предбанник» коммита: командой `git add` ты складываешь сюда те изменения, которые войдут в следующий снимок.
*   **Репозиторий** — база данных в скрытой папке `.git`, где навсегда сохраняются коммиты.

Промежуточный индекс кажется лишним, пока не понадобится закоммитить только часть правок: исправление формулы — отдельным коммитом, эксперименты с графиками — отдельным. Индекс существует именно для этого.

### Коммиты образуют граф

Каждый коммит ссылается на родителя, поэтому история — направленный ациклический граф (DAG). Пока работаешь один, он вырождается в цепочку; ветки заставляют его ветвиться, а слияния — снова сходиться:

```text
A ─── B ─── C ─────── F      main
       └── D ─── E ───┘      fft-filter
```

**Ветка** в Git — не копия проекта, а всего лишь подвижный указатель на коммит (буквально файл на 41 байт внутри `.git`). Поэтому ветки создаются мгновенно и бесплатно. **HEAD** — указатель на то место в графе, где ты сейчас находишься.

## Базовый цикл работы

### Разовая настройка

```bash
# представься: имя и почта попадут в каждый твой коммит
git config --global user.name "Lev Landau"
git config --global user.email "l.landau@g.nsu.ru"

# называть главную ветку main, как принято на GitHub
git config --global init.defaultBranch main
```

### Создать или склонировать репозиторий

```bash
# превратить текущую папку в репозиторий (появится скрытая папка .git)
git init

# или склонировать существующий проект с сервера
git clone https://github.com/nsu-phys/beam-dynamics.git
```

### Правки → индекс → коммит

Основная петля, в которой ты проведёшь 90% времени:

```bash
git status                  # что изменилось? (спрашивай постоянно)

git add processing.py       # добавить файл в индекс
git add plots/              # можно папку целиком
git add -p                  # интерактивно, по кускам — очень полезно

git commit -m "Учтена поправка на температуру датчика"

git status                  # убедиться, что всё зафиксировано
```

`git status` — самая недооценённая команда: она не только показывает состояние всех трёх зон, но и подсказывает, что делать дальше. Первое время вызывай её до и после каждой операции.

### Смотрим историю и различия

```bash
git log                     # полная история с авторами и датами
git log --oneline           # по строчке на коммит
git log --oneline --graph --all   # весь граф с ветками, псевдографикой

git diff                    # что поменялось, но ещё не добавлено в индекс
git diff --staged           # что уже в индексе и войдёт в коммит
git diff a3f2c17 HEAD -- processing.py  # как файл изменился со старого коммита

git show a3f2c17            # что именно сделал этот коммит
```

## .gitignore: что не должно попасть в репозиторий

Git отслеживает только то, что ты явно добавил, но `git status` будет назойливо перечислять всё подряд — от кешей Python до гигабайтных файлов с данными. Файл `.gitignore` в корне проекта говорит, что игнорировать. Для типичного научного проекта:

```gitignore
# байткод и кеши Python
__pycache__/
*.pyc
.ipynb_checkpoints/

# виртуальное окружение
.venv/

# данные измерений и результаты расчётов — им не место в git
data/
*.h5
*.root
*.npz

# тяжёлые артефакты: чекпойнты моделей, дампы
checkpoints/
*.ckpt

# мусор редакторов и ОС
.idea/
.vscode/
.DS_Store

# LaTeX-мусор
*.aux
*.synctex.gz
```

Правило простое: в репозитории живёт то, что ты пишешь руками (код, тексты, конфиги), и не живёт то, что измеряется или генерируется. Сам `.gitignore` коммитится в репозиторий — он общий для всей группы.

## Ветки

Ветка — это возможность экспериментировать, не трогая работающий код. Хочешь попробовать другой алгоритм фильтрации сигнала — не комментируй полфайла, а заведи ветку.

```bash
git branch                    # список веток, звёздочка — текущая
git switch -c fft-filter      # создать ветку и переключиться на неё
# ...правишь и коммитишь сколько угодно...
git switch main               # вернуться на main: файлы мгновенно
                              # станут такими, какими были там
```

`git switch` появился в Git 2.23; в старых руководствах то же самое делает `git checkout -b fft-filter` и `git checkout main` — команды взаимозаменяемы.

### Слияние

Когда эксперимент удался, влей ветку обратно:

```bash
git switch main
git merge fft-filter          # влить коммиты fft-filter в main
git branch -d fft-filter      # удалить ненужный больше указатель
```

Если `main` с момента ветвления не менялся, Git просто передвинет указатель вперёд (fast-forward). Если менялся — создаст коммит слияния с двумя родителями: так граф из картинки выше снова сходится в одну линию.

### Конфликты

Если в двух ветках изменили одни и те же строки, Git честно откажется выбирать за тебя и вставит в файл маркеры конфликта:

```text
<<<<<<< HEAD
dt = 1e-12  # шаг интегрирования для жёсткой задачи
=======
dt = 5e-12  # компромисс между точностью и скоростью
>>>>>>> fft-filter
```

Конфликт — это не поломка, а вопрос. Отредактируй файл: оставь правильный вариант (или скомбинируй оба), удали маркеры и заверши слияние:

```bash
git add integrator.py         # пометить конфликт разрешённым
git commit                    # завершить merge
git merge --abort             # передумал: откатить слияние целиком
```

Чем мельче коммиты и чем чаще ты сливаешь ветки, тем реже и безобиднее конфликты.

## Удалённые репозитории

Пока коммиты лежат только на твоём ноутбуке, нет ни резервной копии, ни совместной работы. Нужен удалённый репозиторий (remote) — копия проекта на сервере: GitHub, GitLab или институтский сервер.

```bash
git remote -v                  # список удалённых репозиториев
# после git clone там уже есть origin — адрес, откуда клонировал

# привязать локальный репозиторий к созданному на GitHub
git remote add origin git@github.com:username/beam-dynamics.git

git push -u origin main        # отправить ветку main на сервер;
                               # -u запоминает связку, дальше просто git push

git fetch                      # скачать чужие коммиты, НЕ трогая твои файлы
git pull                       # fetch + merge: скачать и влить в текущую ветку
git push                       # отправить свои коммиты
```

`git fetch` безопасен всегда: он лишь обновляет локальное знание о сервере, после него можно спокойно посмотреть `git log origin/main` и понять, что принесли коллеги. `git pull` — это `fetch` плюс немедленное слияние. Типовой ритм работы в группе: сел за работу — `git pull`, закончил — `git push`. Чем чаще синхронизируешься, тем меньше конфликтов.

### Fork + pull request

В чужой репозиторий — библиотеки вроде `numpy` или проекта соседней лаборатории — напрямую пушить нельзя. Стандартный механизм совместной работы выглядит так:

1.  **Fork** — кнопкой на GitHub делаешь личную копию репозитория в свой аккаунт.
2.  Клонируешь свой форк, создаёшь ветку, коммитишь исправление.
3.  Пушишь ветку в свой форк.
4.  Открываешь **pull request (PR)** — предложение «заберите мои коммиты к себе», с описанием и дифом.
5.  Владельцы читают код, пишут замечания (code review), ты дополняешь ветку новыми коммитами — PR обновляется автоматически.
6.  Когда всех всё устраивает, PR вливают в основной репозиторий.

Так живёт весь open source и заметная часть открытой науки: исправление даже одной строки в документации `scipy` проходит ровно этот путь. Внутри своей группы обычно пушат в общий репозиторий, но правки всё равно оформляют ветками и PR — ради ревью.

## Хорошие практики

**Атомарные коммиты.** Один коммит — одно логическое изменение. «Исправлена нормировка спектра» и «добавлен скрипт карты магнитного поля» — два коммита, а не один «изменил всякое». Атомарный коммит можно понять, откатить или перенести целиком; коммит-свалку — нет.

**Осмысленные сообщения.** Сообщение `fix` не отвечает ни на один вопрос: что починили, где и почему. Через полгода `git log` из `fix`, `fix2` и `wip` превращается в археологические раскопки. Пиши короткий заголовок (примерно до 50–72 символов) о сути изменения: не «поменял коэффициент», а «Увеличен шаг сетки: старый не влезал в память на кластере». Диф и так покажет, *что* поменялось; сообщение должно объяснять, *зачем*.

**Коммить рабочее состояние.** Старайся, чтобы проект в каждом коммите хотя бы запускался: тогда любая точка истории пригодна для поиска момента, где всё сломалось.

**Что НЕ хранить в git.** Git создан для текста и плохо переносит большие бинарники: каждый попавший в историю гигабайт останется в ней навсегда, и клонирование превратится в мучение. Сырые данные с установки, HDF5/ROOT-файлы, видео, обученные модели в репозиторий не кладут. Для версионирования больших файлов рядом с кодом существуют [Git LFS](https://git-lfs.com/) (в git хранятся лишь ссылки, содержимое — на отдельном сервере) и [DVC](https://dvc.org/) (Data Version Control: версионирует данные и пайплайны обработки, а сами файлы складывает в любое хранилище — хоть в облако, хоть на сетевой диск группы). И никогда не коммить пароли, токены и ключи: история репозитория публична и почти вечна.

## Если что-то пошло не так

Главное успокоительное: закоммиченное почти невозможно потерять — Git скорее сохранит лишнее, чем удалит нужное. Шпаргалка по типовым ситуациям:

| Ситуация | Команда |
|----------|---------|
| Испортил файл, хочу версию из последнего коммита | `git restore file.py` — незакоммиченные правки исчезнут! |
| Сделал `git add` лишнего | `git restore --staged file.py` — убрать из индекса, правки останутся |
| Опечатка в сообщении последнего коммита или забыл файл | `git commit --amend` (только пока не запушил) |
| Хочу «рассыпать» последний коммит обратно в правки | `git reset --soft HEAD~1` — коммит исчез, изменения остались в индексе |
| Выкинуть последний коммит **вместе с изменениями** | `git reset --hard HEAD~1` — **опасно**: правки будут уничтожены |
| Отменить уже запушенный коммит | `git revert a3f2c17` — новый коммит с обратным изменением, история не переписывается |
| Срочно нужна другая ветка, а правки не закончены | `git stash` — спрятать изменения; вернуть их — `git stash pop` |
| «Я всё сломал, коммиты пропали» | `git reflog` — журнал всех положений HEAD; найди нужный хеш и вернись: `git reset --hard <хеш>` |

Про `git reset --hard` запомни отдельно: это одна из немногих команд, молча уничтожающих незакоммиченную работу. Прежде чем её набирать, сделай `git status` и убедись, что терять нечего. И не переписывай историю (`reset`, `--amend`, `rebase`) в ветках, которые уже запушены и с которыми работают другие, — коллегам придётся разгребать разъехавшийся граф.
