# Классы

Функции и декораторы позволяют организовать поведение. Классы добавляют к нему состояние, и вокруг них выросла отдельная культура со своими правилами и своими способами всё испортить.

Класс связывает данные с операциями над ними. Вместо разрозненных переменных и функций, которые их обрабатывают, получается один объект, отвечающий за своё состояние. От Java и C++ Python отличается тем, что не прячет механику: ссылка на экземпляр передаётся методу явным первым аргументом `self`, а не появляется в теле сама собой.

ООП в Python не обязательно. Модуль с десятком функций — совершенно нормальная программа, и заворачивать её в класс только ради класса не нужно. Классы берут тогда, когда у данных появляется состояние, которое надо держать согласованным, или когда одну и ту же операцию нужно выполнять по-разному для разных видов объектов.

## Базовые понятия

### Определение класса

Начнём с минимального примера — счётчика. Метод `__init__` вызывается сразу после создания объекта и задаёт начальное состояние; всё, что записано в `self`, становится атрибутом конкретного экземпляра. Остальные методы этим состоянием пользуются:

```python
class Counter:
    """I count. That is all."""
    
    def __init__(self, initial=0):  # конструктор
        self.value = initial        # запись атрибута

    def increment(self):
        self.value += 1

    def get(self):
        return self.value          # чтение атрибута

# Использование
c = Counter(42)
c.increment()
print(c.get())  # 43
```

Название «конструктор» для `__init__` прижилось, хотя строго говоря оно неверно — объект к этому моменту уже создан. Создаёт его метод `__new__`, а `__init__` только заполняет готовую заготовку. Разница незаметна до того дня, когда понадобится унаследоваться от неизменяемого типа: у `int` или `tuple` менять уже нечего, и всю работу приходится делать в `__new__`.

### Специфика Python

Первым аргументом любого метода идёт `self` — экземпляр, на котором метод вызвали. Писать его приходится вручную, и это осознанное решение языка — явное лучше неявного.

Модификаторов доступа вроде `private` и `protected` в Python нет вовсе. Вместо них — соглашение об именовании, которое понимают все:

- `public_attribute` — часть публичного интерфейса, им можно пользоваться;
- `_internal_attribute` — внутренняя кухня, снаружи трогать не стоит;
- `__private_attribute` — то же самое, но с дополнительной защитой от случайного переопределения в подклассе.

Двойное подчёркивание — единственное, за чем стоит настоящий механизм. Интерпретатор переписывает такое имя, добавляя к нему имя класса: `__private` внутри класса `Counter` превращается в `_Counter__private`. Придумано это против коллизий, а не ради сокрытия данных. Если базовый класс и подкласс заведут по атрибуту `__cache`, они не столкнутся. А добраться до «приватного» атрибута всё равно можно, просто написав полное имя. Python рассчитывает на здравый смысл, не на запреты.

## Атрибуты классов и экземпляров

Атрибуты в Python бывают двух сортов, и путаница между ними — источник самых упорных багов в объектном коде.

### Атрибуты экземпляра

Атрибут экземпляра появляется от присваивания к `self` и принадлежит только этому объекту. Заводить его не обязательно в `__init__`, ведь присвоить атрибут можно и снаружи, уже готовому объекту:

```python
class Noop:
    def __init__(self):
        self.some_attribute = 42

noop = Noop()
noop.other_attribute = 100500  # динамическое добавление
```

Такая свобода — прямое следствие того, что атрибуты хранятся в обычном словаре. Гибкость приятная, но у неё есть оборотная сторона — опечатка в имени не вызовет ошибки. Строка `noop.som_attribute = 0` молча заведёт новый атрибут, старый останется прежним, и искать причину придётся долго.

### Атрибуты класса

Атрибут, объявленный в теле класса, принадлежит самому классу и **один на всех** его экземпляров. Годится это для того, что действительно общее: настроек, констант, реестра всех созданных объектов.

```python
class Counter:
    all_counters = []  # атрибут класса
    
    def __init__(self, initial=0):
        Counter.all_counters.append(self)
        self.value = initial

# Также можно добавлять атрибуты после определения
Counter.some_other_attribute = 42
```

Здесь же прячется ловушка, родственная изменяемым аргументам по умолчанию. Список `all_counters` создаётся один раз при чтении определения класса. Задумай ты его как «список у каждого счётчика свой» — все экземпляры делили бы один. Здесь общий список как раз и нужен, но, объявляя изменяемый атрибут класса, всякий раз спрашивай себя, точно ли он должен быть общим.

### Словарь атрибутов

Все атрибуты экземпляра лежат в обычном словаре `__dict__` — том самом, из-за которого возможно динамическое добавление. Никакой магии тут нет: в него можно заглянуть, посмотреть, что у объекта есть, и даже писать напрямую.

```python
noop = Noop()
noop.some_attribute = 42
print(noop.__dict__)  # {'some_attribute': 42}
print(vars(noop))     # альтернативный способ

# Динамическое управление атрибутами
noop.__dict__["dynamic_attr"] = "value"
```

Встроенная `vars()` делает то же самое, только читается лучше. С аргументом она отдаёт `__dict__` объекта, без аргументов — словарь текущего локального пространства имён. Прямая запись в `__dict__` нужна редко, но пригодится, когда имя атрибута вычисляется на ходу.

### `__slots__` для оптимизации

За гибкость приходится платить памятью. Словарь есть у каждого экземпляра, и на объекте с двумя полями он весит больше самих полей. Если объектов миллионы — скажем, по одному на событие в эксперименте, — плата становится ощутимой.

`__slots__` фиксирует набор атрибутов заранее. Интерпретатор тогда обходится без словаря и раскладывает значения по заранее отведённым ячейкам:

```python
class Noop:
    __slots__ = ["some_attribute"]  # фиксирует набор атрибутов
    
    def __init__(self):
        self.some_attribute = 42

# Экономит память, но запрещает добавление новых атрибутов
```

На объекте с парой полей это экономит около 40 % памяти: 96 байт на экземпляр без слотов против 56 со слотами. На скорость доступа рассчитывать не стоит, замер в главе про оптимизацию показывает, что разница уходит в шум. Взамен теряется динамика, ведь добавить атрибут, которого нет в списке, уже не получится, будет `AttributeError`. Заодно перестают работать слабые ссылки, если не вписать в слоты `__weakref__` явно. Начинать с `__slots__` не надо: это оптимизация на потом, когда профилировщик покажет, что память уходит сюда.

## Методы

### Связанные и несвязанные методы

Метод — функция, лежащая в атрибуте класса, и достать её можно двумя путями. Через класс получается обычная функция, которой экземпляр надо передать руками. Через экземпляр — **связанный** метод, где объект уже подставлен в `self`, так что передавать его не нужно.

```python
class SomeClass:
    def do_something(self):
        print("Doing something.")

# Несвязанный метод
method = SomeClass.do_something
instance = SomeClass()
method(instance)  # нужно явно передать экземпляр

# Связанный метод
bound_method = instance.do_something
bound_method()  # self уже привязан
```

Связанный метод — полноценный объект, который можно положить в переменную, передать в `map` или зарегистрировать как обработчик события; ссылку на свой экземпляр он носит с собой. В Python 2 обращение через класс давало особый тип, который проверял тип первого аргумента и не пропускал посторонние объекты; в Python 3 это просто функция, и приведённый выше код работает без оговорок.

## Свойства (Properties)

Рано или поздно оказывается, что публичный атрибут нужно защитить проверкой или вычислять на лету. В языках со строгой инкапсуляцией на этот случай пишут геттеры и сеттеры заранее — на всякий случай, для всех полей. В Python так не принято. Атрибут остаётся атрибутом, а когда понадобится, за ним прячут методы, не меняя ни строчки в коде, который им пользуется.

Делает это декоратор `@property`. Метод под ним вызывается при чтении, метод под `@имя.setter` — при записи, под `@имя.deleter` — при удалении. Снаружи всё выглядит как обычное присваивание:

```python
class BigDataModel:
    def __init__(self):
        self._params = []
    
    @property
    def params(self):
        return self._params
    
    @params.setter
    def params(self, new_params):
        assert all(p > 0 for p in new_params)
        self._params = new_params
    
    @params.deleter
    def params(self):
        del self._params

model = BigDataModel()
model.params = [0.1, 0.5, 0.4]
print(model.params)  # [0.1, 0.5, 0.4]
```

Присваивание `model.params = [...]` внешне ничем не отличается от записи в обычное поле, но проходит через `assert` в сеттере. В этом весь смысл свойств — интерфейс не меняется, а поведение за ним сколько угодно. Внутри они устроены на дескрипторах, до которых мы дойдём в конце главы.

## Наследование

### Базовое наследование

Подкласс получает всё, что есть у родителя, и добавляет своё. Если метода нет у подкласса, интерпретатор поднимается по цепочке наследования и ищет его выше — `OtherCounter` не определяет `__init__`, поэтому при создании работает родительский:

```python
class Counter:
    def __init__(self, initial=0):
        self.value = initial

class OtherCounter(Counter):
    def get(self):
        return self.value

oc = OtherCounter()  # вызывает Counter.__init__
print(oc.get())      # вызывает OtherCounter.get
```

Родителей, в отличие от многих языков, может быть несколько. Возможность мощная, но за неё приходится платить. Чем сложнее иерархия, тем труднее сказать, чей метод вызовется. Об этом — чуть ниже.

### Перегрузка методов и `super()`

Чаще подкласс не заменяет метод родителя целиком, а надстраивает над ним своё и передаёт управление наверх. Ссылку на родительскую реализацию даёт `super()`.

```python
class Counter:
    all_counters = []
    
    def __init__(self, initial=0):
        self.__class__.all_counters.append(self)
        self.value = initial

class OtherCounter(Counter):
    def __init__(self, initial=0):
        self.initial = initial
        super().__init__(initial)  # вызов родительского конструктора
```

Писать `Counter.__init__(self, initial)` вместо `super()` — распространённая ошибка. Разница вылезет при множественном наследовании. `super()` идёт не «к родителю», а к следующему классу в порядке разрешения методов, а тот зависит от того, как класс использовали дальше. Явное имя родителя эту цепочку рвёт.

### Множественное наследование

Порядок, в котором интерпретатор перебирает классы в поисках метода, называется MRO — method resolution order. Посмотреть его можно у любого класса:

```python
class A:
    def f(self):
        print("A.f")

class B:
    def f(self):
        print("B.f")

class C(A, B):
    pass

print(C.mro())  # порядок разрешения методов
C().f()         # A.f (согласно MRO)
```

Здесь `f` находится в `A`, потому что `A` стоит первым в списке родителей. Считает этот порядок алгоритм C3, заимствованный из языка Dylan, и он даёт три гарантии: подкласс всегда идёт раньше своих родителей; порядок, в котором родители перечислены, сохраняется; каждый класс иерархии встречается в списке ровно один раз. Если требования противоречат друг другу, Python откажется создавать класс — лучше ошибка при импорте, чем непредсказуемый вызов в работе.

### Классы-примеси

Примесь (mixin) — класс, который не задуман для самостоятельного использования. Сущности он не описывает — только добавляет к чужому поведению одну черту: блокировку, журналирование, кеширование. Ниже примесь оборачивает операции счётчика в захват блокировки:

```python
class ThreadSafeMixin:
    def get_lock(self):
        # возвращает объект блокировки
        pass
    
    def increment(self):
        with self.get_lock():
            super().increment()
    
    def get(self):
        with self.get_lock():
            return super().get()

class ThreadSafeCounter(ThreadSafeMixin, Counter):
    pass
```

Работает всё это благодаря `super()` и порядку разрешения методов. Примесь стоит **перед** `Counter` в списке родителей, поэтому её `increment` перехватывает вызов первым, а `super().increment()` внутри уходит дальше по цепочке — в настоящий счётчик. Заметь: `ThreadSafeMixin` не наследуется от `Counter` и вообще ничего о нём не знает. Следующий класс в MRO определяется в момент, когда собирают `ThreadSafeCounter`. Ровно так устроена половина Django.

## Декораторы классов

Декоратор из прошлой главы применяется не только к функциям. Класс — тоже объект, и его точно так же можно пропустить через функцию, которая вернёт что-то другое. Классический пример — синглтон: подменяем класс функцией, которая при первом вызове создаёт экземпляр, а дальше отдаёт тот же самый.

```python
def singleton(cls):
    instance = None
    
    @functools.wraps(cls)
    def inner(*args, **kwargs):
        nonlocal instance
        if instance is None:
            instance = cls(*args, **kwargs)
        return instance
    
    return inner

@singleton
class Noop:
    "I do nothing at all."

print(id(Noop()) == id(Noop()))  # True
```

Декораторы классов появились в Python 3.0 и заметно потеснили метаклассы. То, ради чего раньше приходилось лезть в метапрограммирование, теперь чаще делают одной функцией. Самый известный пример — `@dataclass`, который дописывает классу `__init__`, `__repr__` и `__eq__` по объявленным полям.

## Магические методы

Магические (или дандер-) методы — те, чьи имена окружены двойными подчёркиваниями. Напрямую их не вызывают — за каждым стоит синтаксическая конструкция или встроенная функция. Определив нужный метод, ты учишь свой объект вести себя как встроенный — складываться, сравниваться, печататься, попадать в множество.

### Управление атрибутами

Первая группа перехватывает работу с атрибутами. `__getattr__` вызывается **только тогда, когда атрибут не нашёлся** обычным путём. Это точка, где можно подставить значение вместо `AttributeError`. `__setattr__` и `__delattr__`, наоборот, перехватывают вообще любую запись и любое удаление:

```python
class Noop:
    def __getattr__(self, name):
        # Вызывается при доступе к несуществующему атрибуту
        return f"Attribute {name} doesn't exist"
    
    def __setattr__(self, name, value):
        # Вызывается при установке любого атрибута
        super().__setattr__(name, value)
    
    def __delattr__(self, name):
        # Вызывается при удалении атрибута
        super().__delattr__(name)

noop = Noop()
print(noop.non_existent)  # "Attribute non_existent doesn't exist"
```

Обращение к `super()` внутри `__setattr__` обязательно. Напишешь `self.name = value` — метод вызовет сам себя, и программа уйдёт в бесконечную рекурсию. По этой же причине не трогай `__getattribute__`, родственный метод, который перехватывает доступ ко **всем** атрибутам, а не только к отсутствующим. Ошибиться в нём проще простого, а падает он неочевидно.

### Операторы сравнения

Вторая группа отвечает за сравнение. Их шесть, но писать все шесть незачем — декоратор `@functools.total_ordering` достроит остальные по `__eq__` и любому одному из методов упорядочивания.

```python
import functools

@functools.total_ordering
class Counter:
    def __init__(self, value):
        self.value = value
    
    def __eq__(self, other):
        return self.value == other.value
    
    def __lt__(self, other):
        return self.value < other.value

c1, c2 = Counter(1), Counter(2)
print(c1 < c2)   # True
print(c1 >= c2)  # False (автоматически из __lt__ и __eq__)
```

Есть подвох. Определив `__eq__`, ты неявно отключаешь хеширование: объект перестаёт быть хешируемым и не лезет ни в множество, ни в ключи словаря. Причина та же, что у изменяемых коллекций, — равные объекты обязаны иметь равные хеши, а угадывать за тебя Python не берётся. Если объект должен оставаться хешируемым, `__hash__` придётся написать явно.

### Строковое представление

Третья группа отвечает на вопрос, как объект выглядит в виде текста. Различие между двумя основными методами существенное. `__repr__` пишут для программиста — он должен быть однозначным и в идеале выглядеть как выражение, которым объект можно воссоздать. `__str__` пишут для человека, который смотрит на вывод программы. Если `__str__` не определён, Python возьмёт `__repr__`, поэтому начинают всегда с него.

```python
class Counter:
    def __init__(self, initial=0):
        self.value = initial
    
    def __repr__(self):
        return f"Counter({self.value})"
    
    def __str__(self):
        return f"Counted to {self.value}"
    
    def __format__(self, format_spec):
        return self.value.__format__(format_spec)

c = Counter(42)
print(repr(c))           # Counter(42)
print(str(c))            # Counted to 42
print(f"{c:b}")          # 101010 (бинарное представление)
```

Третий метод, `__format__`, отвечает за подстановку в f-строку со спецификатором. Здесь он просто передаёт спецификатор дальше в целое число, поэтому `{c:b}` печатает значение счётчика в двоичном виде.

Совет из практики. Пиши `__repr__` у любого класса, который проживёт дольше пары строк. Отладка объектов, печатающихся как `<__main__.Counter object at 0x7f3a…>`, — занятие безрадостное.

### Другие полезные магические методы

Остальные полезно знать хотя бы по названиям. `__call__` делает экземпляр вызываемым — на этом строят декораторы в виде классов и объекты, которые хранят настройки между вызовами. `__bool__` задаёт, что объект значит в условии `if`; без него Python спрашивает `__len__`, и объект нулевой длины оказывается ложным, а если нет и его — объект всегда истинен. `__hash__` определяет, как объект попадает в множества и словари.

```python
class Identity:
    def __call__(self, x):
        # Позволяет вызывать экземпляры как функции
        return x
    
    def __bool__(self):
        # Определяет поведение в булевом контексте
        return True
    
    def __hash__(self):
        # Используется для хеширования в словарях и множествах
        return hash(id(self))

identity = Identity()
print(identity(42))  # 42
```

На `__call__` стоит задержаться. Он стирает границу между функцией и объектом — `identity(42)` выглядит как обычный вызов, хотя слева стоит экземпляр класса. Поэтому в Python «вызываемый объект» важнее, чем «функция»: всюду, где документация просит передать функцию, годится любой объект с `__call__`.

## Дескрипторы

Свойства решают задачу для одного атрибута одного класса. Но проверка «значение не отрицательно» нужна десяткам полей в разных классах, и переписывать под каждое пару методов утомительно. Дескриптор — способ вынести логику доступа в отдельный класс и переиспользовать её.

### Базовый дескриптор

Дескриптор — класс, у которого определены `__get__`, `__set__` или `__delete__`. Экземпляр такого класса кладут в **атрибут класса**, и с этого момента любое обращение к атрибуту идёт через него:

```python
class NonNegative:
    def __get__(self, instance, owner):
        # magically_get_value
        pass
    
    def __set__(self, instance, value):
        assert value >= 0, "non-negative value required"
        # magically_set_value
    
    def __delete__(self, instance):
        # magically_delete_value
        pass

class VerySafe:
    x = NonNegative()
    y = NonNegative()

very_safe = VerySafe()
very_safe.x = 42      # OK
very_safe.x = -42     # AssertionError
```

Проверка написана один раз, а полей с ней уже два, и добавить третье стоит одной строки. Ради этого дескрипторы и заводят.

Механизм этот куда более общий, чем кажется. Через дескрипторы в Python реализовано почти всё, что связано с атрибутами: и `@property`, и `@staticmethod`, и `@classmethod`, и сама привязка методов к экземпляру. Знать протокол напрямую нужно нечасто, но, зная его, перестаёшь удивляться, почему функция, лежащая в классе, при обращении через экземпляр вдруг оказывается связанным методом.

### Хранение данных в дескрипторах

Остаётся вопрос, где дескриптору хранить значение. Хранить его в себе нельзя — дескриптор один на весь класс, а экземпляров много, и все они затирали бы друг друга. Правильное место — словарь самого экземпляра:

```python
class Proxy:
    def __init__(self, label):
        self.label = label
    
    def __get__(self, instance, owner):
        return instance.__dict__[self.label]
    
    def __set__(self, instance, value):
        instance.__dict__[self.label] = value
    
    def __delete__(self, instance):
        del instance.__dict__[self.label]

class Something:
    attr = Proxy("attr")

some = Something()
some.attr = 42
print(some.attr)  # 42
```

У каждого экземпляра значение своё, и живёт оно столько же, сколько экземпляр. Второй возможный вариант — общий словарь «экземпляр → значение» внутри дескриптора — хуже по двум причинам. Он требует, чтобы объекты были хешируемыми, и держит на них ссылки, не давая сборщику мусора их убрать.

Единственное неудобство здесь — имя поля приходится дублировать в `Proxy("attr")`. С Python 3.6 от этого избавляет метод `__set_name__` — интерпретатор сам вызывает его при создании класса и сообщает дескриптору, под каким именем тот записан.

### Встроенные дескрипторы

Лучший способ убедиться, что дескрипторы лежат в основании языка, — написать знакомые декораторы самому. Все три ниже — сокращённые, но по сути верные варианты того, что есть в интерпретаторе:

```python
# @property реализован через дескрипторы
class property:
    def __init__(self, get=None, set=None, delete=None):
        self._get = get
        self._set = set
        self._delete = delete
    
    def __get__(self, instance, owner):
        if self._get is None:
            raise AttributeError("unreadable attribute")
        return self._get(instance)

# @staticmethod и @classmethod тоже используют дескрипторы
class staticmethod:
    def __init__(self, method):
        self.__method = method
    
    def __get__(self, instance, owner):
        return self.__method

class classmethod:
    def __init__(self, method):
        self.__method = method
    
    def __get__(self, instance, owner):
        if owner is None:
            owner = type(instance)
        return self.__method.__get__(owner, type(owner))
```

Вся разница между `@staticmethod` и `@classmethod` умещается в две строчки их `__get__`. Статический метод просто отдаёт исходную функцию — никакой привязки не происходит, поэтому и `self` в нём нет. Метод класса привязывает функцию к классу, и в первый аргумент приходит сам класс. Так же, только к экземпляру, привязываются и обычные методы.

## Метаклассы

Раз класс — объект, у него тоже есть тип. Тип обычного класса — `type`, а метакласс — просто класс, унаследованный от `type`, экземплярами которого оказываются другие классы. Если обычный класс описывает, как устроены его объекты, то метакласс описывает, как устроены классы.

Нужны они редко — почти всё, ради чего раньше писали метаклассы, сегодня делается декоратором класса или методом `__init_subclass__`. Но знать о них надо: на метаклассах построены ORM и системы валидации данных, где поля класса объявляются декларативно.

### Базовый метакласс

Метакласс перехватывает создание класса. Метод `__new__` получает всё, из чего класс будет собран: имя, кортеж родителей и словарь с телом класса, и может это изменить, прежде чем класс появится на свет:

```python
class Meta(type):
    def __new__(metacls, name, bases, clsdict):
        print(f"Creating class {name}")
        cls = super().__new__(metacls, name, bases, clsdict)
        return cls
    
    @classmethod
    def __prepare__(metacls, name, bases):
        # Может вернуть нестандартный mapping для clsdict
        return OrderedDict()

class Something(metaclass=Meta):
    attr = "foo"
    other_attr = "bar"
```

Второй метод, `__prepare__`, выбирает, в чём копить тело класса, пока оно читается. Возвращённый им словарь и попадёт потом в `clsdict`, а значит, подсунув сюда свой тип отображения, можно запомнить порядок объявления атрибутов или проверять каждое присваивание на месте. Так и работают ORM, где порядок полей определяет порядок колонок в таблице.

### Создание классов через `type()`

Всё сказанное станет очевиднее, если создать класс вручную. Оператор `class` — не более чем удобная запись для вызова `type` с тремя аргументами: именем, родителями и словарём атрибутов.

```python
# Эквивалентно class Something: attr = 42
name, bases, attrs = "Something", (), {"attr": 42}
Something = type(name, bases, attrs)

some = Something()
print(some.attr)  # 42
```

Пожалуй, это лучшая иллюстрация того, насколько Python последователен. Даже такая фундаментальная конструкция, как объявление класса, сводится к обычному вызову функции.

## Модуль abc для абстрактных базовых классов

Абстрактный базовый класс описывает интерфейс, не реализуя его, — перечисляет методы, которые обязан определить наследник. Пока хоть один из них не реализован, класс считается абстрактным, и создать его экземпляр не выйдет — ошибка возникнет сразу, а не при первом обращении к недостающему методу.

```python
import abc

class Iterable(metaclass=abc.ABCMeta):
    @abc.abstractmethod
    def __iter__(self):
        pass

class Something(Iterable):
    pass

# Something()  # TypeError: Can't instantiate abstract class
```

Отдельной конструкции `interface`, как в Java, в Python нет, и не нужно — интерфейсы описываются обычными классами, только с метаклассом `ABCMeta`. Проще всего наследоваться от готового `abc.ABC`, он делает то же самое.

## Модуль collections.abc

Абстрактные классы для самих коллекций уже написаны и лежат в `collections.abc` — это те же `Container`, `Iterable`, `Sequence` и `Mapping`, о которых шла речь в главе про коллекции. Пользы от наследования две. Интерпретатор проверит, что ты реализовал всё обязательное, и за это бесплатно добавит остальное: реализовав у `MutableMapping` пять методов, ты получишь готовые `get`, `pop`, `setdefault`, `update`, `items`, `keys` и `values`.

```python
from collections.abc import MutableMapping

class MemorizingDict(MutableMapping):
    def __init__(self, *args, **kwargs):
        self._data = dict(*args, **kwargs)
        self._history = deque(maxlen=10)
    
    def __getitem__(self, key):
        return self._data[key]
    
    def __setitem__(self, key, value):
        self._history.append(key)
        self._data[key] = value
    
    def __delitem__(self, key):
        del self._data[key]
    
    def __iter__(self):
        return iter(self._data)
    
    def __len__(self):
        return len(self._data)
    
    def get_history(self):
        return self._history
```

Написано пять обязательных методов и один свой, а на выходе — полноценный словарь, который к тому же помнит десять последних записанных ключей. Он пройдёт `isinstance(d, MutableMapping)` и будет принят любой библиотекой, которая ждёт отображение. Собирать такое вручную, реализуя весь словарный интерфейс с нуля, пришлось бы вчетверо дольше.

## Заключение

Классы дают богатый инструментарий, и большая часть его тебе не понадобится. Метаклассы за всю студенческую практику, скорее всего, не встретятся ни разу, дескрипторы — от силы однажды. Разбирают их для общего понимания. Почти всё, что кажется в Python магией, оказывается одним из этих механизмов.

В повседневной работе хватает малого:

- Класс нужен там, где есть состояние, которое надо держать согласованным. Если состояния нет, хватит функции.
- Атрибут пусть остаётся атрибутом; свойство добавляют тогда, когда за ним понадобилась логика.
- `__repr__` пиши сразу — он окупится на первой же отладке.
- В переопределённых методах вызывай родителя через `super()`, а не по имени класса.
- Прежде чем строить иерархию наследования, подумай, не решается ли задача композицией: объект, который **содержит** другой объект, почти всегда проще того, который от него наследуется.

И последнее. Объектно-ориентированность в Python — инструмент, а не обязанность. Язык одинаково хорошо принимает и модуль из десяти функций, и продуманную иерархию классов; выбирай по задаче, а привычка тут плохой советчик.
