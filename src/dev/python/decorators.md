# Декораторы и модуль `functools`

Одна и та же обвязка кочует из функции в функцию: замерить время, записать вызов в журнал, проверить аргументы, закешировать результат. Логика везде своя, обвязка одна, а копировать её приходится в каждую. Декораторы решают ровно эту задачу — навесить поведение на функцию, не трогая её тело.

Разберём, как декоратор устроен изнутри, как передать ему аргументы, какие ловушки при этом возникают, и посмотрим на готовые декораторы из модуля `functools`.

## Синтаксис декораторов

Декоратор — функция, которая принимает другую функцию и возвращает новую функцию (или любой другой объект). Значок `@` перед определением — «синтаксический сахар». Возможностей он не добавляет, зато ставит имя декоратора на видное место, прямо перед функцией.

```python
@decorator
def foo(x):
    return 42
```

Эквивалентно:

```python
def foo(x):
    return 42

foo = decorator(foo)
```

Таким образом, после применения декоратора имя `foo` будет ссылаться на результат вызова `decorator(foo)`.

## «Теория» декораторов: создание простого декоратора

Разберём устройство на декораторе `trace`, который печатает каждый вызов функции. Внутри происходит три вещи. Декоратор получает исходную функцию в `func` и определяет новую, `inner`; та принимает аргументы в самом общем виде `*args, **kwargs`, чтобы подойти к любой функции; наконец, `inner` делает своё дело и передаёт управление оригиналу, не забыв вернуть его результат. Наружу декоратор отдаёт `inner`:

```python
def trace(func):
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs)
        return func(*args, **kwargs)
    return inner
```

Заметь: `func` остаётся доступной внутри `inner` после того, как `trace` завершилась. Это замыкание из главы про функции.

Применим его:

```python
@trace
def identity(x):
    "I do nothing useful."
    return x

identity(42)  # Вывод: identity (42,) {} → 42
```

### Проблема атрибутов функции

У этой конструкции есть неприятный побочный эффект. После декорирования имя `identity` ссылается уже не на исходную функцию, а на `inner` — со всеми её атрибутами. Документация, имя, сигнатура — всё теперь от обёртки, и человек, читающий `help`, не увидит ничего полезного:

```python
identity.__name__  # 'inner'
help(identity)     # Справка о inner, а не identity
```

Кроме неудобства при отладке, это ломает всё, что опирается на имена функций, — от документации, собираемой автоматически, до фреймворков, которые ищут обработчики по имени.

### Решение: `functools.wraps`

Спасает одна строка. `functools.wraps` — декоратор, который копирует в обёртку метаданные оригинала (`__name__`, `__doc__`, `__module__`) и заодно кладёт ссылку на исходную функцию в `__wrapped__`. Пишешь свой декоратор — ставь `@functools.wraps(func)` над внутренней функцией. Всегда.

```python
import functools

def trace(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs)
        return func(*args, **kwargs)
    return inner
```

Теперь `identity.__name__` и `help(identity)` работают корректно.

## Декораторы с аргументами

Иногда декоратор нужно настроить — скажем, указать `trace`, куда писать. Тут появляется третий уровень вложенности, и он сбивает с толку всех подряд. А дело вот в чём. Запись `@trace(sys.stderr)` — это два действия, а не одно: сначала вызывается `trace(sys.stderr)`, и только её результат применяется к функции как декоратор. Значит, `trace` возвращает декоратор, а тот уже — обёртку:

```python
def trace(handle):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            print(func.__name__, args, kwargs, file=handle)
            return func(*args, **kwargs)
        return inner
    return decorator

@trace(sys.stderr)
def identity(x):
    return x
```

Эквивалентно:

```python
decorator = trace(sys.stderr)
identity = decorator(identity)
```

## Декораторы с опциональными аргументами

Два предыдущих декоратора несовместимы по способу применения. Один пишется как `@trace`, другой — только как `@trace(...)`, а хочется, чтобы работали оба. Приём стандартный — декоратор смотрит, что ему передали. Пришла `func` — его применили без скобок, надо сразу возвращать обёртку. `func` пусто — вызвали со скобками, и вернуть надо декоратор, который отработает следующим шагом:

```python
def trace(func=None, *, handle=sys.stdout):
    if func is None:
        return lambda func: trace(func, handle=handle)

    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, args, kwargs, file=handle)
        return func(*args, **kwargs)
    return inner
```

Использование:

```python
@trace
def foo(): ...

@trace(handle=sys.stderr)
def bar(): ...
```

Звёздочка в объявлении стоит по делу. Без неё `@trace(sys.stderr)` попало бы в `func`, и декоратор принял бы файловый объект за декорируемую функцию. Требование передавать настройки только по имени убирает неоднозначность начисто.

## Практика: полезные декораторы

### @timethis — замер времени выполнения

Первый практический пример — декоратор для замера времени. Он выполняет функцию `n_iter` раз и печатает **лучший** результат, а не средний. Среднее портит любая случайная помеха вроде переключения задач операционной системой, а минимум показывает, на что код способен в спокойной обстановке. По той же причине в стандартной библиотеке есть `timeit.repeat`: он возвращает список результатов, из которого берут `min`. А вот сам `timeit.timeit` минимума не считает — он отдаёт суммарное время всех запусков, и делить его на их число приходится самому.

```python
import time

def timethis(func=None, *, n_iter=100):
    if func is None:
        return lambda func: timethis(func, n_iter=n_iter)

    @functools.wraps(func)
    def inner(*args, **kwargs):
        print(func.__name__, end=" ... ")
        acc = float("inf")
        for i in range(n_iter):
            tick = time.perf_counter()
            result = func(*args, **kwargs)
            acc = min(acc, time.perf_counter() - tick)
        print(acc)
        return result
    return inner
```

### @once — выполнить не более одного раза

Бывает работа, которую надо сделать ровно один раз, сколько бы раз функцию ни звали: прочитать конфигурацию, установить соединение, разобрать большой справочник. `@once` запоминает результат первого вызова и дальше отдаёт его же.

Хранить состояние декоратор мог бы в замыкании, но здесь оно положено прямо на `inner` — помнишь, функция тоже объект и допускает произвольные атрибуты. Плюс такого решения в том, что флаг видно снаружи — `some_func.called` покажет, звали функцию или нет.

```python
def once(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        if not inner.called:
            inner.result = func(*args, **kwargs)
            inner.called = True
        return inner.result
    inner.called = False
    return inner
```

### @memoized — мемоизация

Следующий шаг — запоминать результат отдельно для каждого набора аргументов. Это и называется мемоизацией. Функция ведёт словарь «аргументы → результат» и повторно ничего не считает. Ключом служит кортеж из позиционных аргументов и отсортированных именованных; сортировка нужна, чтобы `f(a=1, b=2)` и `f(b=2, a=1)` попали в одну ячейку.

```python
def memoized(func):
    cache = {}
    @functools.wraps(func)
    def inner(*args, **kwargs):
        key = args + tuple(sorted(kwargs.items()))
        if key not in cache:
            cache[key] = func(*args, **kwargs)
        return cache[key]
    return inner
```

**Ограничение:** ключом словаря может быть только хешируемый объект, поэтому такая мемоизация сломается, если в функцию передать список, словарь или множество. Для универсального решения аргументы сериализуют (например, через `pickle`) — но тогда теряется скорость, ради которой всё и затевалось. На практике проще применять мемоизацию только к функциям с простыми аргументами и брать готовый `functools.lru_cache`, о котором ниже.

### @deprecated — пометить функцию как устаревшую

Когда функцию собираются убрать, её сначала помечают устаревшей: она ещё работает, но при каждом вызове напоминает о себе предупреждением. Это даёт пользователям библиотеки время переписать свой код.

```python
import warnings

def deprecated(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        warnings.warn(
            f"{func.__name__} устарела и будет удалена",
            category=DeprecationWarning,
            stacklevel=2,      # показать строку вызывающего кода, а не эту
        )
        return func(*args, **kwargs)
    return inner
```

Здесь важна деталь, на которой легко ошибиться. Предупреждение должно выдаваться **при вызове** функции, поэтому `warnings.warn` стоит внутри `inner`. Если вынести его в тело декоратора — соблазн велик, ведь так короче, — предупреждение сработает один раз при импорте модуля и больше никогда. Пользователь получит сообщение об устаревшей функции, которую, возможно, даже не вызывал, а при настоящих вызовах не услышит ничего.

Аргумент `stacklevel=2` переводит указатель со строки внутри декоратора на ту, где функцию вызвали. Без него предупреждение бесполезно: место вызова по нему не найти.

Учти, что `DeprecationWarning` по умолчанию скрыт везде, кроме `__main__`. Чтобы увидеть его в своём коде, запусти интерпретатор с ключом `-W default` или добавь `warnings.simplefilter("always", DeprecationWarning)`.

## Контрактное программирование с декораторами

Контрактное программирование — идея описывать в самой функции, что она требует от входа и что обещает на выходе. Декораторы для этого подходят идеально — проверка стоит рядом с объявлением, её видно с первого взгляда, а тело функции остаётся чистым. Напишем два, `@pre` для предусловия и `@post` для постусловия. Оба принимают проверяющую функцию и текст сообщения, а отличаются только тем, к чему применяется проверка: `pre` смотрит на аргументы до вызова, `post` — на результат после.

```python
def pre(cond, message):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            assert cond(*args, **kwargs), message
            return func(*args, **kwargs)
        return inner
    return decorator

def post(cond, message):
    def decorator(func):
        @functools.wraps(func)
        def inner(*args, **kwargs):
            result = func(*args, **kwargs)
            assert cond(result), message
            return result
        return inner
    return decorator
```

Использование:

```python
@pre(lambda x: 0 < x < 1, "argument must be a fraction")
@post(lambda r: r < 0, "log of a fraction must be negative")
def log_fraction(x):
    return math.log(x)
```

Одна оговорка про `assert`. Интерпретатор, запущенный с ключом `-O`, выбрасывает такие проверки из кода целиком. Для контрактов внутри своей программы это как раз то, что нужно: в отладке проверяем, в бою не платим. А вот данные, пришедшие извне, `assert`-ом проверять нельзя — там нужен явный `raise`.

## Цепочки декораторов

Декораторов на одной функции может быть несколько, и порядок их важен.

```python
@deco1
@deco2
def foo(): ...
```

Читаются они снизу вверх: ближайший к `def` применяется первым, и получается вот что:

```python
foo = deco1(deco2(foo))
```

Значит, при вызове управление идёт в обратную сторону — сначала во внешний `deco1`, потом во внутренний `deco2` и только потом в саму функцию. Отсюда и порядок на практике. `@functools.lru_cache` ставят выше проверок аргументов, чтобы попадание в кеш не тратило время на валидацию, а `@timethis` — ниже, чтобы он мерил саму функцию, а не работу соседних декораторов.

## Модуль `functools`

### `lru_cache` — мемоизация с ограничением

Готовая и куда более качественная замена нашему `@memoized`. От самописного варианта её отличают две вещи. Кеш ограничен по размеру, и при переполнении из него вытесняется то, к чему дольше всего не обращались (это и означает LRU — least recently used). Благодаря ограничению кеш не съедает всю память в долго живущей программе.

```python
@functools.lru_cache(maxsize=128)
def expensive_func(x):
    return x * x
```

Значение `maxsize=None` снимает ограничение — так делают только для функций с заведомо небольшим числом различных аргументов. Метод `cache_info()` покажет, сколько было попаданий и промахов. Если попаданий почти нет, кеш только мешает. Ограничение то же, что у самописного варианта, — аргументы должны быть хешируемыми.

### `partial` — частичное применение

`partial` закрепляет часть аргументов функции и возвращает новую, которой эти аргументы передавать уже не нужно. Это аккуратная замена лямбде там, где надо «донастроить» готовую функцию перед передачей её куда-то дальше:

```python
f = functools.partial(sorted, key=lambda x: x[1])
f([('a', 4), ('b', 2)])  # [('b', 2), ('a', 4)]
```

### `singledispatch` — обобщённые функции

Когда функция должна вести себя по-разному для разных типов, напрашивается лестница из `isinstance`. Она работает, но её приходится править всякий раз, когда появляется новый тип. `singledispatch` переворачивает эту схему: базовая функция объявляется один раз, а реализации для конкретных типов регистрируются отдельно — в том числе из другого модуля, который про базовую функцию узнал позже:

```python
@functools.singledispatch
def pack(obj):
    raise TypeError(f"Unsupported type: {type(obj)}")

@pack.register(int)
def _(obj):
    return b"I" + hex(obj).encode("ascii")

@pack.register(list)
def _(obj):
    return b"L" + b",".join(map(pack, obj))
```

Выбор реализации идёт по типу **первого** аргумента — отсюда «single» в названии. Имя `_` у зарегистрированных функций взято не просто так, ведь обращаться к ним напрямую не нужно, вызывать всегда будут базовую `pack`.

### `reduce` — свёртка последовательности

`reduce` сворачивает последовательность в одно значение: берёт первые два элемента, применяет к ним функцию, к результату применяет её же со следующим элементом и так до конца.

```python
functools.reduce(lambda acc, x: acc * x, [1, 2, 3, 4])  # 24
```

В функциональных языках это базовая конструкция, а в Python её используют редко — явный цикл читается лучше, да и для самых частых свёрток есть готовые `sum`, `min`, `max` и `any`.

## Заключение

Декораторы — не просто «синтаксический сахар», а рабочий инструмент, который позволяет добавить функции поведение, не трогая её тело, и тем самым не размазывать одну и ту же обвязку по всей программе.

Что из этой главы понадобится на практике:

- Свой декоратор всегда начинается с `@functools.wraps(func)` над внутренней функцией.
- Декоратор с аргументами — функция, возвращающая декоратор; уровней вложенности становится три.
- Настройки декоратора делай ключевыми аргументами, иначе `@deco` и `@deco(...)` не отличить.
- В цепочке декораторов ближайший к `def` применяется первым, а при вызове срабатывает последним.
- Прежде чем писать своё, загляни в `functools`: `lru_cache`, `partial`, `singledispatch` и `total_ordering` закрывают большую часть нужд.
