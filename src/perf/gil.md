# Многопоточность и GIL

Профилировщик показал, где программа проводит время, а векторизация и JIT-компиляция это время сократили. Следующий очевидный ход состоит в том, чтобы задействовать все ядра процессора, а не одно. С Python здесь всё непросто, и разбираться придётся с самого начала: что такое процесс, что такое поток и почему в Python второе не даёт того, чего от него ждут.

## Необходимый минимум: процессы и потоки

### Процесс

**Процессом** называют запущенную программу. Операционная система выделяет каждому процессу собственное, изолированное от остальных состояние:

* виртуальное адресное пространство, то есть своя память, в которую другие процессы заглянуть не могут;
* указатель на исполняемую инструкцию;
* стек вызовов;
* системные ресурсы, например открытые файловые дескрипторы.

Если нужно выполнять несколько задач одновременно, их можно раздать разным процессам. Изоляция здесь и достоинство, и недостаток. Процессы не мешают друг другу, но и обмениваться данными им сложно: общей памяти у них нет.

### Поток

**Поток** исполняется независимо от других потоков, как и процесс, но живёт *внутри* процесса и делит с ним адресное пространство и системные ресурсы. Отсюда главное различие. Двум потокам одного процесса ничего не стоит работать с общими данными, ведь они просто видят одни и те же объекты.

Удобно это лишь до тех пор, пока два потока не полезут в одни данные одновременно. Тогда начинаются гонки, о которых мы поговорим чуть ниже.

Порядком исполнения и процессов, и потоков распоряжается операционная система, поочерёдно выдающая каждому по нескольку тактов процессора.

## Модуль `threading`

Поток в Python устроен как самый обычный системный поток, и управляет его исполнением операционная система, а не интерпретатор. Создать поток можно классом `Thread` из модуля стандартной библиотеки `threading`.


```python
import time
from threading import Thread

def countdown(n):
    for i in range(n):
        print(n - i - 1, "left")
        time.sleep(1)
```


```python
t = Thread(target=countdown, args=(3,))
```


```python
t.start()
```

    2 left


Альтернативным способом создать поток служит наследование.


```python
class CountdownThread(Thread):
    def __init__(self, n):
        super().__init__()
        self.n = n
        
    def run(self): # вызывается методом start
        for i in range(self.n):
            print(self.n - i - 1, "left")
            time.sleep(1)
```


```python
t = CountdownThread(3)
```


```python
t.start()
```

    2 left


Недостаток этого подхода состоит в том, что он ограничивает переиспользование кода. Функциональность класса `CountdownThread` доступна только в отдельном потоке.

Встроенного способа убить поток в Python нет, и это осознанное решение разработчиков языка, а не недосмотр. Корректное завершение почти всегда означает освобождение ресурсов. Поток мог открыть файл, дескриптор которого надо закрыть, или захватить примитив синхронизации, который надо отпустить. Убийство на полуслове оставило бы всё это висеть, поэтому о завершении поток обычно просят флагом.


```python
class Task:
    def __init__(self):
        self._running = True
    
    def terminate(self):
        self._running = False
    
    def run(self, n):
        while self._running:
            ...
```

Набор примитивов синхронизации в модуле `threading` стандартный:
* `Lock`, обычный мьютекс, используемый для организации эксклюзивного доступа к разделяемому состоянию.
* `RLock`, рекурсивный мьютекс, разрешающий потоку, владеющему мьютексом, захватывать его больше одного раза.
* `Semaphore`, вариация мьютекса, захватываемая не более фиксированного числа раз.
* `BoundedSemaphore`, семафор, следящий за тем, чтобы его захватывали и освобождали одинаковое число раз.

Все примитивы синхронизации реализуют единый интерфейс:
* метод `acquire` захватывает примитив синхронизации,
* а метод `release` освобождает его.


```python
from threading import Lock


class SharedCounter:
    def __init__(self, value):
        self._value = value
        self._lock = Lock()
    
    def increment(self, delta=1):
        self._lock.acquire()
        self._value += delta
        self._lock.release()
    
    def get(self):
        return self._value
```

## Модуль `queue`

Обмениваться данными между потоками руками, расставляя мьютексы, занятие неблагодарное. Обычно берут готовую очередь. Модуль `queue` реализует несколько потокобезопасных вариантов.

* `Queue`, очередь FIFO,
* `LifoQueue`, очередь LIFO, то есть стек,
* `PriorityQueue`, очередь элементов, то есть пар (priority, item).

Никаких изысков внутри нет, ведь все методы, меняющие состояние, работают «внутри» мьютекса. `Queue` держит элементы в `deque`, а `LifoQueue` и `PriorityQueue` в обычном списке.

Классическая схема «производитель-потребитель» на очереди выглядит следующим образом.


```python
def worker(q):
    while True:
        item = q.get() # блокирующе ждёт следующий
        do_something(item) # элемент
        q.task_done() # уведомляет очередь о выполнении
        
def master(q):
    for item in source():
        q.put(item)

    # блокирующе ждёт, пока все элементы
    # очереди не будут обработаны
    q.join()
```

## Пример с модулем `futures`: `integrate`

Проверим всё это на счётной задаче, численном интегрировании методом прямоугольников. Функция считает интеграл в лоб, циклом по разбиению отрезка.


```python
import math

def integrate(f, a, b, *, n_iter=1000):
    acc = 0
    step = (b - a) / n_iter
    for i in range(n_iter):
        acc += f(a + i * step) * step
    return acc
```


```python
integrate(math.cos, 0, math.pi / 2)
```




    1.0007851925466296




```python
from functools import partial

def integrate_async(f, a, b, *, n_jobs, n_iter=1000):
    executor = ThreadPoolExecutor(max_workers=n_jobs)
    spawn = partial(executor.submit, integrate, f,
                    n_iter=n_iter // n_jobs)
    step = (b-a)/n_jobs
    fs=[spawn(a+i*step,a+(i+1)*step)
        for i in range(n_jobs)]
    return sum(f.result() for f in as_completed(fs))
```


```python
integrate_async(math.cos, 0, math.pi / 2, n_jobs=2)
```




    1.0007851925466305



## Параллелизм и конкурентность

```python

```

    154 ms ± 2.28 ms per loop (mean ± std. dev. of 7 runs, 100 loops each)



```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2)
```

    142 ms ± 2.11 ms per loop (mean ± std. dev. of 7 runs, 100 loops each)


### Вот он, GIL

Результат обескураживает. Два потока вместо одного дали выигрыш в проценты вместо ожидаемого ускорения вдвое. Причиной служит **GIL** (global interpreter lock, глобальная блокировка интерпретатора).

GIL представляет собой мьютекс, гарантирующий, что в каждый момент времени байт-код исполняет только один поток. Появился он не по недосмотру. Внутреннее состояние интерпретатора (в первую очередь счётчики ссылок у каждого объекта) не защищено от одновременного доступа, и глобальная блокировка остаётся самым простым способом не дать двум потокам испортить его разом. Платой за простоту стало то, что мы наблюдали в замере.

Отсюда главное следствие: **потоки в Python не ускоряют вычисления.** Сколько бы их ни было, байт-код по-прежнему исполняется по очереди, а к вычислениям добавляются накладные расходы на переключение, так что иногда многопоточная версия оказывается даже медленнее однопоточной.

### Когда GIL мешает, а когда нет

Ответ зависит от того, чем занята программа.

Если она **считает**, GIL становится прямым препятствием, и потоки бесполезны. Обойти его можно двумя путями: уйти в отдельные процессы, у каждого из которых свой интерпретатор со своим GIL (об этом ниже), или спуститься в скомпилированный код, умеющий GIL отпускать.

Если же программа **ждёт**, то есть читает файл, тянет данные по сети, опрашивает прибор, картина меняется полностью. На время ожидания поток отпускает GIL, и остальные спокойно работают. Для такой нагрузки потоки прекрасно подходят, и никакого проигрыша от блокировки нет.

Заметь, что и NumPy на длинных операциях отпускает GIL, так что пока перемножаются большие матрицы, интерпретатор свободен. Поэтому многопоточность в связке с NumPy работает лучше, чем можно ожидать.

### C и Cython: как отпустить GIL

Скомпилированный код может отпустить GIL явно, на то время, пока он не трогает объекты Python. В Cython для этого есть блок `with nogil`. Внутри него живут только сишные типы, зато остальные потоки работают по-настоящему параллельно.


```python
%load_ext Cython
```


```cython
%%cython

from libc.math cimport cos

def integrate(f, double a, double b, long n_iter):
    cdef double acc = 0
    cdef double step=(b-a)/n_iter
    cdef long i
    with nogil:
        for i in range(n_iter):
            acc += cos(a + i * step) * step
    return acc
```


```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2)
```

    5.88 ms ± 126 µs per loop (mean ± std. dev. of 7 runs, 100 loops each)


Те же два потока, тот же `integrate_async`, и 5.88 мс вместо 142. Только выигрыш этот составной, и делить его надо честно. Потоков всего два, поэтому на снятие GIL приходится не больше двух раз; остальное, примерно тринадцатикратное, дала компиляция в машинный код. Вывод отсюда не «`nogil` ускоряет в двадцать четыре раза», а «сначала Cython, и только потом распараллеливание того, что он скомпилировал».

> **О замерах ниже.** Ячейка выше переопределила имя `integrate`: теперь под ним живёт скомпилированная Cython-версия, а не та, с которой глава начиналась. Все дальнейшие числа получены с ней, поэтому сравнивать их со 142 мс из раздела про потоки нельзя; между собой можно. Если хочешь сравнить способы распараллеливания начистоту, перезапусти блокнот, пропустив ячейку с Cython.

## Модуль `multiprocessing`
### Процессы как ещё одно лекарство от GIL

Раз глобальная блокировка одна на интерпретатор, самый прямой способ её обойти сводится к тому, чтобы завести несколько интерпретаторов. Это и делают процессы. У каждого свой GIL, друг другу они не мешают, и на восьми ядрах восемь процессов считают одновременно.

Платой за это становится изоляция. Процессы не разделяют память, поэтому всё, что нужно передать между ними, приходится сериализовать и копировать. Для расчёта, где каждому процессу отдают кусок работы и забирают число, это несущественно; для задачи с большим общим состоянием накладные расходы могут съесть весь выигрыш.

За работу с процессами в Python отвечает модуль `multiprocessing`, устроенный намеренно похоже на `threading`.


```python
import multiprocessing as mp
```


```python
p = mp.Process(target=countdown, args=(5, ))
```



    2 left
    1 left
    0 left


Примитивы синхронизации здесь те же самые: мьютексы, семафоры, условные переменные. А чтобы процессы могли обмениваться данными, есть `Pipe`, соединение двух процессов поверх сокетов.

## Процессы и производительность

Реализация функции `integrate_async` на основе пула потоков работала долго, попробуем использовать пул процессов.


```python
from concurrent.futures import ProcessPoolExecutor
```


```python
def integrate_async(executor, f, a, b, *, n_jobs, n_iter=1000):
    spawn = partial(executor.submit, integrate, f,
                    n_iter=n_iter // n_jobs)

    step = (b - a) / n_jobs
    fs=[spawn(a + i * step, a + (i + 1) * step)
        for i in range(n_jobs)]

    return sum(f.result() for f in as_completed(fs))
```

Пул принимается аргументом, а не создаётся внутри, и это принципиально. Запуск
процесса стоит десятки миллисекунд: на macOS и Windows интерпретатор стартует
заново, целиком. Создав пул внутри измеряемой функции, замерять будешь запуск
интерпретатора, а не счёт. Вдобавок незакрытый `ProcessPoolExecutor` оставляет
процессы жить, и за сотню итераций `%%timeit` машина обрастёт ими всерьёз.

```python
with ProcessPoolExecutor(max_workers=2) as executor:
    integrate_async(executor, math.cos, 0, math.pi / 2,
                    n_iter=10**6, n_jobs=2)          # прогрев
    %timeit -n5 integrate_async(executor, math.cos, 0, math.pi / 2, \
                                n_iter=10**6, n_jobs=2)
```

    21 ms ± 0.2 ms per loop (mean ± std. dev. of 5 runs, 5 loops each)

Последовательный счёт той же интеграции занимает 44 мс. Два процесса дают 21 мс,
то есть то самое двукратное ускорение, которого и ждёшь от двух ядер, и никакого
GIL, потому что у каждого процесса он свой.


## Пакет `joblib`

Пакет `joblib` даёт параллельный аналог обычного цикла `for`, удобный, когда итерации независимы и их надо просто разложить по ядрам. Чем раскладывать, потоками или процессами, выбирается одним аргументом `backend`.


Замеры ниже сделаны на **исходной**, чистой Python-версии `integrate`. Если в блокноте
уже выполнена ячейка с `%%cython`, имя `integrate` указывает на скомпилированную
функцию, и числа получатся другие, на порядок меньше. Сравнивать их с тем, что было
до Cython, нельзя; чтобы повторить замеры отсюда, определи `integrate` заново.

```python
from joblib import Parallel, delayed

def integrate_async(f, a, b, *, n_jobs, n_iter=1000, backend=None):
    step = (b - a) / n_jobs
    with Parallel(n_jobs=n_jobs, backend=backend) as parallel:
        fs = (delayed(integrate)(f, a + i * step,
                                 a + (i + 1) * step,
                                 n_iter=n_iter // n_jobs)
              for i in range(n_jobs))
        return sum(parallel(fs))   # внутри with: пул переиспользуется
```


```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2, backend="threading")
```

    104 ms ± 280 µs per loop (mean ± std. dev. of 7 runs, 100 loops each)



```python
%%timeit -n100
integrate_async(math.cos, 0, math.pi / 2, n_iter=10**6, n_jobs=2, backend="multiprocessing")
```

    290 ms ± 1.13 ms per loop (mean ± std. dev. of 7 runs, 100 loops each)


Сравнение бэкендов показывает главное. Сам по себе `joblib` ничего не ускоряет, он лишь удобно раскладывает работу, а упрётся она всё в тот же GIL на потоках или в ту же сериализацию на процессах.

## JIT-компилятор `numba`

И последнее замечание. Numba из главы про профилирование обходит GIL заодно с ускорением. Декоратор `@jit(nopython=True, parallel=True)` компилирует функцию в машинный код и отпускает блокировку, так что цикл `prange` раскладывается по ядрам всерьёз.


```python
import math
from numba import jit, prange

@jit(nopython=True, parallel=True, fastmath=True)
def integrate(a, b, n_iter=1000):
    acc = 0
    step = (b - a) / n_iter
    for i in prange(n_iter):
        acc += math.cos(a + i * step) * step
    return acc
```

## Резюме

Всё содержание главы укладывается в один вопрос, который стоит задавать себе перед выбором инструмента, **считает программа или ждёт**.

Если ждёт сети, диска, прибора, ответа пользователя, бери потоки. GIL на время ожидания отпускается, потоки дёшевы, и десятки одновременных ожиданий обходятся почти бесплатно. Если ждать предстоит тысячами, переходи к асинхронности из следующей главы.

Если считает, потоки не помогут никогда, сколько бы их ни было. Здесь работают три пути: вынести расчёт в отдельные процессы через `multiprocessing`, где у каждого свой интерпретатор и свой GIL; спуститься в скомпилированный код на Cython или C, умеющий GIL отпускать; или, что обычно проще всего, поручить расчёт NumPy, отпускающему блокировку за тебя.

И общее правило, которое сэкономит много времени: прежде чем распараллеливать, **замерь**. Довольно часто выясняется, что узкое место не там, где казалось, и одна правка алгоритма даёт больше, чем любое количество потоков.
