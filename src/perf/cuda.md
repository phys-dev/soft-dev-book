# CUDA и вычисления на GPU

В главе про профилирование мы разгоняли умножение матриц на CPU: переставляли циклы, компилировали код через Numba и Cython, а в конце просто вызвали NumPy и получили микросекунды вместо десятков миллисекунд. В главе про GIL выяснилось, что потоки в Python упираются в глобальную блокировку, а процессов у тебя столько, сколько ядер — то есть штук восемь-шестнадцать. Это потолок CPU.

А теперь посмотри на видеокарту. У современного GPU тысячи ядер, а пиковая производительность — десятки терафлопс против единиц у процессора. Если твоя задача — выполнить одну и ту же операцию над миллионами чисел (а в физике это почти всегда так), GPU даст ускорение в 10–100 раз. Эта глава о том, как забрать это ускорение, не выходя из Python.

## Зачем физику видеокарта

GPU придумали для игр: нужно было независимо посчитать цвет каждого из миллионов пикселей 60 раз в секунду. Быстро выяснилось, что «одна и та же формула для миллионов независимых элементов» — это не только про пиксели:

* **Моделирование частиц.** Метод частиц в ячейках (PIC), молекулярная динамика, трекинг пучка в ускорителе — миллионы частиц, и каждая на каждом шаге обновляется по одним и тем же уравнениям движения.
* **Сеточные задачи.** Уравнения теплопроводности, Пуассона, Максвелла, Навье–Стокса на разностных сетках: значение в каждом узле пересчитывается по одному шаблону.
* **Обработка данных детекторов.** Реконструкция треков, фильтрация изображений, томография — конвейеры однотипных операций над большими массивами. Триггерные фермы на LHC давно считают на GPU.
* **Монте-Карло.** Транспорт излучения, генерация событий: миллионы независимых историй.
* **Нейросети.** Обучение — по сути миллиарды умножений матриц; без GPU глубокое обучение просто не случилось бы.

Общее у всех этих задач одно: **массовый параллелизм данных**. Много элементов, над каждым — одинаковая и относительно простая работа, элементы почти не зависят друг от друга. Именно под такой профиль GPU и заточен.

## Чем GPU отличается от CPU

CPU оптимизирован под **латентность**: выполнить одну цепочку инструкций как можно быстрее. Ради этого ядро CPU обвешано сложной машинерией — предсказателем переходов, внеочередным исполнением, огромными кешами. GPU оптимизирован под **пропускную способность**: выполнить как можно больше работы в секунду, пусть каждая отдельная операция и займёт больше времени. Ядра у него простые, зато их тысячи.

|                              | CPU                                   | GPU                                        |
|------------------------------|---------------------------------------|--------------------------------------------|
| Ядер                         | 4–64 сложных                          | тысячи простых (RTX 4090 — 16 384)         |
| Частота                      | 3–5 ГГц                               | 1–2.5 ГГц                                  |
| Логика ядра                  | предсказание переходов, внеочередное исполнение | максимально простая                |
| Скрытие задержек памяти      | большие кеши                          | тысячи нитей: пока одни ждут память, считают другие |
| Полоса памяти                | ~50–100 ГБ/с (DDR5)                   | сотни ГБ/с — единицы ТБ/с (GDDR6X, HBM)    |
| Оптимизирован под            | латентность одной задачи              | суммарную пропускную способность           |
| Идеальная нагрузка           | ветвистая, последовательная           | однотипная над большими массивами          |

### SIMT и warp

Ядра GPU не полностью независимы. Нити (threads) исполняются группами по 32 штуки — такая группа называется **warp**. Все нити warp'а в каждый момент выполняют одну и ту же инструкцию, но над разными данными. Эта модель называется SIMT — Single Instruction, Multiple Threads: один поток команд, много потоков данных.

Отсюда важное следствие. Если внутри warp'а код ветвится (`if`), и часть нитей пошла по одной ветке, а часть по другой, GPU выполнит **обе ветки по очереди**, выключая «чужие» нити. Это называется дивергенцией warp'а: ветвистый код на GPU не ускоряется, а деградирует. Хорошая GPU-программа — это когда 32 соседние нити дружно делают одно и то же.

### Иерархия памяти

Память GPU устроена ступеньками, и разница между ступеньками — порядки:

* **Регистры** — свои у каждой нити, доступ за ~1 такт. Локальные переменные ядра живут здесь.
* **Разделяемая память (shared memory)** — общая для блока нитей, порядка 100 КБ на мультипроцессор, доступ за ~10–30 тактов. Это управляемый вручную кеш: сюда загружают кусок данных, который блок будет использовать многократно.
* **Глобальная память** — те самые гигабайты «памяти видеокарты». Видна всем нитям, полоса огромная (сотни ГБ/с), но латентность — сотни тактов.

GPU прячет латентность глобальной памяти не кешами, как CPU, а количеством нитей: пока один warp ждёт данные, мультипроцессор исполняет другие. Поэтому нитей нужно запускать сильно больше, чем физических ядер — десятки тысяч и миллионы, это нормально.

## Модель CUDA

CUDA — платформа NVIDIA для вычислений общего назначения на GPU. Терминология из неё расползлась по всем инструментам, поэтому выучим её один раз.

* **Host** — CPU и оперативная память. **Device** — GPU и его память. Это два разных мира со своими адресными пространствами; данные между ними надо явно копировать.
* **Ядро (kernel)** — функция, которую host запускает на device. Она исполняется одновременно тысячами нитей: каждая нить выполняет один и тот же код, но обрабатывает свой элемент данных.
* Нити организованы в двухуровневую иерархию: **сетка (grid) → блоки (blocks) → нити (threads)**.

```text
Grid (сетка — весь запуск ядра)
├── Block 0 ── [нить 0][нить 1] ... [нить 255]
├── Block 1 ── [нить 0][нить 1] ... [нить 255]
├── Block 2 ── [нить 0][нить 1] ... [нить 255]
└── ...

глобальный индекс нити = blockIdx.x * blockDim.x + threadIdx.x
```

Зачем два уровня? Блок целиком попадает на один мультипроцессор: его нити могут общаться через разделяемую память и синхронизироваться между собой. Блоки же друг о друге ничего не знают, и планировщик раскидывает их по мультипроцессорам как угодно — именно поэтому одна и та же программа масштабируется и на ноутбучную видеокарту с 20 мультипроцессорами, и на серверную со 130.

Внутри ядра нить первым делом выясняет, кто она такая. У неё есть номер блока `blockIdx`, размер блока `blockDim` и номер внутри блока `threadIdx`. Глобальный индекс собирается из них:

```text
i = blockIdx.x * blockDim.x + threadIdx.x
```

Например, нить номер 5 в блоке номер 3 при блоках по 256 нитей получит `i = 3 * 256 + 5 = 773` и будет обрабатывать 773-й элемент массива. Цикл `for i in range(n)` из CPU-кода на GPU исчезает: вместо него запускается `n` нитей, и каждая делает одну итерацию.

## Главное правило: данные должны жить на GPU

У GPU своя память, и соединена она с host'ом через шину PCIe с пропускной способностью порядка 10–30 ГБ/с. Сравни с полосой памяти самого GPU — около терабайта в секунду. Копирование массива host → device часто стоит дороже, чем вычисления над ним: перегнать гигабайтный массив через PCIe — десятки миллисекунд, а перемножить матрицы такого размера GPU успеет быстрее.

Отсюда антипаттерн номер один:

```text
плохо:  [CPU: данные] → GPU → шаг → [CPU] → GPU → шаг → [CPU] → ...
хорошо: [CPU: данные] → GPU → шаг → шаг → шаг → ... → [CPU: результат]
```

Правильная схема любой GPU-программы: скопировать входные данные на устройство **один раз**, выполнить там всю цепочку вычислений (все шаги по времени, все итерации), и забрать назад только результат — а лучше только диагностику: энергию, спектр, картинку. Если в цикле по шагам у тебя мелькает копирование туда-обратно — ускорения не будет.

## CuPy: NumPy на видеокарте

Самый короткий путь к GPU из Python — [CuPy](https://cupy.dev/). Это реализация интерфейса NumPy поверх CUDA: те же `ndarray`, `sum`, `dot`, `fft`, `linalg`, только массивы лежат в памяти видеокарты и все операции выполняет GPU.

```python
import cupy as cp

x = cp.arange(10**7, dtype=cp.float32)   # массив рождается сразу в памяти GPU
y = cp.sin(x) ** 2 + cp.cos(x) ** 2      # считает GPU, host только раздаёт команды
s = y.sum()                              # редукция тоже на GPU, результат — 0-мерный массив

y_host = cp.asnumpy(y)                   # явное копирование device → host (в NumPy-массив)
x_gpu = cp.asarray(y_host)               # и обратно, host → device
```

Если ты умеешь писать векторизованный NumPy-код (а после главы про профилирование — умеешь), ты уже умеешь программировать GPU: в большинстве скриптов достаточно заменить `import numpy as np` на `import cupy as cp`.

Проверим на нашем старом знакомом — умножении матриц:

```python
import numpy as np
import cupy as cp
from time import perf_counter

n = 4096
A = np.random.rand(n, n).astype(np.float32)
B = np.random.rand(n, n).astype(np.float32)

# --- CPU ---
t0 = perf_counter()
C = A @ B
t_cpu = perf_counter() - t0

# --- GPU ---
A_gpu = cp.asarray(A)                  # копируем данные на видеокарту один раз
B_gpu = cp.asarray(B)

C_gpu = A_gpu @ B_gpu                  # прогрев: первый вызов компилирует ядра
cp.cuda.Stream.null.synchronize()

t0 = perf_counter()
C_gpu = A_gpu @ B_gpu
cp.cuda.Stream.null.synchronize()      # дожидаемся, пока GPU реально досчитает
t_gpu = perf_counter() - t0

print(f"CPU: {t_cpu:.3f} c, GPU: {t_gpu:.4f} c, ускорение x{t_cpu / t_gpu:.0f}")
```

На бесплатной T4 в Colab это даёт ускорение в один-два порядка относительно NumPy — при том что NumPy сам по себе уже близок к пределу CPU.

Два обязательных замечания про такие замеры:

* **Запуск ядер асинхронный.** Вызов `A_gpu @ B_gpu` лишь ставит работу в очередь GPU и возвращается немедленно. Если замерить время без `cp.cuda.Stream.null.synchronize()`, получатся фантастические микросекунды — время постановки в очередь, а не вычислений. Синхронизация происходит и неявно — при копировании результата на host или вызове `float(s)`, поэтому «обычный» код работает корректно; но в бенчмарках синхронизируй явно.
* **Первый вызов — прогрев.** При первом обращении CuPy компилирует ядра под твою видеокарту, это заметные доли секунды. Замеряй со второго раза (то же самое ты уже видел у Numba).

Бонус для библиотечного кода: функция `cp.get_array_module(x)` возвращает `numpy` или `cupy` в зависимости от того, где лежит массив `x`. Так пишут функции, которые прозрачно работают и на CPU, и на GPU.

## Numba CUDA: пишем ядро сами

CuPy покрывает всё, что выражается операциями над целыми массивами. Но иногда алгоритм в такие операции не укладывается: нестандартная поэлементная логика, свой обход данных. В главе про профилирование мы в такой ситуации вешали `@numba.jit` на функцию с циклами, и Numba компилировала её для CPU. У Numba есть и второй бэкенд: `@cuda.jit` компилирует Python-функцию в CUDA-ядро.

Канонический пример — сложение векторов:

```python
import numpy as np
from numba import cuda

@cuda.jit
def add_kernel(a, b, out):
    i = cuda.grid(1)              # глобальный индекс нити в одномерной сетке
    if i < out.size:              # нитей запущено чуть больше, чем элементов
        out[i] = a[i] + b[i]      # каждая нить обрабатывает ровно один элемент

n = 10_000_000
a = np.random.rand(n).astype(np.float32)
b = np.random.rand(n).astype(np.float32)

# явно переносим данные на device и заводим там массив под результат
d_a = cuda.to_device(a)
d_b = cuda.to_device(b)
d_out = cuda.device_array_like(d_a)

# конфигурация запуска: сколько нитей в блоке и сколько блоков в сетке
threads_per_block = 256
blocks_per_grid = (n + threads_per_block - 1) // threads_per_block  # округление вверх

add_kernel[blocks_per_grid, threads_per_block](d_a, d_b, d_out)
cuda.synchronize()                # дожидаемся завершения (запуск, как всегда, асинхронный)

out = d_out.copy_to_host()        # забираем результат на CPU
```

Разберём по шагам:

* **Тело ядра** — код *одной* нити. Циклов по элементам нет: параллелизм создаётся тем, что этих нитей запустятся миллионы. `cuda.grid(1)` — сокращение для `cuda.blockIdx.x * cuda.blockDim.x + cuda.threadIdx.x`, той самой формулы глобального индекса.
* **Проверка `if i < out.size`** обязательна. Число нитей кратно размеру блока: для `n = 10^7` при блоках по 256 запустится 39 063 блока, то есть 10 000 128 нитей — на 128 больше, чем элементов. Лишние нити без проверки полезли бы за границу массива.
* **`threads_per_block`** обычно берут 128–512 (максимум 1024, лучше кратно 32 — размеру warp'а). Точное значение — вопрос тонкой настройки, для начала 256 — хороший выбор.
* **`blocks_per_grid`** вычисляется из размера задачи: классическая формула округления вверх `(n + tpb - 1) // tpb`.
* **Конфигурация в квадратных скобках** `kernel[blocks, threads](...)` — так Numba передаёт CUDA, сколько нитей запустить.
* **Ядро ничего не возвращает** — оно может только писать в переданные ему массивы, поэтому `d_out` создаём заранее.

Если передать в ядро обычные NumPy-массивы, Numba скопирует их на GPU и обратно сама — удобно для проб, но в цикле по шагам это тот самый антипаттерн с копированием. Явные `cuda.to_device` / `copy_to_host` держат трафик под контролем. Кстати, ядра Numba умеют принимать и массивы CuPy — инструменты дружат между собой.

Внутри `@cuda.jit`-функции доступно ограниченное подмножество Python: числа, арифметика, циклы, условия, обращение к массивам, математика из `math`. Никаких списков, словарей и создания массивов — как и в `nopython`-режиме обычной Numba, только строже.

Сетки и блоки бывают не только одномерными. Для матриц, изображений с детекторов и разностных сеток удобны двумерные: нить получает сразу пару индексов и обрабатывает один узел сетки. Вот, например, ядро, считающее дискретный лапласиан — сердце уравнений теплопроводности и Пуассона:

```python
@cuda.jit
def laplace_kernel(u, out):
    i, j = cuda.grid(2)                   # у нити теперь два индекса: строка и столбец
    if 0 < i < u.shape[0] - 1 and 0 < j < u.shape[1] - 1:   # только внутренние узлы
        out[i, j] = (u[i + 1, j] + u[i - 1, j] +
                     u[i, j + 1] + u[i, j - 1] - 4 * u[i, j])

threads_2d = (16, 16)                     # блок 16x16 = 256 нитей
blocks_2d = ((nx + 15) // 16, (ny + 15) // 16)   # покрываем сетку nx на ny узлов
laplace_kernel[blocks_2d, threads_2d](d_u, d_lap)
```

Каждая нить читает пять соседних узлов и пишет один, а дальше GPU сам исполняет это для всех миллионов узлов сетки. Явная разностная схема для двумерной теплопроводности отсюда в одном шаге: `u += alpha * dt / h**2 * lap`.

## Пример из физики: дрейф частиц в скрещенных полях

Соберём всё вместе на настоящей задаче. Возьмём облако из пяти миллионов электронов в скрещенных полях \\( \vec{E} = (E_0, 0, 0) \\) и \\( \vec{B} = (0, 0, B_0) \\) и проинтегрируем их движение схемой Бориса — стандартным методом всей вычислительной физики плазмы (её родственницу ты уже видел в примере REDPIC). Теория обещает, что помимо ларморовского вращения облако как целое дрейфует поперёк обоих полей со скоростью \\( E_0 / B_0 \\), не зависящей ни от заряда, ни от массы.

```python
import cupy as cp   # замени на "import numpy as cp" — и тот же код посчитает CPU

# --- параметры задачи (СИ) ---
q, m = -1.602e-19, 9.109e-31          # заряд и масса электрона
E0, B0 = 1e3, 1e-2                    # поля: В/м и Тл
dt, n_steps = 1e-11, 2000             # шаг 10 пс, всего 20 нс (~5 ларморовских периодов)
N = 5_000_000                         # пять миллионов частиц

# --- начальное состояние: облако ~1 мм с тепловым разбросом скоростей ---
# все массивы создаются сразу в памяти GPU и живут там до конца расчёта
rng = cp.random.default_rng(42)
x = rng.standard_normal(N, dtype=cp.float32) * 1e-3    # м
y = rng.standard_normal(N, dtype=cp.float32) * 1e-3
vx = rng.standard_normal(N, dtype=cp.float32) * 1e5    # м/с
vy = rng.standard_normal(N, dtype=cp.float32) * 1e5

# --- константы схемы Бориса: обычные числа, считаются один раз на CPU ---
h = q * dt / (2 * m)                  # q·dt/2m
t = h * B0                            # tan(θ/2) поворота в магнитном поле за шаг
s = 2 * t / (1 + t * t)

for step in range(n_steps):
    vx += h * E0                      # полшага разгона электрическим полем
    px = vx + vy * t                  # поворот скорости вокруг B:
    py = vy - vx * t                  #   промежуточный вектор v'
    vx, vy = vx + py * s, vy - px * s #   точный поворот на угол ω_c·dt
    vx += h * E0                      # ещё полшага разгона
    x += vx * dt                      # сдвигаем частицы
    y += vy * dt

# --- диагностика: на host уходят только два числа, не массивы ---
v_drift = float(y.mean()) / (n_steps * dt)   # float() неявно синхронизирует GPU
energy = float(0.5 * m * (vx**2 + vy**2).mean())
print(f"скорость дрейфа: {v_drift:.3e} м/с (теория: {-E0 / B0:.3e})")
```

Обрати внимание на структуру:

* **Данные рождаются на GPU** (`cp.random`) и не покидают его все 2000 шагов. За пределы устройства уходят два числа диагностики — и только в этот момент host дожидается GPU.
* **Физика — несколько строк массивных операций.** Каждая строка цикла — это одно-два CUDA-ядра, которые CuPy запускает над пятью миллионами элементов. Сам цикл по шагам остаётся на CPU, и это нормально: 2000 итераций цикла — копейки, дорогая работа внутри.
* **Тот же код работает на CPU.** Поменяй первую строку — получишь NumPy-версию для отладки на ноутбуке без видеокарты. На GPU она побежит в десятки раз быстрее.
* **float32.** Для такой задачи одинарной точности достаточно, а на игровых и облачных картах она в разы быстрее двойной (об этом ниже).

Дальше эту заготовку можно развивать: неоднородные поля (поле зависит от координаты частицы — по-прежнему поэлементные операции), потери и рождение частиц (маски), самосогласованное поле (гистограмма зарядов + Пуассон через `cp.fft`). Всё это остаётся в рамках CuPy.

## Когда GPU не поможет

GPU — не волшебная кнопка «быстрее». Есть честный список ситуаций, где он бесполезен или вреден:

* **Маленькие данные.** Запуск ядра стоит ~5–10 микросекунд, копирование через PCIe — ещё дороже. Если работы меньше, чем на миллисекунду, накладные расходы съедят всё. Складывать массивы из тысячи элементов на GPU бессмысленно — NumPy сделает это быстрее.
* **Ветвистая логика.** Из-за дивергенции warp'ов код, где каждый элемент обрабатывается по-своему (деревья решений, парсинг, сложные `if`-каскады), параллелится плохо.
* **Последовательные зависимости.** Если шаг `i+1` нельзя начать без результата шага `i`, а внутри шага работы мало, параллелить нечего. Одна частица на миллиард шагов — задача для CPU и Numba. Но заметь: миллион *независимых* траекторий по миллиарду шагов — снова идеальная задача для GPU; в физике спасение часто в том, чтобы параллелить по ансамблю или по параметрам, а не по времени.
* **Двойная точность на игровых картах.** GeForce считает float64 в 32–64 раза медленнее float32 — блоки FP64 там почти отсутствуют. Полноценный FP64 (половина от FP32) есть только у вычислительных карт вроде A100/H100. Если твоей задаче — небесной механике, длинному интегрированию, плохо обусловленной алгебре — нужна двойная точность, замерь её отдельно, иначе тебя ждёт разочарование.
* **Задачи про ожидание, а не про счёт.** Если программа ждёт сеть или диск — тебе в главу про асинхронность, GPU тут ни при чём.

Практическое правило: прежде чем переписывать на GPU, профилируй (глава про профилирование в помощь) и прикинь арифметическую интенсивность — сколько операций приходится на каждый байт данных. Умножение матриц — отлично, поэлементное сложение — уже упирается в память, а не в вычислители.

## Экосистема: не CUDA единой

Писать ядра руками нужно реже, чем кажется: вокруг CUDA вырос целый слой «GPU для людей». [PyTorch](https://pytorch.org/) и [JAX](https://docs.jax.dev/) по сути дают NumPy на видеокарте плюс автоматическое дифференцирование и JIT-компиляцию. Физики массово используют их не только для нейросетей, но и как удобный вычислительный бэкенд: перенос тензора на карту умещается в одно `.to("cuda")`, а `jax.jit` и `jax.vmap` компилируют и векторизуют целые модели. Библиотеки [RAPIDS](https://rapids.ai/) (cuDF, cuML) переносят на GPU pandas и scikit-learn, что выручает, когда узкое место не физика, а обработка таблиц с данными. Под капотом у всех этих инструментов работают те же ядра, сетки и блоки, так что понимание модели CUDA останется с тобой в любом из них. Ну а если однажды упрёшься в пределы Python, тебя ждёт CUDA C++, и концепции там ровно те же.

## Итог: лестница ускорения

Этой главой раздел про ускорение программ заканчивается, так что соберём всю лестницу целиком. Когда код медленный, поднимайся по ступенькам сверху вниз и останавливайся, как только стало достаточно быстро:

1. **Профилируй.** Пока `line_profiler` не показал, где уходит время, любая оптимизация — гадание.
2. **Проверь алгоритм.** Никакое железо не спасёт \\( O(n^2) \\) там, где есть \\( O(n \log n) \\).
3. **Векторизуй.** NumPy вместо циклов — обычно первый и самый дешёвый порядок ускорения.
4. **Компилируй.** Numba или Cython — для логики, которая в массивные операции не укладывается.
5. **Распараллель на CPU.** Процессы для счёта (GIL!), асинхронность — если узкое место ожидание, а не вычисления.
6. **Переноси на GPU.** Много однотипной работы над большими массивами — CuPy; своя поэлементная логика — Numba CUDA. Помни два правила: данные живут на GPU, а замеры делаются с синхронизацией.

Красивая симметрия напоследок: тот же векторизованный стиль мышления, который в начале раздела ускорял код на CPU, здесь почти без изменений пересаживается на видеокарту. Учишься один раз — ускоряешься везде.
