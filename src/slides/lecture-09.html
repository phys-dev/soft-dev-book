Цель лекции

Найти место, где программа теряет время, и ускорить именно его

Профилировщик показывает, на что уходит время. Дальше выбирается самый дешёвый способ ускорения: другой алгоритм, приём языка, NumPy, компиляция горячего цикла или параллельные вычисления. Каждый шаг подтверждается замером и тестом: ускоренный неверный расчёт остаётся неверным.

Изложение. Python обладает многими достоинствами, кроме скорости. Медленный код на Python почти всегда можно ускорить, не переписывая его целиком на C++, но для этого необходимо знать, где именно он медленный. Интуиция о том, где программа проводит время, систематически ошибается: функция, которая кажется тяжёлой, часто занимает проценты, а основное время уходит в незаметный цикл. Поэтому порядок работы всегда один и тот же: измерить, найти горячее место, ускорить его самым дешёвым способом и снова измерить. Для физиков: расчёт динамики пучка или обработка данных эксперимента обычно проводят большую часть времени в одном-двух вложенных циклах. Ускорение именно этих циклов в сто раз превращает расчёт, не укладывающийся в ночь, в расчёт на несколько минут.

Пояснение

Интерпретатор проверяет типы на каждой операции; заранее вычисляются лишь выражения из констант, остальной код исполняется буквально.

Изложение. Тип значения, связанного с именем, становится известен только во время выполнения: одна и та же функция add складывает целые и вещественные числа, склеивает строки и списки. Поэтому на каждой операции интерпретатор выясняет типы операндов и выбирает подходящую реализацию сложения, а эти проверки, повторяющиеся миллионы раз, требуют времени. Каждое число в Python — объект в куче со счётчиком ссылок и указателем на тип: целое число занимает 28 байт, тогда как в C переменная типа double — 8 байт, а сложение — одна инструкция процессора. Кроме того, интерпретатор не знает заранее, с какими данными работает, и обязан исполнять написанный код почти буквально: компилятор заранее вычисляет лишь выражения из литералов вроде 60 * 60 * 24 и отбрасывает ветвь if False, а выражение с именами вычислить заранее нельзя, поскольку любое имя может быть переопределено.

Пояснение

Проверку, которую компилятор C вынес бы из цикла, переносит только программист: 13,1 → 9,8 мкс.

Изложение. В Python почти всё может быть изменено во время выполнения: встроенное имя len переопределяется присваиванием, тело уже определённой функции заменяется через атрибут __code__, атрибуты классов и модулей меняются в любой момент. Поэтому интерпретатор не может заранее подставить тело функции в место вызова или отделить от цикла первую итерацию, на которой проверка i == 0 истинна: он не знает, не будут ли по ходу выполнения переопределены имена range и len. Оптимизацию, разрешённую любому компилятору C, приходится выполнять вручную: в примере главы книги проверка i == 0 выполняется на каждой из тысячи итераций, а вынесенная из цикла — один раз, и на стенде функция ускоряется с 13,1 до 9,8 мкс, на четверть.

Важно

Производительность не была главной целью CPython, а совместимость с C API ограничивает изменения внутреннего устройства.

Изложение. Третья причина — сама эталонная реализация языка. CPython компилирует исходный текст в байт-код, а затем цикл интерпретатора выполняет инструкции по одной: для выражения a + b это загрузка двух имён и инструкция BINARY_OP, внутри которой выясняются типы операндов и вызывается нужная реализация сложения. Каждая инструкция — ветвь кода на C с проверками, работой со счётчиками ссылок и созданием объектов-результатов. CPython начинали писать задолго до многоядерных процессоров, производительность никогда не была его главной целью, а совместимость с C API, на котором построены NumPy и тысячи расширений, ограничивает изменения внутреннего устройства. Начиная с версии 3.11 проект Faster CPython ускоряет интерпретатор: специализирующий адаптивный интерпретатор подменяет общие инструкции быстрыми вариантами для встреченных типов, и в среднем 3.11 работает в 1,25 раза быстрее 3.10. В 3.13 появились экспериментальный JIT-компилятор и отдельная сборка без глобальной блокировки интерпретатора. Альтернативная реализация PyPy с JIT-компилятором ускоряет чистый Python в разы, но совместима не со всеми расширениями на C.

Пояснение

О производительности думают с самого начала, выбирая алгоритм и структуры данных; переписывают ради скорости — после замера.

Изложение. Фраза Кнута о преждевременной оптимизации — одна из самых цитируемых в программировании, и обычно её приводят без второй половины. Полностью она говорит, что о мелкой эффективности следует забыть в 97 процентах случаев, но нельзя упускать возможности в критических 3 процентах. С ней согласуются три правила оптимизации: не делать; делать позже; делать оптимально. Противоречия здесь нет: думать о производительности необходимо с самого начала, выбирая алгоритм и структуры данных, а переписывать код ради скорости — лишь тогда, когда замер показал, что это требуется. Самая быстрая оптимизация — та, которую не пришлось выполнять, потому что программа и так укладывается в отведённое время. Обратная крайность — архитектура, не продуманная вовсе: медленную систему, построенную без расчёта на объём данных, поздняя оптимизация не исправляет.

Пояснение

Закон Амдала: ускорение части программы ограничено долей её времени.

Изложение. Главная задача — найти место, к которому имеет смысл прикладывать усилия, а порядок работы задают три правила. Первое — профилирование: угадывать, какая часть программы работает дольше всего, бесполезно, профилировщик отвечает на этот вопрос точно. Количественно это выражает закон Амдала: если доля p времени программы ускорена в s раз, вся программа ускоряется в 1 / ((1 − p) + p / s) раз. Функция, занимающая 1 процент времени и ускоренная в десять раз, даёт выигрыш в один процент; даже бесконечно быстрая часть, занимающая 90 процентов, ускоряет программу лишь в десять раз. Второе правило — сохранение корректности: оптимизация легко нарушает правильность незаметно, оставляя результат правдоподобным, но неверным, поэтому перед переписыванием фрагмент покрывают тестами. Третье правило — замер после правки на тех же данных: выигрыш, не подтверждённый замером, считать выигрышем нельзя.

Важно

timeit.timeit возвращает сумму всех запусков, а не время одного.

Изложение. Когда требуется измерить время одного фрагмента, а не снимать полный профиль, применяется модуль timeit из стандартной библиотеки. Из командной строки он запускается как python3 -m timeit: ключ -s задаёт подготовку, которая в замер не входит, а сам фрагмент передаётся строкой; модуль подбирает число запусков так, чтобы прогон длился не меньше 0,2 секунды, повторяет прогон пять раз и печатает лучшее время одного запуска. Из программы вызываются функции timeit.timeit и timeit.repeat: первая возвращает суммарное время number запусков, вторая — список таких сумм по нескольким прогонам. Берут минимум: более медленные прогоны замедлены не самим кодом, а другими процессами. На время замера timeit отключает сборщик мусора, а время измеряет по time.perf_counter; если код создаёт много объектов и сборка мусора входит в его цену, сборщик включают первой строкой подготовки: gc.enable(). Код передаётся строками, поскольку timeit подставляет его в шаблон и исключает накладные расходы на вызов функции-обёртки. В IPython для той же цели предусмотрена команда %timeit, печатающая среднее время и стандартное отклонение по семи прогонам.

Важно

getsizeof не видит объектов, на которые ссылается контейнер: список частиц весит столько же, сколько список чисел.

Изложение. Измерение памяти в Python затруднено, и первый способ, подсказанный документацией, вводит в заблуждение. Функция sys.getsizeof возвращает размер самого объекта: для списка это массив ссылок, но не объекты, на которые эти ссылки ведут. Поэтому список из миллиона экземпляров класса весит по getsizeof столько же, сколько список из миллиона чисел. Модуль tracemalloc из стандартной библиотеки отслеживает выделения памяти интерпретатором: get_traced_memory возвращает текущий и пиковый объём, а снимки take_snapshot показывают, какие строки кода выделили больше всего памяти. У массива NumPy точный размер данных возвращает атрибут nbytes. Память процесса в целом, RSS, показывают ps и top, но она включает запас, который аллокатор удерживает после освобождения объектов, поэтому для сравнения структур данных она плохо подходит.

Пояснение

__slots__ указывают в каждом классе иерархии: иначе словарь атрибутов возвращается.

Изложение. Список чисел хранит не числа, а ссылки на объекты: на стенде каждый элемент списка вещественных чисел обходится в 8 байт ссылки и 24 байта объекта float. Модуль array хранит числа примитивного типа подряд, по 8 байт на double, а массив NumPy устроен так же, но вдобавок поддерживает вычисления. Кортеж немного компактнее списка: ему не нужен запас под рост, который держит список, созданный включением или append. Атрибут __slots__ отменяет у экземпляров словарь атрибутов и размещает объявленные поля в фиксированных ячейках; на стенде это экономит четверть памяти на частицу из трёх полей. С наследованием __slots__ неудобен: его указывают в каждом классе иерархии, иначе словарь атрибутов возвращается и экономия исчезает. Иногда последовательность не требуется хранить вовсе: range вычисляет элемент по индексу, а генератор выдаёт значения по одному.

Объект без ссылок освобождается сразу, недостижимые циклы находит сборщик мусора. Утечкой в Python называют долгоживущие ненужные объекты: на них ссылаются кеш, глобальный список, аргумент по умолчанию.

Пояснение

Кеш ограничивают: functools.lru_cache(maxsize=…). Рост памяти показывает сравнение двух снимков tracemalloc.

Изложение. В смысле C++ утечек в Python почти нет: объект освобождается, когда на него не остаётся ссылок, а циклические ссылки находит поколенческий сборщик мусора, разобранный в главе книги «Объекты и память». Утечкой в Python обычно называют долгоживущие ненужные объекты, на которые кто-то продолжает ссылаться. Классических источников три. Изменяемый аргумент по умолчанию создаётся один раз при определении функции и накапливает данные всех вызовов. Кеш, заведённый на атрибуте класса, общий для всех экземпляров и растёт неограниченно: записи из него никто не удаляет. Большой массив в локальной переменной длинной функции живёт до её конца, даже если больше не нужен. Кеш ограничивают по размеру, например декоратором functools.lru_cache с параметром maxsize; применённый к методу, такой кеш хранит ссылку на self и удерживает экземпляры, пока запись не вытеснена. Место роста памяти находят сравнением двух снимков tracemalloc, сделанных до и после подозрительного участка.

import numba
import numpy as np
 
@numba.njit
def jit_product(X, Y):
    n, m = X.shape
    p = Y.shape[1]
    Z = np.zeros((n, p))
    for i in range(n):
        for k in range(p):
            acc = 0.0
            for j in range(m):
                acc += X[i, j] * Y[j, k]

Параметры

Важно

Компиляция не меняет асимптотику: тройной цикл остаётся O(n³).

Изложение. Numba — JIT-компилятор для числового кода на Python. Декоратор @numba.njit заменяет функцию обёрткой, которая при первом вызове выводит типы аргументов, переводит функцию в промежуточное представление LLVM и компилирует его в машинный код; при следующих вызовах с теми же типами сразу выполняется готовый код. Numba работает с числами и массивами NumPy, а не со списками произвольных объектов, поэтому матрицы передаются как массивы float64. Лучше всего Numba ускоряет явные циклы по элементам: выражение над срезами внутри цикла, например (X[i, :] * Y[:, k]).sum(), создаёт временные массивы и замедляет функцию в несколько раз. Первый вызов включает компиляцию и длится в тысячи раз дольше самого счёта, поэтому замер проводят после прогрева; параметр cache=True сохраняет скомпилированный код на диск между запусками, а parallel=True вместе с prange распределяет итерации цикла по ядрам. Компиляция ускоряет константу, но не меняет асимптотику: квадратичный алгоритм остаётся квадратичным.

from numba import njit, prange
 
def forces_par(x, y, z, fx):
    for i in prange(len(x)):       # по ядрам
        for j in range(len(x)):
            if i != j:
                r3 = ((x[j]-x[i])**2 + (y[j]-y[i])**2
                      + (z[j]-z[i])**2)**1.5
                fx[i] += (x[i]-x[j]) / r3
 
par = njit(parallel=True)(forces_par)

Для физика

Сильноточный пучок расталкивает сам себя; в коде REDPIC суммирование кулоновских сил между макрочастицами — самая затратная функция расчёта.

Пояснение

Каждая частица взаимодействует с каждой: сложность O(N²), и слагаемые для разных i независимы — внешний цикл распараллеливается.

Изложение. Умножение матриц — учебный пример; на реальной задаче выигрыш выглядит так же. В коде REDPIC, которому в книге посвящена отдельная глава, пучок представлен ансамблем макрочастиц, а самой затратной функцией расчёта является суммирование кулоновских сил между частицами — эффект пространственного заряда, из-за которого сильноточный пучок расталкивает сам себя. Каждая частица взаимодействует с каждой, поэтому сложность — O(N²). Цикл, записанный напрямую, допускает и JIT-компиляцию, и распараллеливание: слагаемые для разных i вычисляются независимо. Для параллельной версии внешний range заменяется на prange, так Numba узнаёт, какой цикл распределить по ядрам. Запись njit(parallel=True)(forces_par) вместо декоратора удобна, когда одну функцию измеряют в нескольких режимах.

Важно

Без проверки границ ошибка индекса не вызывает IndexError, а портит чужую память.

Изложение. Второй путь к машинному коду — Cython, язык, представляющий собой Python с объявлениями типов C. Файл .pyx транслируется в код на C, компилятор C собирает из него модуль расширения, и модуль импортируется как обычный; команда cythonize -i выполняет всю сборку на месте. Без объявлений типов Cython порождает вызовы C API Python для каждой операции, и выигрыша почти нет. Объявления cdef для локальных переменных и типизированные представления памяти double[:, :] для массивов позволяют обращаться к числам напрямую, без объектов. Декораторы boundscheck(False) и wraparound(False) отключают проверку выхода за границы и поддержку отрицательных индексов. Взамен ошибка в индексе перестаёт вызывать IndexError и приводит к обращению в чужую память без какого-либо сообщения, поэтому границы такого цикла выверяют вручную. Команда cython -a строит HTML-отчёт, в котором жёлтым отмечены строки, всё ещё обращающиеся к C API Python.

Для физика

Пояснение

Cython выбирают, когда нужен готовый модуль без компилятора на стороне пользователя или обёртка библиотеки на C.

Изложение. Numba компилирует функцию на лету, при первом вызове, и выводит типы по аргументам: для численного цикла над массивами достаточно добавить декоратор, и никакой сборки не требуется. Её ограничение — поддерживаемое подмножество Python: числа, массивы NumPy, кортежи, простые классы через jitclass; со строками, словарями произвольных объектов и сторонними библиотеками она работает плохо или не работает вовсе. Cython компилирует заранее: типы объявляются вручную, требуется компилятор C и шаг сборки, зато результат — обычный модуль расширения, который распространяется готовым пакетом формата wheel и не требует компилятора на стороне пользователя, а из кода на Cython можно напрямую вызывать функции библиотек на C и C++. Поэтому Cython чаще используют для обёрток существующих библиотек, а для ускорения числовых циклов научного кода первым выбором служит Numba.

Изложение. Векторизация переносит цикл из интерпретатора в скомпилированный код NumPy: операция записывается над массивом целиком, а поэлементный цикл выполняется на C. Матричное умножение X @ Y, как и X.dot(Y), вызывает BLAS — библиотеку линейной алгебры, использующую векторные инструкции процессора и оптимально работающую с кешем. Тип данных определяет больше, чем запись: BLAS поддерживает только вещественные и комплексные типы, и целочисленные матрицы NumPy перемножает собственным циклом: на матрицах 64×64 на стенде вчетверо медленнее, а с ростом размера разрыв многократно увеличивается, поскольку этот цикл не использует ни блочной обработки, ни нескольких ядер. Векторизация не бесплатна по памяти: пространственный заряд без циклов требует массивов разностей размером N×N, и при больших N они не помещаются в кеш, а затем и в память. Numba и Cython необходимы там, где задача не векторизуется или векторизация требует слишком много памяти.

Для физика

Перебор параметров установки — естественная задача для процессов: расчёты независимы.

Пояснение

Подробно — главы книги «Многопоточность и GIL» и «Асинхронность».

Изложение. Глобальная блокировка интерпретатора, GIL, пропускает в интерпретатор CPython только один поток одновременно, поэтому потоки не ускоряют вычисления на чистом Python. Вычислительные задачи распараллеливают процессами: concurrent.futures.ProcessPoolExecutor, модуль multiprocessing или пакет joblib запускают несколько интерпретаторов, у каждого своя блокировка; плата — запуск процессов и передача данных между ними. Скомпилированный код может освободить GIL: Numba с prange и Cython с prange из модуля cython.parallel выполняют циклы на нескольких ядрах внутри одного процесса, а функцию Cython с блоком nogil можно вызывать одновременно из нескольких потоков. Для задач, которые в основном ожидают ввода-вывода, достаточно потоков или asyncio: во время ожидания GIL свободен. Начиная с Python 3.13 существует отдельная сборка интерпретатора без GIL, в которой потоки выполняют код Python на всех ядрах: в 3.13 она экспериментальная, с 3.14 поддерживается официально (PEP 779), а расширения на C должны её поддерживать. Подробно эти темы разобраны в главах книги «Многопоточность и GIL» и «Асинхронность». Для физиков: перебор параметров установки или ансамбль независимых расчётов — естественная задача для пула процессов: каждый расчёт выполняется в своём процессе, а результаты собираются в конце.

Python медленный не потому, что плохо написан, а потому, что гибок: тип каждого значения выясняется при выполнении, всё может быть изменено на лету, а цикл интерпретатора работает с объектами в куче. Ускорять имеет смысл только измеренное: timeit отвечает на вопрос, какой из двух фрагментов быстрее, cProfile и line_profiler — где программа проводит время, py-spy — чем занят уже работающий расчёт. Самый дешёвый выигрыш даёт смена структуры данных или алгоритма; микрооптимизации дают проценты, а рекомендации устаревают с выходом новых версий интерпретатора, поэтому каждая проверяется замером. Память измеряют tracemalloc, а не getsizeof; числа хранят в массивах, а многочисленные объекты — со __slots__. NumPy, Numba и Cython переносят горячий цикл в машинный код и ускоряют его в десятки и сотни раз; следующие шаги — процессы и видеокарта. Сначала правильно, потом быстро.
