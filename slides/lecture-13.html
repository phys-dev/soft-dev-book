Перейти от папок с файлами к базе данных, которой можно доверять

Тот, кто понимает модель данных, индексы и транзакции, проектирует схему журнала измерений, пишет запросы, которые отвечают за миллисекунды, не теряет записанное при сбоях и одновременной работе, восстанавливает базу из резервной копии и выбирает СУБД по задаче, а не по моде.

Изложение. Цель лекции — перейти от папок с файлами к базе данных, которой можно доверять. Доверие складывается из нескольких свойств: данные проверяются при записи и не противоречат друг другу, нужное находится за миллисекунды, а не за часы работы скрипта, подтверждённая запись не теряется ни при сбое, ни при одновременной работе нескольких программ, а после ошибочной команды базу можно восстановить. Каждое из этих свойств обеспечивает отдельный механизм СУБД, и лекция рассматривает их по порядку: схема и ограничения, индексы и планы, транзакции, резервные копии. Вторая часть цели — прикладная: работать с базой из программ на Python и выбирать систему под задачу, а не по популярности.

Кампания измерений, например калибровка датчиков положения пучка, состоит из заходов, различающихся энергией пучка и оператором, а в каждом заходе с нескольких каналов снимаются точки — время и значение. Температура магнита медленно растёт, ток пучка экспоненциально спадает. Миллион строк для СУБД немного, но этого уже достаточно, чтобы увидеть разницу между полным просмотром таблицы и поиском по индексу.

Изложение. Хранение данных в лаборатории обычно начинается с файла result.csv; затем появляются result_final.csv, result_final_v2.csv и папки по датам с десятками файлов, названных по энергии пучка и фамилии оператора. Одновременный доступ: скрипт сбора дописывает файл, а программа анализа в тот же момент читает недописанную строку, два писателя портят файл. Целостность: CSV не проверяет ни типов, ни ссылок, и в столбец температуры попадает строка «error». Поиск: чтобы найти точки одного канала одного захода, приходится читать все файлы целиком. Восстановление: сбой посреди записи оставляет файл в промежуточном состоянии. Система управления базами данных, СУБД, представляет собой программное обеспечение, которое берёт эти задачи на себя: транзакции, блокировки и версии строк разграничивают доступ, типы, ключи и ограничения проверяют данные при записи, язык SQL и индексы находят нужное, журнал упреждающей записи WAL и резервные копии восстанавливают базу. Кроме того, СУБД отделяет хранение от логики программ, что позволяет нескольким программам работать с одной базой. Запрос при этом описывает, что требуется найти, а не как перебирать файлы.

Нагрузка задаёт устройство системы: строки или столбцы на диске, транзакции, способ вставки.

Для физика

Журнал запусков — OLTP, анализ архива за сезон — OLAP, медленный контроль ускорителя — временные ряды.

Изложение. Системы различаются прежде всего нагрузкой, под которую они построены. OLTP, обработка транзакций в реальном времени, представляет собой множество коротких операций, каждая из которых читает или меняет несколько строк: запись нового захода, оплата в интернет-магазине. Ответ нужен за миллисекунды, а данные должны оставаться согласованными при тысячах одновременных клиентов. OLAP, аналитическая обработка, — редкие тяжёлые запросы, которые просматривают миллионы и миллиарды строк ради нескольких чисел, например статистика параметров пучка за сезон; ответ допустимо ждать секунды. Временные ряды сочетают обе черты: непрерывный поток мелких вставок «метка времени — значение» и аналитические запросы по окнам времени, как в системе медленного контроля ускорителя, где сотни датчиков вакуума, температуры и токов опрашиваются каждую секунду годами. От профиля нагрузки зависит устройство системы: OLTP-базы хранят таблицу по строкам и поддерживают транзакции, аналитические хранят данные по столбцам, что ускоряет агрегацию по нескольким столбцам миллиардов строк. Использовать систему не по назначению можно, но дорого: аналитика на PostgreSQL ограничена скоростью полного чтения больших таблиц, а частые мелкие вставки в ClickHouse перегружают его фоновые слияния.

Пояснение

SQLite не заменит кластер, а кластер ради сотни байт не разворачивают: систему выбирают по нагрузке и объёму.

Изложение. Вместо перечня сотен систем рассмотрим несколько признаков, по которым они различаются; таблица сравнивает четыре системы, которые часто встречаются вместе. Объём: SQLite хранит базу в одном файле и уместна до сотен гигабайт, PostgreSQL обслуживает терабайты на одном сервере, ClickHouse — петабайты на кластере, а Valkey и Redis ограничены оперативной памятью. Нагрузка: SQLite — встраиваемая OLTP-база, PostgreSQL — классическая OLTP, ClickHouse — классическая OLAP, Valkey — хранилище «ключ — значение» в памяти. Язык запросов: PostgreSQL почти полностью следует стандарту SQL, у ClickHouse свой диалект SQL, а у Valkey вместо языка — набор команд, и фильтрацию по значениям выполняет приложение. Транзакции: SQLite и PostgreSQL обеспечивают полный набор гарантий ACID; в ClickHouse привычных транзакций нет, но вставка блока строк в одну партицию таблицы семейства MergeTree атомарна; Valkey выполняет каждую команду атомарно, а группу команд MULTI/EXEC — подряд, без вклинивания чужих запросов, но без отката. Репликация: у SQLite встроенной нет — в поставке есть утилита sqlite3_rsync для разовой синхронизации копии, а непрерывную репликацию дают сторонние средства; PostgreSQL поддерживает физическую и логическую, ClickHouse реплицирует таблицы семейства Replicated с координацией через ClickHouse Keeper, Valkey передаёт изменения репликам асинхронно.

Новое соединение с PostgreSQL — новый процесс; пул соединений, например PgBouncer, переиспользует их.

Для физика

SQLite — база одного исследователя и его скриптов; PostgreSQL — общая база группы с правами доступа.

Изложение. По архитектуре СУБД делятся на встраиваемые и клиент-серверные. SQLite является библиотекой, которая работает внутри процесса программы: обращение к базе — вызов функции, без сети и отдельного сервиса, а вся база — файл на локальном диске, рядом с которым в режиме WAL находится файл журнала. Поэтому SQLite не требует установки и настройки, но права доступа к ней — права на файл, а писать в базу одновременно могут только процессы одной машины. PostgreSQL представляет собой сервер: главный процесс принимает соединения на порту 5432 и для каждого клиента порождает отдельный процесс, а процессы координируются через общую память, где хранятся буферы страниц, блокировки и сведения о транзакциях. Модель «процесс на соединение» надёжна и прозрачна: утечка памяти в одном сеансе исчезает вместе с процессом, а зависший сеанс виден в списке процессов вместе с типом выполняемой команды; текст запроса показывает представление pg_stat_activity. Цена — дорогое соединение: открыть его заметно дороже, чем выполнить простой запрос, а один сервер выдерживает порядка тысяч одновременных соединений. Программы, которые открывают соединение на каждый запрос, ставят перед сервером пул соединений, например PgBouncer: в транзакционном режиме он выдаёт серверное соединение клиенту на время одной транзакции. ClickHouse обслуживает клиентов потоками из пула, а Valkey выполняет команды в одном главном потоке.

Изложение. Реляционная модель, предложенная Эдгаром Коддом в 1970 году, остаётся основной: данные хранятся в таблицах, которые в теории называются отношениями. Порядок строк в таблице не определён, и упорядоченными они приходят только при явной сортировке в запросе. Пояснение

Денормализация — сознательное дублирование ради быстрой аналитики; начинают с нормализованной схемы.

Изложение. Проще всего хранить всё в одной широкой таблице, повторяя в каждой точке измерения название кампании, энергию пучка и фамилию оператора. Такая схема работает до первой правки: если в фамилии оператора опечатка, исправлять приходится миллион строк, а сбой на середине оставляет данные противоречивыми. Это называется аномалиями обновления. Нормализация устраняет дублирование: каждый факт хранится один раз, а остальные таблицы на него ссылаются. Формально её описывают нормальные формы. Для первой необходимо, чтобы значения были атомарными, без повторяющихся групп: не список каналов в одной ячейке, а отдельная строка на канал. Вторая и третья сводятся к правилу «каждый неключевой столбец зависит от ключа, от всего ключа и ни от чего, кроме ключа»: энергия — свойство захода и хранится в runs, название установки — свойство кампании и хранится в experiments. Обратный процесс, денормализация, тоже бывает оправдан: для тяжёлой аналитики собирают широкую таблицу, чтобы не соединять таблицы в каждом запросе, — в таком виде данные часто переносят в аналитическую СУБД. Но проектирование начинают с нормализованной схемы.

Важно

Без PRAGMA foreign_keys = ON ссылка на несуществующую кампанию проходит без ошибки.

Изложение. Схема таблицы является одновременно документацией и проверкой, которую база выполняет при каждой записи независимо от кода программы. Первичный ключ уникален и по стандарту не может быть пустым; в SQLite столбец INTEGER PRIMARY KEY совпадает с внутренним номером строки rowid и заполняется автоматически, а первичный ключ другого типа из-за давней ошибки допускает NULL, если столбец не объявлен NOT NULL, а таблица — не STRICT и не WITHOUT ROWID. NOT NULL запрещает пропуск значения, UNIQUE — повтор; в примере номер захода уникален внутри кампании. REFERENCES объявляет внешний ключ. Особенность SQLite: внешние ключи проверяются, только если в соединении выполнена команда PRAGMA foreign_keys = ON, и включать её необходимо в каждом новом соединении; без неё ссылка на несуществующую кампанию принимается без ошибки. PostgreSQL и MySQL с движком InnoDB проверяют внешние ключи по умолчанию. Ещё одна особенность SQLite — динамическая типизация: в столбец REAL можно записать строку «error», и база сохранит её как текст; таблицы с ключевым словом STRICT, появившиеся в версии 3.37, обеспечивают строгую проверку типов. Нарушение ограничения завершается ошибкой записи, а не порчей данных, которую обнаруживают через полгода. Время в журнале установки хранят в UTC или, в PostgreSQL, типом timestamptz: строка местного времени без смещения при переводе часов и при обмене данными между площадками даёт повторы и пропуски меток.

Пояснение

LEFT JOIN сохраняет строки левой таблицы без пары: так находят заходы без измерений.

Изложение. SQL является декларативным языком: запрос описывает, какой результат нужен, а как его получить, решает СУБД. Рассмотрим запросы на слайде. Первый выбирает десять последних заходов с энергией выше 10 МэВ: WHERE отбирает строки, ORDER BY с DESC сортирует по убыванию, LIMIT ограничивает результат. Второй запрос собирает разложенные по таблицам данные обратно: JOIN сопоставляет строки по условию, обычно «внешний ключ равен первичному», а псевдонимы AS m, AS r и AS e сокращают имена. Части запроса записываются в одном порядке, а логически выполняются в другом: сначала FROM и JOIN формируют строки, затем WHERE отбирает их, GROUP BY и HAVING группируют, SELECT вычисляет столбцы результата, ORDER BY и LIMIT сортируют и обрезают. Поэтому по стандарту псевдоним столбца из SELECT нельзя использовать в WHERE, и PostgreSQL на такой запрос ответит ошибкой. Кроме обычного, внутреннего JOIN, есть LEFT JOIN: он сохраняет строки левой таблицы и при отсутствии пары справа заполняет её столбцы значением NULL. В скриптах столбцы перечисляют явно, а не через звёздочку: это позволяет сохранить прежний состав результата при добавлении столбца в таблицу.

Изложение. Агрегатные функции COUNT, SUM, AVG, MIN и MAX сворачивают группу строк в одно значение, а GROUP BY задаёт признак группы. Главное практическое следствие: агрегация выполняется там, где хранятся данные, и в программу на Python приходит готовая сводка из нескольких десятков строк вместо миллиона точек.

Пояснение

Поиск — спуск от корня к листу: три-четыре страницы вместо просмотра миллиона строк.

Для физика

Индекс (run_id, channel) ускоряет поиск по run_id и по паре, по channel — лишь перебором run_id.

Изложение. Без индекса запрос с условием WHERE просматривает всю таблицу строку за строкой: это полный просмотр, SCAN в плане SQLite и Seq Scan в PostgreSQL. Индекс представляет собой отдельную структуру, обычно B-дерево, в которой значения индексируемых столбцов хранятся упорядоченными вместе со ссылками на строки таблицы: в SQLite — номером строки rowid, в PostgreSQL — адресом версии строки. Каждый узел дерева — страница размером в несколько килобайт с сотнями ключей, поэтому даже для миллиона строк дерево имеет три-четыре уровня, и поиск сводится к спуску от корня к листу. На схеме упрощённо показаны значения run_id: чтобы найти заход 7, достаточно прочитать корень, один внутренний узел и лист, где находятся номера строк 150001–155000 — точки канала BPM01 этого захода. Упорядоченные ключи в листьях позволяют читать диапазон значений подряд, от листа к соседнему, и выдавать данные уже отсортированными; в PostgreSQL соседние страницы каждого уровня к тому же связаны ссылками, а SQLite переходит к следующему листу через родительский узел. Индекс по нескольким столбцам упорядочен сначала по первому столбцу, затем по второму, как телефонный справочник по фамилии и имени: индекс (run_id, channel) ускоряет поиск по run_id и по паре run_id и channel, а по одному channel — только перебором значений run_id, пропуском (skip scan): SQLite выбирает его после ANALYZE, если значений первого столбца немного, PostgreSQL — с версии 18. Число чтений, таким образом, растёт как логарифм размера таблицы и потому почти не зависит от него.

Важно

Индекс на каждый столбец замедляет запись и раздувает базу: индексы строят под частые запросы.

Изложение. Индекс не бесплатен. Он занимает место: как мы видели в демонстрации, индекс по двум столбцам увеличил файл на 16 МиБ, почти наполовину. Индекс полезен, когда условие отбирает малую долю строк; если же под условие попадает большая часть таблицы, чтение строк вразброс по индексу обходится дороже последовательного чтения всей таблицы, и планировщик справедливо выбирает полный просмотр. Порядок столбцов определяет, какие запросы ускоряются: индекс (run_id, channel, t) позволяет найти точки канала и сразу получить их упорядоченными по времени, без временного B-дерева. Индекс, который содержит все столбцы, нужные запросу, называется покрывающим: таблицу при таком запросе не читают вовсе. Первичный ключ и ограничение UNIQUE индексируются автоматически, а столбцы внешних ключей в SQLite и PostgreSQL индексируют вручную, если их не покрывает индекс, начинающийся с того же столбца: без индекса на measurements.run_id удаление захода при включённой проверке внешних ключей просматривает все измерения. В журнале этот ключ покрывает индекс (run_id, channel, t), а runs.experiment_id — индекс ограничения UNIQUE (experiment_id, run_number); MySQL создаёт индекс по внешнему ключу сам. Таким образом, индексы строят под реальные частые запросы, а их использование проверяют планом.

Важно

После массовой загрузки статистика устаревает: ANALYZE выполняют сразу после неё.

Изложение. Один и тот же запрос можно выполнить многими способами: прочитать таблицу целиком или спуститься по индексу, соединить таблицы вложенным циклом, хешированием или слиянием, в том или ином порядке. Планировщик перебирает варианты и выбирает самый дешёвый по оценке стоимости в условных единицах: в PostgreSQL чтение страницы подряд стоит 1, чтение страницы вразброс — 4, обработка строки — 0,01; эти веса задаются параметрами seq_page_cost, random_page_cost и cpu_tuple_cost. Оценка зависит от селективности условия, то есть доли строк, которые оно отберёт, а её планировщик берёт из статистики: числа строк, числа различных значений, самых частых значений и гистограммы распределения. Статистику собирает команда ANALYZE. В PostgreSQL её запускает фоновая автоочистка, когда изменилась заметная доля таблицы; SQLite собирает статистику только по команде ANALYZE или PRAGMA optimize и хранит её в таблице sqlite_stat1, где для индекса записаны число строк и среднее число строк на одно значение. Когда данные меняются быстрее, чем обновляется статистика, например после массовой загрузки, план опирается на устаревшие сведения, и запрос, выполнявшийся за миллисекунды, начинает занимать секунды. По этой причине ANALYZE необходимо выполнять сразу после массовой загрузки. Подсказок планировщику в ядре PostgreSQL нет, их дают расширения, и относятся к ним настороженно: закреплённый план опирается на прошлые предположения о данных.

Изложение. Транзакция представляет собой группу операций, которая выполняется как единое целое. Её гарантии описывает аббревиатура ACID. Атомарность: применяются либо все операции, либо ни одна, и сбой на середине откатывает сделанное. Согласованность: база переходит из одного корректного состояния в другое, не нарушая ограничений. Изолированность: параллельные транзакции не видят промежуточных состояний друг друга; насколько строго, задаёт уровень изоляции. Долговечность: подтверждённые командой COMMIT данные сохраняются даже при внезапном отключении питания, потому что до ответа клиенту изменения записаны в журнал на диске. Модуль sqlite3 открывает транзакцию неявно перед первой изменяющей командой, commit её фиксирует, rollback откатывает. Ту же пару обеспечивает конструкция with con:, которая фиксирует транзакцию при выходе из блока и откатывает при исключении, но соединение, в отличие от файла в конструкции with open, не закрывает. Долговечность требует времени: каждая фиксация ждёт, пока диск подтвердит запись.

Пояснение

По умолчанию: PostgreSQL — READ COMMITTED, MySQL InnoDB — REPEATABLE READ, SQLite — SERIALIZABLE.

Важно

На строгих уровнях PostgreSQL может прервать транзакцию ошибкой сериализации: её повторяют.

Изложение. Полная изоляция, при которой параллельные транзакции дают тот же результат, что и выполненные по очереди, дорога, поэтому стандарт SQL определяет четыре уровня изоляции через аномалии, допустимые на каждом из них. Рассмотрим их по порядку. Грязное чтение — транзакция видит незафиксированные изменения другой. Неповторяемое чтение — повторный запрос той же строки внутри транзакции возвращает другое значение, потому что другая транзакция успела её изменить и зафиксировать. Фантомы — повторный запрос по условию возвращает новые строки. Аномалия сериализации — результат параллельных транзакций невозможно получить ни при каком порядке их последовательного выполнения. Таблица показывает минимальные требования стандарта; реализации бывают строже. PostgreSQL по умолчанию работает на уровне READ COMMITTED, где каждый оператор видит данные, зафиксированные к его началу; на уровне REPEATABLE READ вся транзакция видит снимок на момент первого запроса, и фантомов в PostgreSQL на нём тоже нет, а READ UNCOMMITTED ведёт себя как READ COMMITTED. MySQL с движком InnoDB по умолчанию использует REPEATABLE READ, а SQLite обеспечивает сериализуемость, разрешая в каждый момент одну пишущую транзакцию. Строгие уровни требуют от приложения дополнительной логики: на уровнях REPEATABLE READ и SERIALIZABLE PostgreSQL может прервать транзакцию ошибкой сериализации, и её необходимо повторить целиком.

Пояснение

Писатель всегда один: второй ждёт timeout (в sqlite3 — 5 с) и получает database is locked.

Важно

WAL не работает на сетевом диске (NFS, SMB): все процессы должны быть на одной машине.

Изложение. SQLite разграничивает доступ блокировками всего файла базы. В режиме журнала по умолчанию, DELETE, транзакция перед изменением страницы копирует её прежнее содержимое в файл lab.db-journal, а новые данные пишет прямо в lab.db; при сбое прежние страницы восстанавливаются из журнала. Для фиксации транзакции писателю необходимо получить исключительную блокировку, и он ждёт, пока не закончатся все читающие транзакции; новые читатели, в свою очередь, ждут окончания фиксации. В режиме WAL, который включает команда PRAGMA journal_mode=WAL, новые версии страниц дописываются в файл lab.db-wal, а основной файл не меняется до контрольной точки, которая переносит страницы обратно. Читатель видит снимок базы на момент начала своей транзакции, что позволяет читать и писать одновременно: график строится, пока скрипт сбора пишет данные. Писатель в обоих режимах один: вторая пишущая транзакция ждёт освобождения блокировки время timeout, по умолчанию 5 с в модуле sqlite3, и затем получает ошибку database is locked; транзакцию, которая будет писать, начинают командой BEGIN IMMEDIATE, чтобы ждать блокировку сразу, а не посреди работы. Режим WAL запоминается в файле базы, но требует, чтобы все процессы работали на одной машине: на сетевом диске он неприменим.

Пояснение

UPDATE — новая версия и отметка xmax у старой; мёртвую версию убирает VACUUM, когда её не видит ни один снимок.

Важно

Долгая транзакция удерживает старый снимок: мёртвые версии накапливаются, таблица и индексы разрастаются.

Изложение. PostgreSQL изолирует транзакции не блокировками на чтение, а многоверсионностью, MVCC. UPDATE не меняет строку на месте: он записывает новую версию строки, а у старой отмечает в служебном поле xmax номер изменившей транзакции; у каждой версии в поле xmin записан номер создавшей её транзакции. Каждый запрос работает со снимком — сведениями о том, какие транзакции были зафиксированы к его началу, — и по xmin и xmax решает, какую из версий видеть. Такая схема обеспечивает независимость чтения и записи: читатели не ждут писателей, а писатели не ждут читателей; ждать друг друга приходится только транзакциям, изменяющим одну и ту же строку. Откат дёшев: транзакция лишь помечается прерванной, а её версии становятся невидимыми. Обратная сторона — мёртвые версии, которые не видит уже ни один снимок: их убирает VACUUM, обычно запускаемый автоматически. Долгая транзакция или забытый открытый сеанс удерживают старый снимок, VACUUM не может удалить версии, которые этот снимок ещё видит, и при частых изменениях таблица и индексы разрастаются, а простой запрос начинает читать тысячи мёртвых версий ради одной живой. Обычный VACUUM освобождает место внутри файла, а уменьшает файл, лишь когда освободились страницы в самом его конце; сжимает таблицу VACUUM FULL, переписывая её под исключительной блокировкой.

Он создаёт таблицу runs со строкой energy = 5.0, а сеанс B начинает транзакцию на заданном уровне изоляции и читает строку вместе со служебными полями xmin и xmax. На уровне READ COMMITTED B сначала видит версию с xmin=740; после того как A изменил строку и зафиксировал изменение, тот же запрос в той же транзакции B возвращает уже новую версию, xmin=741 и energy = 5.5; это и является неповторяемым чтением. Пояснение

PEP 249: connect, execute, fetchall, commit одинаковы; различаются знаки параметров — ? и %s.

Важно

Соединение с PostgreSQL дорогое: сервис берёт его из пула (psycopg_pool), а не открывает на запрос.

Изложение. Драйверы баз данных в Python следуют общему интерфейсу DB-API, описанному в PEP 249: функция connect возвращает соединение, метод execute выполняет запрос с параметрами, fetchone и fetchall или итерация по курсору возвращают строки кортежами, commit и rollback управляют транзакцией. Общий интерфейс позволяет писать для SQLite и PostgreSQL почти одинаковый код. Различаются знаки параметров: модуль sqlite3 использует вопросительные знаки, драйвер PostgreSQL psycopg — %s. Различается и контекстный менеджер: with con: в sqlite3 только завершает транзакцию, а with psycopg.connect(...) as conn: фиксирует транзакцию и закрывает соединение. Для массовой загрузки в PostgreSQL вместо тысяч INSERT используют команду COPY, которой psycopg передаёт строки потоком: это самый быстрый способ загрузить данные. Соединение с сервером PostgreSQL — отдельный процесс, поэтому сервис открывает соединения не на каждый запрос, а берёт из пула, например psycopg_pool.ConnectionPool. Третья версия psycopg является заменой psycopg2 для нового кода: она умеет работать асинхронно, передаёт параметры серверу отдельно от текста запроса и поддерживает конвейерную отправку команд.

Изложение. Когда часть запроса приходит извне — из формы веб-страницы, аргумента командной строки или присланного файла, — склеивать её с текстом запроса нельзя. Покажем это на примере: если в f-строку подставить ввод ' OR '1'='1, условие превращается в channel = '' OR '1'='1', которое истинно для каждой строки, и запрос возвращает всю таблицу; ввод с точкой с запятой и командой DROP TABLE в драйвере, исполняющем несколько операторов подряд, уничтожит таблицу. Такая атака называется SQL-инъекцией и является одной из самых старых и до сих пор распространённых уязвимостей; её классическая иллюстрация — комикс xkcd 327 о школьнике по имени Bobby Tables. Параметризованный запрос неуязвим по построению: текст запроса и значения передаются драйверу раздельно, и введённая строка остаётся строкой при любом содержимом. Значения передают только параметрами, даже собственные. Имя таблицы или столбца параметром быть не может; если его выбирает пользователь, допустимые имена проверяют по белому списку. Дополнительную защиту обеспечивают права: сервис подключается к базе от роли, которой разрешены только нужные операции с нужными таблицами.

Пояснение

PostgreSQL: create_engine('postgresql+psycopg://…') и установленный драйвер psycopg.

Изложение. ORM, объектно-реляционное отображение, связывает таблицы с классами, строки с объектами, а внешние ключи — с атрибутами-связями; стандартом в Python является SQLAlchemy. Во второй версии модели описываются аннотациями Mapped и функцией mapped_column, запросы строятся функцией select, а выполняются в сеансе Session, который отслеживает изменённые объекты и при commit превращает их в INSERT и UPDATE. Смена SQLite на PostgreSQL сводится к другому адресу базы в create_engine и установленному драйверу psycopg; для простых моделей остальной код не меняется, а различия типов и поведения проявляются на сложных схемах. ORM генерирует обычный SQL, и параметр echo=True выводит его в журнал. Типичная ошибка — проблема N+1: обращение к связи run.measurements в цикле по заходам выполняет отдельный запрос для каждого захода; опция selectinload позволяет загрузить связанные объекты одним дополнительным запросом. Та же ошибка возникает при обращении к m.run в цикле по точкам: JOIN в select служит только отбору строк и связь не заполняет, поэтому запрос на слайде выбирает сразу нужные столбцы обеих таблиц. Изменения схемы в проекте с ORM оформляют миграциями Alembic. ORM оправдан в приложении с десятком связанных таблиц и типовыми операциями создания, чтения, изменения и удаления, а аналитику с агрегатами и оконными функциями короче и быстрее писать на SQL.

Важно

Для физика

Правило 3-2-1: три копии на двух видах носителей, одна из них — вне здания.

Изложение. Резервная копия защищает от событий, которых транзакции не предотвращают: ошибочной команды DROP TABLE или DELETE без WHERE, сбоя диска, потери машины. Копирование файла базы командой cp корректно, только когда к базе никто не подключён; в режиме WAL подтверждённые транзакции до контрольной точки находятся в отдельном файле, и копия одного основного файла их теряет. SQLite делает согласованную копию во время работы с базой методом Connection.backup() из Python или командой VACUUM INTO. Для PostgreSQL рассмотрим два способа. Утилита pg_dump создаёт логическую копию одной базы — SQL-команды или сжатый архив, который восстанавливает pg_restore, — на момент начала копирования; её можно развернуть и на более новой версии сервера. Утилита pg_basebackup снимает физическую копию файлов всего сервера, а вместе с непрерывным архивом журнала WAL позволяет восстановиться на любой момент времени. Хранят копии по правилу «три-два-один»: три копии на двух видах носителей, одна из них — вне здания. Главное правило — копия без проверенного восстановления копией не считается: восстановление репетируют по инструкции на отдельной машине и проверяют, что данные на месте, а инструкцию пишут так, чтобы её выполнил дежурный ночью, а не только автор.

Команда ls показывает, что основной файл занимает 4096 байт — одну страницу с заголовком, — а данные находятся в файле wal.db-wal размером 28 872 байта рядом с файлом общей памяти wal.db-shm. Копия основного файла командой cp открывается как база без таблиц: консоль python3 -m sqlite3 отвечает no such table: m. Таким образом, подтверждённые данные в такую копию не попали. Метод Connection.backup() из скрипта backup.py и команда VACUUM INTO, выполненная прямо в консоли, делают согласованные копии с 500 строками. После завершения писателя командой kill его соединение закрывается штатно: последнее соединение выполняет контрольную точку, журнал переносится в основной файл, который вырастает до 20 480 байт, файлы -wal и -shm исчезают, и теперь простая копия тоже содержит 500 строк.

Демонстрация. В контейнере pg таблица measurements с миллионом строк заполнена тем же скриптом fill.sql, что и в демонстрации EXPLAIN ANALYZE, а алиас psql запускает клиент внутри контейнера. Первая команда открывает транзакцию, удаляет таблицу и откатывает транзакцию: в PostgreSQL даже изменения схемы транзакционны, и после ROLLBACK таблица на месте со всеми 1 000 000 строк. Затем pg_dump создаёт логическую копию базы в сжатом формате custom и записывает её на стенд в файл lab.dump размером 8 425 662 байта, около 8,0 МиБ. Команда DROP TABLE без транзакции выполняется с автофиксацией, и таблица удалена безвозвратно. Восстановление идёт по правилам репетиции: createdb создаёт пустую базу restored, pg_restore разворачивает в неё архив, и запрос подтверждает, что в восстановленной таблице снова 1 000 000 строк. Восстановление в отдельную базу позволяет сначала проверить данные, а затем вернуть нужную таблицу в рабочую базу, например командой pg_restore с ключом -t.

Для физика

Ошибочный DROP TABLE в 18:03: из ночной копии и архива WAL база восстанавливается на 18:02:59.

Важно

Реплика не заменяет копию: ошибочная команда доходит до неё за доли секунды.

Изложение. Журнал упреждающей записи, WAL, является основой надёжности PostgreSQL: каждое изменение сначала записывается в журнал, и только потом меняются файлы таблиц, поэтому после сбоя сервер восстанавливается, проигрывая журнал от последней контрольной точки. Тот же журнал решает ещё три задачи. Для восстановления базы на любой момент достаточно базовой физической копии и архива сегментов WAL: ночная копия и архив журнала до 18:02:59 возвращают таблицу, ошибочно удалённую в 18:03. Это восстановление на момент времени, PITR; момент задаёт параметр recovery_target_time. Если передавать журнал потоком на другой сервер, получается физическая реплика — побайтовая копия всего сервера, доступная только для чтения; она требует той же основной версии PostgreSQL и той же архитектуры и служит для резервирования и разгрузки чтения. Логическая репликация расшифровывает журнал в изменения строк выбранных таблиц и передаёт их подписчику, который может работать на другой версии PostgreSQL; так переходят на новую версию с минимальным простоем, а сторонние средства тем же способом передают изменения в аналитическую систему. Реплика не заменяет резервную копию: ошибочный DROP TABLE доходит до неё за доли секунды.

Для физика

Временной ряд датчиков секционируют по месяцам: архив старше срока хранения удаляется одной командой.

Пояснение

Встроенное шардирование — у ClickHouse, MongoDB, YDB; в PostgreSQL — расширение Citus или своё в приложении.

Важно

Шардирование планируют заранее: переделка работающей базы в десятки терабайт занимает месяцы.

Изложение. Один сервер PostgreSQL на современном оборудовании годами обслуживает базу лаборатории и даже института, и масштабирование начинают с дешёвых шагов. Пул соединений, например PgBouncer, позволяет тысячам клиентов работать через десятки серверных процессов. Реплики разгружают основной сервер от чтения: отчёты и графики строятся по реплике, хотя она может отставать на доли секунды. Секционирование представляет собой разбиение большой таблицы на части по диапазону, например временного ряда датчиков по месяцам: запрос за неделю читает одну секцию, а данные старше срока хранения удаляются одной командой вместо медленного DELETE. Шардирование распределяет данные по нескольким серверам по ключу; запросы внутри одного шарда остаются быстрыми, а соединения и транзакции между шардами дороги, поэтому небольшие справочники копируют на каждый шард или денормализуют. Встроенное шардирование есть у ClickHouse, MongoDB и YDB, а в PostgreSQL его добавляет расширение Citus или реализует само приложение. Если заранее ясно, что данные не поместятся на один сервер, шардирование закладывают с самого начала: переделка работающей базы в десятки терабайт отнимает месяцы работы целой команды.

Важно

Нижние пороги: нагрузка, упавшая до нуля, — тоже авария.

Изложение. СУБД наблюдают как любое приложение, но с поправкой на её особенности. Ресурсы: процессор, память, свободное место и inode на диске, число операций ввода-вывода в секунду; диск для базы — самый частый узкий ресурс. Запросы: их число в секунду, задержки по перцентилям p50 и p99, а не по среднему, которое скрывает медленные запросы, и распределение по типам — рост доли чтений указывает на отказ кеша перед базой, резкое увеличение числа UPDATE — на ошибку в приложении. Ошибки в журнале под нагрузкой бывают всегда, например при обрыве соединения клиентом, поэтому тревогу поднимают по превышению порога. Специфические признаки PostgreSQL: самые дорогие запросы показывает расширение pg_stat_statements, число мёртвых версий строк — представление pg_stat_user_tables, отставание реплик — pg_stat_replication. Необходимо задавать и нижние пороги: если нагрузка на базу упала до нуля, это авария, хотя ни один верхний порог не превышен — например, данные удалены, и запросам стало нечего делать. Если выделенного администратора баз данных нет, первым вариантом рассматривают управляемую СУБД облачного провайдера, где копии, обновления и мониторинг берёт на себя провайдер.

Для физика

Данные ускорительного комплекса: PostgreSQL — строгие метаданные, MongoDB — разнородные измерения, Redis — текущие состояния устройств.

Изложение. Под отдельные профили нагрузки существуют нереляционные хранилища. Valkey и Redis хранят пары «ключ — значение» в оперативной памяти и отвечают за доли миллисекунды: это кеш результатов тяжёлых запросов, очереди задач, счётчики. По умолчанию они периодически сохраняют снимок памяти RDB и при сбое теряют записанное после него; журнал команд AOF включается отдельно и сокращает потерю примерно до секунды. Команды выполняются в одном потоке, поэтому KEYS со звёздочкой, перебирающая все ключи, на время перебора блокирует сервер для всех клиентов, а перебор ведут командой SCAN. В 2024 году Redis сменил лицензию на несвободную, и сообщество под эгидой Linux Foundation продолжило открытый проект под названием Valkey; в 2025 году Redis 8 вышел и под свободной лицензией AGPLv3. MongoDB хранит документы со вложенной структурой и подходит для разнородных метаданных, где у соседних записей разные поля; схему по умолчанию проверяет код, но коллекции можно задать валидатор $jsonSchema. ClickHouse хранит данные по столбцам и считает агрегаты по миллиардам строк за секунды, но рассчитан на вставку крупными партиями: каждая вставка создаёт на диске новый кусок, и поток вставок по одной строке приводит к ошибке Too many parts. Базы временных рядов InfluxDB и TimescaleDB, расширение PostgreSQL, автоматически прореживают и удаляют старые данные и строят агрегаты по окнам времени. В системе хранения данных ускорительного комплекса, описанной в главе «Работа с базами данных», используются сразу три базы: так называемое полиглотное хранение оправдано, когда профили данных действительно различны, а цена ему — отсутствие транзакции, охватывающей все базы.

Пояснение

Один исследователь и его скрипты — SQLite; общая база группы — PostgreSQL; вторая СУБД — когда первая измеримо не справляется.

Для физика

Тип JSONB в PostgreSQL покрывает потребность в документах для большинства задач лаборатории.

Изложение. Выбор СУБД начинают с вопроса, насколько технология «скучна» в смысле эссе Д. Маккинли «Choose Boring Technology» (2015): система, которая работает десятилетиями, имеет известные ошибки, документацию, сотни специалистов и платную поддержку, реже приводит к неожиданностям, чем модная база с тремя выпусками. Далее проверяют, есть ли резервное копирование с восстановлением на момент времени и насколько просто проверить восстановление. Оценивают объём и рост данных: если ясно, что один сервер не справится, нужна система со встроенным шардированием или заранее спланированное своё. Разные нагрузки разводят по разным системам: транзакционная база для записи и аналитическая копия для отчётов проще в эксплуатации, чем одна система для всего. Ищут истории неудач, а не только успехов: если в блоге разработчиков сообщается лишь о достижениях, а на форумах встречаются только вопросы о подключении, то о слабых местах системы известно мало и первым с ними столкнётся сам пользователь. Проверяют безопасность по умолчанию: например, у FoundationDB сетевой доступ к порту без настроенного TLS даёт полные права, а встроенная авторизация помечена в документации как экспериментальная. Таким образом, для лаборатории практический вывод прост: данные одного исследователя — SQLite, общая база группы — PostgreSQL, где для документов достаточно типа JSONB; вторую систему заводят, когда первая измеримо перестала справляться с конкретной нагрузкой.

лекции

Изложение. Отметим основные выводы лекции. СУБД берёт на себя то, с чем не справляются папки с файлами: одновременный доступ, целостность данных, быстрый поиск и восстановление после сбоев. Схема с первичными и внешними ключами и ограничениями является документацией, которую база проверяет при каждой записи, а SQL описывает нужный результат, оставляя способ его получения планировщику. Индекс на основе B-дерева превращает просмотр миллиона строк в спуск по нескольким страницам, а план запроса выбирается по статистике, которую необходимо поддерживать актуальной. Транзакция выполняется целиком или не выполняется вовсе; одновременный доступ SQLite разграничивает блокировками файла и журналом WAL, а PostgreSQL — версиями строк. Из Python значения в запрос передают только параметрами, ORM и pandas при этом генерируют тот же SQL. Наконец, резервная копия ценна только вместе с проверенным восстановлением, а систему выбирают по нагрузке, начиная с проверенных временем SQLite и PostgreSQL.

Изложение. Надпись на последнем слайде — COMMIT, команда, которая фиксирует транзакцию: после неё изменения становятся видимыми другим транзакциям и сохраняются при сбое. Она парная к SQL на титуле: лекция начиналась с языка запросов и завершается фиксацией сделанного. Лекция завершается ответами на вопросы.
